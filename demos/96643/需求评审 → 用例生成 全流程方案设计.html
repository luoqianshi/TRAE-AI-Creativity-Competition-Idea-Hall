🚨当前痛点

江油高标农田等项目复盘发现，需求到用例链路存在 3 大系统性缺陷：

1. 编码损坏与可读性丢失

中文页名被 hash 化后，req-wiki 出现大量乱码文件名（如 å_å_æ.json），导致 REQ→TC 双向追溯断裂，review 可追溯性评分仅 1/5。

2. 重"抽取"轻"理解/校验"

流水线缺少业务背景理解、已有界面探索和覆盖率自动校验，生成 410 条用例后仍无法保证"每个 REQ 至少 1 正 1 异"。

3. 失败静默与模式混淆

分支抽取 20/20 失败仍继续生成弱图谱；headless、no-browser、CDP、visible 等浏览器模式概念混用，导致实现误判。

🔍需求评审流水线（8+ 阶段）

ht-req-router 编排 8+ 个阶段，新增 Stage 0/1.5/6.5 以强化"理解—校验—修复"闭环。

0

业务背景理解

ht-req-business-context ▼

目的

回答"为什么做、给谁做、成功标准、不做影响、优先级"。无背景时阻塞或触发 Stage 4 自动推断。

输入

  • PRD 摘要 / 目标用户 / 成功指标 / 业务影响 / MoSCoW 优先级

输出

  • business-context.seed.md / candidate.json / candidate.md / confirmation.md
门禁：无业务背景 MUST 标注缺失；置信度 < 0.6 纳入 R01 风险
1

模板健康检查

ht-req-template ▼

目的

验证公司 Axure 需求模板是否最新、字段完整、URL 可访问，避免基于错误模板生成用例。

输入

  • Axure URL、模板元数据、版本号

输出

  • template-health-report.md / 版本漂移告警
门禁：模板版本漂移或字段缺失 MUST 提示用户
1.5

已有界面探索（迭代场景）

expert-ui-explorer ▼

目的

对迭代项目探索已上线真实系统，采集页面模型，避免只基于 Axure 原型而忽略生产环境差异。

输入

  • --existing-system-url / --iteration 标志 / projects/ 历史版本目录

输出

  • existing-ui-model.json / 页面 DOM 快照 / 关系分析
门禁：pages 数 == 0 触发 validation_failure → DP-H08
2

Axure 多页探索

axure-exploration-orchestrator ▼

目的

按浏览器能力预检结果选择适配器，递归发现 Axure 原型中的所有页面与分支。

输入

  • Axure URL、浏览器模式（static / headless-browser / cdp-attached / visible-browser）

输出

  • extract-preflight.json / 页面树 / branch 列表
门禁：预检全失败或分支成功率 < 80% 触发 DP-H08；默认使用 headless 浏览器
3

需求抽取

ht-req-axure-extract ▼

目的

从 Axure 页面提取字段表、交互、流程、实体，生成 REQ-XXX 编号需求。

输入

  • 页面树、DOM 快照、截图

输出

  • REQ-XXX-NNN 需求条目 / field-tables/ / 页面级 extract-result.json
门禁：_slug() 必须保留中文可读；仅转义文件系统非法字符
4

需求分析

ht-req-analyze ▼

目的

汇总需求、反推业务背景、生成 Mermaid 关系图（页面/流程/实体/状态），识别缺失与冲突。

输入

  • REQ 列表、field-tables、existing-ui-model（迭代场景）

输出

  • business-context.candidate.md / relationship-analysis.md / *.mmd
门禁：Mermaid 图不得只有占位节点；空实体比例 < 30%；视觉失败率 > 50% 标记 R05

输入

输出

  • review-report.md / grill-notes.md

🛡️质量门禁与审核清单

质量红线贯穿全链路，未达标不得进入下一阶段。

需求评审 7 维度评分

  • 完整性（Completeness）
  • 一致性（Consistency）
  • 可追溯性（Traceability）
  • 可测试性（Testability）
  • 移动一致性（Mobile Parity）
  • 数据字典准确性（Data Dictionary）
  • OpenSpec 治理合规（Governance）

任一度 < 4 或 high 风险 MUST 进入 Grill Stage。

Grill Stage 触发条件 P0

  • 业务背景置信度 < 0.6 或未确认（R01）
  • 分支抽取成功率 < 80%
  • 视觉/图形抽取失败率 > 50%（R05）
  • Mermaid 图为占位图或空实体 > 30%
  • 7 维度评分任一度 < 4

DP-H08 修复入口

  • 预检全部失败 → 触发 DP-H08
  • 分支抽取成功率 < 80% → 触发 DP-H08
  • R01/R05 阻断级风险 → 触发 DP-H08
  • dynamic-planning-orchestrator 调度修复
  • 修复后使用 --retry-stage 或 --resume-from 复跑

用例生成 20 条 P0 质量红线摘要

  • 每个 REQ 至少 1 正 1 异常/边界用例
  • 输入含 mojibake 必须阻断
  • 用例步骤必须可独立执行
  • 断言必须明确、可判定
  • REQ→TC 双向追溯 100% 可链接
  • 覆盖率 < 90% 必须自审补充

完整 20 条见 gen-test-cases SKILL。

REQ→TC 双向追溯

  • 每条 TC 必须关联 1-N 条 REQ
  • 每条 REQ 必须被至少 1 条 TC 覆盖
  • 追溯矩阵输出至 coverage-report.json
  • 缺失追溯 MUST 生成缺口列表

浏览器模式语义 P0

  • static：无浏览器进程、无可见 UI
  • headless-browser：有浏览器进程、无可见 UI
  • cdp-attached：浏览器会话可附着、UI 可选
  • visible-browser：有浏览器进程且有可见窗口

❓常见问题

Q1：为什么新增 Stage 0 业务背景理解？▼
旧流水线直接从模板检查进入 Axure 探索，缺少"为什么做"的上下文。Stage 0 强制提取 why/目标用户/成功指标，并在缺失时由 Stage 4 反推候选背景，确保评审有据可依。
Q2：Stage 1.5 只在迭代项目触发吗？▼
是的。当 projects/ 下存在同名历史版本、用户传入 --existing-system-url 或 --iteration 时触发；全新项目直接跳过，避免无效探索。
Q3：浏览器模式有哪些，默认是什么？▼
四种：static（无浏览器）、headless-browser（默认，无 UI）、cdp-attached（复用 Chrome/CDP）、visible-browser（可见窗口，仅调试）。标准自动化默认优先 headless 或 static，不依赖可见 UI。
Q4：DP-H08 触发后如何复跑？▼
DP-H08 由 dynamic-planning-orchestrator 接收 validation_failure 事件后调度修复。修复完成后，使用 ht-req-router --retry-stage <stage> 或 --resume-from <stage> 复跑，并在 req-wiki/README.md 追加 recovery-log.md。
Q5：覆盖率 90% 是怎么计算的？▼
coverage_checker.py 按"每个 REQ 至少 1 条正向 + 1 条异常/边界用例"作为达标条件。覆盖率 = 达标 REQ 数 / 总 REQ 数 × 100%，输出 coverage-report.json 与缺口列表。
