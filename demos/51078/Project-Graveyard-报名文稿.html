Project Graveyard

项目墓园 · Vibe Coder 的烂尾项目开源认领社区

让 AI 编程时代被遗忘的半成品项目，被看见、被理解、被认领、被拆件复用，或者被体面归档。

1 创意名称 + 创意介绍

核心定位与产品形态

创意名称
Project Graveyard / 项目墓园
想解决什么问题

AI 编程工具让"开始一个项目"变得前所未有的容易，但让"完成一个项目、交接一个项目、复用一个项目"变得更混乱。

过去开发者的门槛是"我不会写代码"，现在的门槛是"我有 20 个 AI 生成的半成品，但没有一个真正完成"。这些烂尾项目并非毫无价值——它们可能包含一个不错的产品想法、一套可复用的 UI、一段有用的 Prompt，或者一个已验证的失败经验。

Project Graveyard 要做的，就是把这些"废弃项目"变成"可交接资产"。

为什么会想到做这个

在使用 TRAE、Cursor、Claude Code 等 AI 编程工具的过程中，我自己积累了大量"做到一半就放弃"的项目。删掉觉得可惜，放着又占地方，GitHub 上 star 数为 0 的 private repo 越来越多。

我意识到这不是我个人的问题——在 Vibe Coding 浪潮下，"烂尾"是一种普遍现象。而问题的另一面是：很多开发者在寻找半成品组件、学习他人思路、或者想找个项目练手。供需两端都存在，但缺乏一个专门的连接平台。

大概是什么产品

一个 Web 平台。用户可以上传自己做了一半、不想继续但又觉得可惜的项目，由 AI（火山引擎大模型）自动生成多维度评分报告。其他开发者可以浏览、筛选、申请下载感兴趣的项目，与原作者自行联络后继续开发、拆件复用，或者学习归档。

网站本身不做复杂的社区治理和项目管理，只做三件事：上传、评分、匹配。

2 目标用户及痛点

为谁而做，在什么场景下解决什么问题

面向哪些用户
  • Vibe Coding 用户：TRAE、Cursor、Claude Code、Lovable 等 AI 编程工具的活跃用户，项目产出快但完成率低。
  • 独立开发者 / 学生：有大量 side project，想清理库存或者找新项目接手。
  • 转开发人群：产品经理、设计师、运营想转开发，需要半成品项目练手或参考。
  • Hackathon 参与者：赛后项目不想维护，但希望有人能继续。
  • 组件/模板寻找者：不想从零开始，想找个半成品改改就用。
在什么场景下使用
  • 场景 A - 上传方：周末用 TRAE 花 3 小时搭了一个项目骨架，做到登录页就没动力了。打开 Project Graveyard，上传压缩包和 README，AI 自动生成评分报告，设置"授权下载"，挂出去等有缘人。
  • 场景 B - 下载方：想做一个食谱推荐 App，但不想从零写 UI。在 Project Graveyard 搜索"食谱"，找到一个完成度 60% 的项目，AI 报告显示"前端 UI 完成度高，阻塞点在推荐算法"。申请下载，联系原作者，接手前端部分，重写后端逻辑。
  • 场景 C - 学习者：刚学 React，想看看别人怎么组织项目结构。浏览低完成度的项目，下载后分析文件组织和代码风格。
当前痛点

对于上传者：项目烂尾后没有合适的去处。GitHub 上放 private repo 等于雪藏，放 public 又担心代码质量差被人笑话。直接删掉又觉得可惜——毕竟投入了时间和精力。

对于下载者：想找个半成品项目练手或复用组件，但没有专门的搜索渠道。GitHub 上搜"todo app"出来几万个结果，但无法快速判断哪个"烂得刚刚好"——完成度不低到无法运行，也不高到没有改造空间。

对于双方：缺乏一个中立的、带 AI 分析的平台来降低信息差和信任成本。

3 价值与意义

为什么这个创意值得做

效率提升

降低筛选成本：AI 自动分析项目完成度、技术栈、阻塞点和可复用资产，浏览者可以在 10 秒内判断一个项目是否值得下载，而不需要下载整个压缩包逐行阅读。

降低交接成本：通过"为什么烂尾""卡在哪里""哪些部分可复用"等结构化信息，让接手者快速理解项目现状，减少沟通摩擦。

降低重复造轮子：一个项目的 UI 组件、问卷逻辑、Prompt 模板可以被拆出来复用，减少开发者从零开始的时间浪费。

社会价值

减少数字浪费：Vibe Coding 时代产生了大量"数字垃圾"——有价值的半成品被直接删除。Project Graveyard 让半成品有机会被二次利用，延长项目的生命周期。

降低学习门槛：初学者可以通过分析真实的半成品项目（而不是完美的教程代码）来学习实际开发中的取舍、组织和坑点。

建立开发者间的弱连接：两个互不相识的开发者，因为一个烂尾项目产生连接，可能衍生出合作、友谊或新的产品。

4 核心功能模块

MVP 阶段的核心能力

模块 功能描述 MVP 优先级
用户系统 邮箱注册 / GitHub OAuth 登录，个人中心（我的项目、我的申请、账号设置） P0 必须
项目上传 填写项目信息（名称、描述、README、烂尾原因），上传压缩包，选择下载权限（公开/授权）和开源协议 P0 必须
AI 评分报告 火山引擎大模型自动分析项目，输出六维评分（完成度、目标清晰度、技术栈、阻塞点、可复用价值、文档完整度） P0 必须
项目广场 瀑布流展示项目卡片，支持按技术栈、阻塞点类型、完成度筛选和搜索 P0 必须
授权下载 浏览者申请下载 -> 作者收到通知 -> 一键同意/拒绝 -> 生成限时下载链接 P0 必须
项目详情页 展示完整 AI 评分报告、文件结构预览、作者信息、下载/申请按钮 P1 重要

5 与 GitHub 的差异

核心差异化定位

GitHub 是代码仓库，Project Graveyard 是项目遗产交接处。

维度 GitHub Project Graveyard
核心关注点 代码质量、Star、Fork、PR 为什么烂尾、卡在哪里、谁适合接手、哪些可复用
项目状态 默认假设项目是"在进行中" 明确标注"待认领""可拆件""已归档"
信息结构 README + 代码 AI 评分卡 + 烂尾原因 + 阻塞点 + 复用资产清单
用户关系 贡献者、协作者 原作者、接手者、拆件者、旁观者
目标 把项目做得更好 让半成品被复活、拆件、展出或体面安葬

6 Demo 展示主流程

参赛时最适合演示的闭环流程

1
用户登录并上传项目
开发者小李上传一个烂尾的食谱推荐项目 MealMate，填写 README 和烂尾原因。
2
AI 自动生成评分报告
火山引擎大模型分析后输出：完成度 60%、阻塞点为推荐算法、可复用资产为 UI 组件和问卷模块。
3
项目展示在项目广场
项目卡片显示名称、技术栈、完成度星级、阻塞点标签，等待有缘人。
4
另一位用户发现并申请下载
开发者小王搜索"食谱"发现 MealMate，查看 AI 报告后点击"申请下载"，填写微信号和用途。
5
原作者同意授权
小李收到邮件通知，在个人中心一键同意，系统生成 24 小时限时下载链接发给小王。
6
双方自行联络，项目获得第二次生命
小王下载项目包，双方加微信沟通后续计划——可能是接手复活，也可能是只拆几个组件。

7 技术方案

MVP 技术栈与实现思路

前端
Next.js 14 + Tailwind CSS，暗色主题设计，响应式布局，支持 SSR 提升 SEO。
后端
Next.js API Routes + PostgreSQL，RESTful API 设计，JWT 认证，文件上传至火山引擎 TOS。
AI 评分
火山引擎 Ark API（Doubao-pro 模型），通过结构化 Prompt 提取项目信息，返回 JSON 格式六维评分。
第三方服务
火山引擎 TOS（文件存储）、火山引擎短信服务（授权通知）、GitHub OAuth（登录）。
