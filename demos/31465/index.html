STEP 3智能融合引擎

系统将依次执行「语义分块 → 大纲映射 → 内容融合 → 一致性校验」四个阶段。每一步清晰标注由 LLM 还是传统代码负责。

LLM 大语言模型负责
  • 跨资料语义理解与内容整合
  • 按大纲节点生成融合段落
  • 摘要继承与上下文连贯
  • 内容连贯性抽检与精炼
CODE 传统代码负责
  • 资料解析（docx/xlsx/pdf/OCR）
  • 语义分块与 Token 估算
  • 分块→大纲节点映射
  • 排版渲染、图表编号、格式校验

LLM 与传统代码职责边界

系统将确定性任务交给传统代码，语义理解任务交给 LLM，确保在有限算力下稳定输出

01
资料解析 传统代码
解析 docx / xlsx / pdf / 图片 OCR，提取结构化文本与表格
理由：格式解析规则明确，无需语义理解，确定性可复现
02
语义分块 传统代码
基于文档结构 + 语义边界 + Token 约束（8K~32K）进行分块
理由：分块策略需精确可控，避免上下文溢出，确定性优先
03
大纲映射 传统代码
分块→大纲节点多对多映射，基于关键词匹配 + 向量检索，构建融合任务图
理由：映射关系需可追溯、可审计，传统检索更稳定
04
内容融合 LLM
按大纲节点聚合相关分块，LLM 生成融合段落，支持迭代精炼
理由：跨资料语义整合、去重、改写需要语言理解能力
05
一致性校验 LLM
跨节点摘要继承，检测术语不一致、逻辑断裂，迭代精炼
理由：连贯性判断需语义理解，传统规则无法覆盖
06
排版渲染 传统代码
套用 Word 模板，生成目录、页眉页脚、图表编号、交叉引用
理由：排版规则确定，模板渲染无需语义，保证格式合规
07
格式校验 传统代码
检查字体、字号、行距、编号连续性、引用完整性等格式规范
理由：格式合规性是规则检查，确定性判定

真实系统开发需求摘要

以下为面向开发团队的完整需求概要，详细规格见 DEVELOPMENT_SPEC.md

🏗 系统架构
五层分层架构：接入层（Web/API）→ 编排层（任务调度）→ LLM 层（融合生成）→ 传统代码层（解析/分块/排版）→ 输出层（文档渲染）。各层解耦，可独立扩展。
📦 核心模块
资料解析（多格式）· 语义分块（结构+语义）· 大纲映射（任务图）· 内容融合（LLM 生成）· 排版引擎（模板渲染）· 质量校验（格式+连贯性）
⚙ 技术栈建议
前端 React + 富文本编辑器；后端 Python FastAPI；LLM 接入本地 9B（Qwen2.5-9B / GLM-4-9B）via Ollama/vLLM，云端可选；文档处理 python-docx；向量检索 FAISS/Milvus。
React 18 FastAPI Qwen2.5-9B GLM-4-9B python-docx FAISS Ollama Docker
🚀 部署方案
本地隐私部署：Docker Compose（前端 + FastAPI + 本地 LLM），数据不出域。
云端部署：前端 CDN + 后端 K8s + 云端 LLM API。
混合部署：敏感资料本地处理，非敏感走云端。
📊 长文档流水线
分块策略：结构优先 + 语义边界 + 大小约束（≤4K tokens/块）
映射策略：多对多映射 + 冲突检测
融合策略：单节点生成 + 跨节点一致性校验 + 迭代精炼
上下文管理：滑动窗口 + 摘要继承 + 关键信息缓存
🎯 开发里程碑
MVP：单格式解析 + 基础分块 + LLM 融合 + 简单排版
Beta：多格式支持 + 向量映射 + 模板系统 + 质量校验
正式版：分布式编排 + 多 LLM 调度 + 完整部署方案
