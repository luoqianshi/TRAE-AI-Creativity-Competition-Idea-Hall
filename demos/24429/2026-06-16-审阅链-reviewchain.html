在 TRAE IDE 里，4 个 PM / 架构师 / 执行人 / 审核人 Skill 接力跑完 1 个 feature PR——基于 TRAE 的 SKILL.md 规范 + 自身项目实践 总结出来的 5 个 SKILL.md，原本"AI 自己跑 4 步"变成"4 个 Skill 接力跑"，每步只读自己的切片，审核 Skill 有权拒收让执行 Skill 回炉。

🩹 当前的 4 个痛点

为什么"让 AI 写 PR"这么难？

💥

上下文溢出

多轮对话中，PM 的需求澄清、执行人的代码细节、审核人的质疑混在一个上下文里，互相干扰，AI 开始自相矛盾。

🤥

自审失灵

同一个 Agent 又写代码又审自己代码，必然宽松——"自审"本质上没有拒收权，质量不可控。

🕳️

审计不可见

出 bug 不知道是 PM 拆错了还是执行人写歪了，没有 token 消耗、运行耗时、质疑点等可追溯日志。

🔌

上下文断层

现有"多 Agent"工具多是独立 Web App，与 TRAE IDE 上下文断层，需要反复复制粘贴。

💡 4 条核心创新

审阅链的差异化点

01

Skill 体系接力化

5 个 Skill 全部基于 TRAE 的 SKILL.md 规范（TRAE 支持用户自定义 Skill）+ 自身项目实践 总结得出。不造新概念，评委对 SKILL.md 形式秒懂，零学习成本。

02

上下文物理隔离

每个 Skill 加载时物理上只读自己的 context 切片，不读上上轮对话。从"AI 自己连跑 4 步"变成"4 个独立 Skill 各看各的"，杜绝角色间串台。

03

审核 Skill 拒收权

审核 Skill 的 6 维审查清单（前 5 维参考工程实践的 5 维审查思路，第 6 维"对齐设计"是审阅链独有），升级为签字权——不通过则整单打回执行 Skill，强制重做；最多 3 轮，超过则升级用户裁决。

04

完整审计 + 状态机

每角色写入 audit/：输入摘要、token 消耗、运行时长、质疑点，state.json 记录状态机（PENDING_PM / REVIEWING / REJECTED / APPROVED / ESCALATED）。

⚙️ 执行人角色 · reviewchain-executor

输入上下文（仅读）：02_design.md + 相关源码全文 + 上轮拒收意见（如有）

🧐 审核人角色 · reviewchain-reviewer

输入上下文（仅读）：code_diff.patch + 02_design.md + 测试结果 + 相关源码

核心任务：

  • 代码审查：是否对齐设计？SQL 注入？边界条件？
  • 输出 03_review.md：status: PASS/REJECT + 质疑点
  • 拒收时必须列出具体意见（模糊拒收会被调度器拒绝）

6 维审查清单：前 5 维（架构/耦合/细节/质量/可观测）来自工程实践通用标准 + 第 6 维"对齐设计"（审阅链独有）

权威性：不是评分，是签字 —— 不通过则整单打回执行人

↩️ 拒收状态机： REVIEWING → 拒收 → REJECTED（回流，第 N/3 轮） → 执行人改完 → REVIEWING → 通过 → APPROVED
拒收 ≥ 3 轮 → 状态置为 ESCALATED，打包所有 audit/ 日志升级用户裁决 ↩️

📋 reviewchain-pm Skill

2
🏛️ reviewchain-architect Skill

3
⚙️ reviewchain-executor Skill
读取 context/executor_input.md，按 02_design.md 实际编码 + 3 个 pytest 用例，输出 artifacts/code_diff.patch
4
🧐 reviewchain-reviewer Skill（6 维审查）
读取 context/reviewer_input.md（diff + 设计 + 测试结果），pytest 全绿但发现 SQL 拼接未参数化 → 写入 artifacts/03_review.md：status: REJECT，意见回流
5
⚙️ reviewchain-executor Skill（回炉，第 1/3 轮）
拒收意见以最高优先级注入新的 executor_input.md，改用参数化查询重写，重新输出 code_diff.patch
6
🧐 reviewchain-reviewer Skill（第 2 轮审查）
6 维全通过 → 03_review.md：status: PASS，调度 Skill 输出 PR 描述给用户，写入 audit/ 全程日志

⚔️ 在 TRAE 里，现在怎么做 vs 审阅链怎么做

同样的 IDE、同样的对话窗口——用户手动切角色 vs 5 个 Skill 自动接力

现在：TRAE 多轮对话 + 手动 prompt 切角色
你正在用的方式
→ 角色切换 第 1 轮手动写"你现在是 PM"，第 2 轮"你是架构师"，第 3 轮"写代码"，第 4 轮"审一下"——靠用户自己记
→ 质量把关 同一个 Agent 写完代码，紧接着"请审查上面这段"——自己审自己，模型会委婉放过
→ 拒收能力 用户自己看 diff、自己说"这里有问题"——所有质疑压力落在人身上
→ 上下文 PM 闲聊、架构讨论、代码、审查全混在一个滚动上下文里，10 轮后开始自相矛盾
→ 追溯性 出 bug 不知道是需求拆错了还是代码写歪了，没有审计
审阅链：5 个 Skill 自动接力 + 拒收权
用户只输入需求，剩下的交给 Skill 流水线
✓ 角色切换 reviewchain-orchestrator 自动按 PM → 架构 → 执行 → 审核顺序接力，用户不用记顺序
✓ 质量把关 审核 Skill 独立，看到的是别人写的代码 + 6 维清单（前 5 维工程通用 + 第 6 维"对齐设计"独有）
✓ 拒收能力 审核 Skill 有签字权，不通过则强制打回执行 Skill 改，最多 3 轮，超过则升级用户
✓ 上下文 每个 Skill 只读自己的 context/*.md 切片，物理上不串台
✓ 追溯性 audit/ 记录每角色输入摘要 / 输出 / token / 质疑点 + state.json 状态机
