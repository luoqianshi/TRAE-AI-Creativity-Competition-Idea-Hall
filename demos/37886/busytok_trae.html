Problems

AI Agent 越能干，Token 成本越需要被管理

当开发者开始把真实任务交给 AI Agent，成本问题不再只是“模型单价”，而是每个任务、每个子任务、每个模型选择共同叠加出来的结果。

◎

Token 消耗不透明

一次 AI Agent 任务会消耗多少输入、输出和上下文 Token，用户通常缺少清晰视角。

↯

任务成本难归因

需求分析、代码阅读、方案生成、代码修改、测试修复混在一起，很难判断哪一步最烧钱。

◇

子代理成本不可控

复杂任务如果拆给多个子代理，但全部使用强模型，整体成本会快速升高。

⚖

模型选择缺少依据

强模型效果好但贵，低成本模型便宜但能力不同，用户很难判断每类任务应该用哪个模型。

⌁

缺少持续优化反馈

历史任务里的 Token 浪费、上下文过长、模型过度使用等问题，往往没有被沉淀成优化建议。

¥

预算难以提前控制

开发者通常在账单出现后才发现成本过高，缺少任务执行过程中的成本分析和模型分配策略。

Solution

Busytok 的核心思路：审计 Token，并把模型选择下沉到子任务

Busytok 不追求把所有任务都交给最强模型，而是围绕一个更细的粒度做优化：通过开子代理拆分任务，再根据每个子代理负责的具体工作选择合适模型。

采集用量

记录每次 AI Agent 任务的输入 Token、输出 Token、总 Token 与预估费用。

分析任务

把复杂任务拆成需求分析、代码阅读、方案生成、代码修改、测试修复等阶段。

开子代理

为不同子任务启动对应子代理，让每个子代理只负责更明确、更小的任务范围。

模型路由

根据子代理任务复杂度、上下文长度和预算，选择强模型、中等模型或低成本模型。

持续优化

根据历史 Token 成本和任务效果，沉淀更合理的子代理模型分配策略。

Task-level Routing

通过开子代理，实现任务级别的模型路由

对于一个代码重构任务，Busytok 的理念不是“一个模型做到底”，而是将任务拆给多个子代理，并让每个子代理使用最适合它的模型。

复杂任务拆分 Main Agent → Sub Agents
1
主 Agent 接收目标 例如：重构一个模块，减少重复代码，并修复相关测试。
2
拆分为多个子任务 需求理解、代码阅读、方案设计、代码修改、测试修复分别处理。
3
为子任务开启子代理 不同子代理拥有更清晰的任务边界，减少无效上下文和重复消耗。
4
按任务类型选择模型 简单任务用低成本模型，关键推理和核心修改保留强模型。
