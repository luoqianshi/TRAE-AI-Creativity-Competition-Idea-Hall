飞书多维表格 AI 数据同步助手

面向飞书多维表格的超大数据量增量同步引擎：多数据源接入、千万级差异比对、强隔离与频控容错、支持图片附件、带会员能力控制。

一句话判断：这不是一个“把 Excel 贴进表格”的轻量导入器，而是一套面向飞书多维表格的数据同步执行系统。它保留旧版插件的交互优势，把最重的对比、写入、附件、权限与稳定性能力全面迁移到后端作业链路。

准确性优先：在工程取舍上，先保证 diff 结果正确、可复核、可恢复，再追求吞吐与并发。面对千万级数据量，系统不依赖“整表进内存”的做法，而是通过 stream / page / bucket / checkpoint / 外部存储 组合，把内存消耗控制在可配置上限内，避免随数据规模线性暴涨。

重构方向：原版纯前端实现在 client 目录，已验证真实需求。新版以 Server(API + Job) 为核心，形成 JobService → JobExecutor → CompareExecutionService → AttachmentPipeline → FeishuWriteExecutor 的稳定执行链路，为 AI 能力、会员体系和商业化扩展提供承载面。

项目背景与验证

已验证的真实需求

项目起点是我开发的飞书多维表格侧边栏插件，用于把 Excel 数据与多维表格数据做对比导入。旧版方案在 client 目录中以纯前端方式实现，优点是交互直观、上手快，但随着数据量上升、附件复杂度增加、任务时长变长，浏览器端模型开始暴露稳定性和资源边界。

旧版已经拿到了明确的需求背书：插件文档累计阅读量近 2w、过万人访问。这说明场景成立，用户不只需要“导入”，而是需要“对齐现有表、做差异、能解释、能恢复、可控权限”的同步能力。

重构升级的产品判断

新版不是推翻重做，而是把旧版已经验证过的交互价值留在前台，把最重、最难、最需要稳定性的链路迁到后端 server。核心升级目标有三条：第一，保留旧版所有功能；第二，把对比与导入升级为作业化执行；第三，为 AI 推荐、会员能力和商业化扩展建立可靠底座。

产品定位从“前端导入工具”升级为“数据同步引擎”。前端负责配置与解释，后端负责执行与保障。

架构总览

系统采用“前端做薄、核心下沉”的结构。侧边栏插件负责采集用户意图、展示 AI 推荐与解释，后端负责标准化接入、差异规划、附件处理、稳定写回、鉴权与审计。会员与策略数据不依赖 MySQL，而是用固定的飞书多维表格作为配置与会员数据库，降低维护成本并保持业务可运营。

升级路线

  • 阶段一：保留旧版 UI 体验与导入流程，先把建单、执行、结果回传迁到后端。
  • 阶段二：引入 CompareExecutionService，把差异比对从“页面内逻辑”升级为“可 checkpoint 的执行引擎”。
  • 阶段三：引入 AttachmentPipeline 与 FeishuWriteExecutor，把附件闭环、串行锁、429 退避和降批重试做成平台能力。
  • 阶段四：在 UI 层增加 AI 推荐与解释，在会员策略层加入权限与性能档位控制。

系统边界

前端职责
采集配置、展示 AI 推荐、展示风险与解释、发起作业、查看结果。
后端职责
鉴权、执行、分页拉取、差异规划、附件 staging、稳定写回、审计与清理。
数据边界
按 tenant + base_id + user_id 绝对隔离文件缓存、checkpoint、临时附件和作业记录。
能力边界
会员策略控制限额、并发、附件导入、性能档位和优先队列，不侵入核心执行代码。

作业执行链路

后端执行链路的核心思想是把“一个同步任务”拆成可观测、可恢复、可重试的多个阶段。作业一旦建单，后续执行就不再依赖浏览器页面是否存活；结果、错误、附件状态、checkpoint 都被纳入持久化控制。

核心能力矩阵

本项目的创造力不在于堆叠概念，而在于把看似分散的“导入、对比、附件、AI、会员、稳定性、安全”做成一套可协同的工程系统。下表按能力域、落地方式、产出与价值进行展开。

准确性优先与千万级差异比对方案

这部分是整个项目最硬核的工程中心。面对千万级数据量，系统不追求“先快再说”，而是坚持先做对，再做稳，最后再做快。核心原则是：不全量载入、不把状态全部堆进内存、不让恢复粒度过粗、不让并发破坏一致性。

1. 输入与目标输出

source_rows(stream) + target_rows(stream) → diff_plan(add / update / delete)

输入端与目标端都被抽象为行流，系统最终产出的不是“直接写入”，而是一个可审查、可 checkpoint、可重放的 diff_plan。这让“比对”和“提交”变成两个阶段，可以独立校验、重试和限速。

2. 分桶 / 分片

以 index_key hash 进行分桶，把全局比较拆成多个局部问题。桶内仍按顺序配对和行哈希判定变更，同一索引 key 多行场景有独立策略，不把含糊匹配混进主流程。

分桶的价值在于降低单次比较规模，也让 checkpoint 可以落在桶级别，而不是整任务级别。

3. 流式处理

source 与 target 都不做全量内存加载。Excel / JSON / TXT 解析后直接产出 RowStream，目标表按页读取；每一页只保留当前阶段真正需要的结构化索引、桶统计或最小比较状态。

内存曲线因此与“当前在处理的桶 / 页 / batch”有关，而不是与总数据量简单线性绑定。

4. 外部存储中间态

桶索引、行哈希、比对游标和 checkpoint 不强依赖进程内存，可下沉到磁盘、DuckDB 或 KV。这样在千万级数据场景下，内存承担的是“执行窗口”，外部存储承担的是“全局记忆”。

这一步是避免 O(N) 内存增长的关键，也是任务可恢复的基础。

5. 分页读取目标表

目标多维表格通过 page_token 分页拉取，边拉边标准化、边构建必要索引或桶摘要，避免为了一次对比先把整表读完。分页策略与 checkpoint 配合后，异常恢复可以回到页级或桶级，而不是整表重扫。

6. 多线程与分层并发

CPU 密集部分，如 normalize、hash、schema 对齐，可走独立 worker；IO 密集部分，如分页拉取、文件下载、附件上传，则由另一层并发池控制。这样可以避免把下载阻塞混进哈希计算，也避免把写入限流影响解析。

一致性与校验策略

  • 同一 index_key 出现多行时，不做模糊猜测，采用桶内顺序配对 + 行哈希判断，必要时输出风险提示而不是武断更新。
  • 支持抽样校验：对每个桶随机抽样，复核源记录数、目标记录数、计划结果数与哈希一致性。
  • 支持汇总一致性检查：总输入、总输出、总删除、总附件成功/失败计数必须可回放、可对账。

目标指标表达

  • 内存上限固定且可配置，由运行容器预算决定，不因总数据量简单线性扩张。
  • 吞吐量在桶数与并发度增加时可近似线性提升，但最终受飞书 API 与附件链路限流约束。
  • 恢复粒度细化到 page / bucket / batch / attachment stage，降低失败后的重跑成本。
  • 系统把“快”建立在“可恢复、可观测、可证明正确”的前提上，而不是以内存换速度。

附件与图片的完整工程链路

Excel 内嵌图片

系统从 xlsx 结构中解析内嵌图片与锚点关系，得到 anchor → fileValue，其中可携带 parent_token / name 等必要信息。这样图片不会停留在“单元格里看见了”，而是能进入后端统一的附件写回链路。

URL 附件

公开 URL 与带请求头 URL 共用一套 staging 流程。对于私有资源，允许声明 method / headers / body，但敏感信息只在运行期解密使用，不进入明文日志。

staging 与回写

所有附件统一进入待上传项队列：download → temp file → upload_all → file_token。最终写回多维表格附件字段的值结构是 [{file_token: ...}]，与主写入计划合流。

失败不拖垮主写入

附件失败会被记录为 attachment_failed 和 errors 摘要，但主数据写入不应因个别附件问题整体阻塞。系统将“主数据正确入表”与“附件补齐”在状态上拆开，避免资源型错误拖垮结构化写入。

AI 智能能力：工程化落点，而不是口号

本项目中的 AI 不承担“替代执行引擎”的职责，而是插入在更适合机器推断与解释的位置：UI 配置辅助、配置生成、风险说明、结果解释。真正的导入与写回仍由后端作业系统执行，这保证 AI 出错时系统不会失控，AI 变强时又能持续提升体验。

智能分析

在用户上传数据或选择目标表后，AI 先分析表头、字段类型、主键候选与异常列分布。它不是直接替用户提交作业，而是产出一份建议配置草案，供用户确认。

与后端作业系统协同

AI 只生成建议，不绕过后端执行规则。协同链路是：AI 生成建议 → UI 形成 config → JobService 建单 → JobExecutor 执行 → CompareExecutionService / AttachmentPipeline / FeishuWriteExecutor 落地 → AI 读取结果做解释。这样 AI 既能提升配置效率，又不会直接侵入执行安全边界。

商业化与会员体系

项目的商业化不是在导入器外层生硬套付费墙，而是把会员能力收进系统治理层。会员码鉴权只是入口，真正重要的是能力控制必须通过规则表驱动，而不是把套餐判断写死在业务代码里。

为什么不用 MySQL

会员、配置与策略数据使用固定飞书多维表格作为“轻量业务数据库”。这样既贴合当前生态，也降低了中小团队的维护成本。对这类规则型数据来说，低维护与可运营性比引入额外数据库更重要。

付费能力示例

  • 多任务并行：普通用户串行，会员用户可并行执行多个 job。
  • 更高同步限额：控制单次导入记录规模与日配额。
  • 附件导入：作为高价值能力独立开关。
  • 性能档位：更高桶并发、更多 worker、更高读取窗口。
  • 优先队列：在共享资源下优先调度高阶会员任务。
会员体系的工程价值不只是“能收费”，而是提供一套可维护、可扩展、可运营的能力分层模型。未来新增套餐、灰度能力、试用策略，只需改规则，不需要反复侵入核心引擎。

数据隔离与安全

身份与凭证

会话 token 用于识别用户身份；运行时凭证按 job 恢复；敏感配置，尤其是 requestConfig 里的敏感 header/body，采用可逆加密存储，只在执行窗口解密使用。

数据安全

作业记录、缓存、checkpoint、附件 staging 均按 tenant + base_id + user_id 隔离；接口层做权限校验；日志只保留必要诊断信息并脱敏；临时文件在任务完成或过期后清理。

接口与下载安全

所有接口都带鉴权、限速与输入校验。URL 下载仅允许 http/https，并可配置域名黑名单或白名单，避免把附件功能变成 SSRF 通道。

日志脱敏 Authorization / Cookie / Token 等不明文记录 排错需要信息，但不能以泄露凭证为代价。
租户隔离 隔离 key 贯穿存储、锁、任务与缓存 从根上避免跨租户、跨 base、跨用户串扰。
接口治理 鉴权、限速、参数校验、审计 把风险前置到入口，不等执行链路深处才发现异常输入。
SSRF 约束 URL 仅允许 http/https，支持黑白名单 附件能力必须可用，但必须明确下载边界。
