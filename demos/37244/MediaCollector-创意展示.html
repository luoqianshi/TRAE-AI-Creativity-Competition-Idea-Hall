THE PROBLEM

媒体收藏者的三重困境

本地媒体文件格式杂乱、元数据缺失、播放受限——这是每一个资源收藏者都在反复面对的痛点。

🗂️

格式混乱，整理靠手动

电影/电视剧/漫画/音乐散落在多个磁盘，命名五花八门，MKV/AVI/MP4/PDF/ZIP 混杂。手动改名、归类、匹配元数据耗时耗力，且容易出错。

🎬

浏览器播放，格式受限

本地 NAS 上的 MKV/AVI 视频无法直接在浏览器播放，必须下载或安装专用播放器。跨设备、跨场景的流式播放几乎不可能，移动端体验极差。

📥

资源获取，工具割裂

下载用 Aria/迅雷，刮削用 tinyMediaManager，播放用 Plex/Jellyfin——工具链割裂，数据无法打通，下载到入库到播放要反复搬运。

TECHNICAL BREAKTHROUGH

用 TRAE 完成的关键功能突破

在已有项目基础上，借助 TRAE Work / TRAE IDE 实现了「服务端 DASH 流媒体解码」与「BitTorrent 客户端」两大技术难点。

📡

服务端 DASH 流媒体解码（dash-handler）

让任意格式视频在浏览器流畅播放 · JavaCV + FFmpeg
  • fMP4 分片实时切分：使用 FFmpegFrameGrabber 按时间区间抓取帧，FFmpegFrameRecorder 重编码为 fMP4，生成 init segment + media segment
  • 音视频独立 track：视频与音频各自生成只含自己 track 的 init segment，避免多流冲突
  • MP4 Box 二级解析：手写 ftyp/moov/moof/mdat/tfdt 解析与改写，修正时间轴使分片连续
  • 硬件加速探测：自动检测 h264_qsv / h264_nvenc / h264_amf / h264_videotoolbox，无则回退 libx264
  • MPD 清单生成：动态生成 DASH MPD，描述 SegmentTimeline、timescale、Representation
  • CFR 时间戳对齐：按固定帧率写入 PTS，解决 AVI 等容器可变帧率导致的画面错乱

🔌

自研 BitTorrent 客户端（torrent4j）

Java + Netty 从零实现 · DHT/Peer/元数据交换全协议
  • DHT 网络完整实现：遵循 BEP-5，支持 ping/find_node/get_peers/announce_peer，IPv4/IPv6 双栈
  • 标准 Peer 协议：握手、Bitfield 交换、request/piece/cancel，Choke/Unchoke 流量控制
  • 扩展协议：元数据交换（BEP-9 磁力链接）、快速扩展（BEP-6）、UT-PEX 节点交换
  • Netty 高性能 IO：NIO 驱动 UDP/TCP，IO 线程与业务线程分离，ByteBuf 零拷贝
  • 异步任务与缓存：Guava Cache LRU 分片缓存，SHA-1 校验完整性
