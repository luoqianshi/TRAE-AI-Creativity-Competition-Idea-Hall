AI 研发治理 · 一篇视觉化的论述

写得越多，烂得越快。
难的不是想招，是把约束做成
一道连 AI 自己都绕不过去的闸。

提示词是祈祷，文档会被跳过，只有机制不会。这是把"AI 听不听话"从玄学，变成工程的故事。

SCROLL
01 · 核心冲突

把希望寄托在"这次模型能听话"，
这是祈祷，不是工程。

提示词 · The Prayer

把不写烂代码当成提示词问题

本质是把希望寄托在"这次模型能听话"上。优化 prompt、换个模型、加几条告诫——赌的都是它这一次愿意守规矩。可人的记性和纪律，是整条链路里最不可靠的一环。

"再优化优化提示词"——我认为这是错的方向。
治理 · The Engineering

承认失败是系统性、可枚举的

把它们列出来，针对每一类设计约束。把"AI 听不听话"从玄学问题，变成工程问题。靠每个人每次都写对、靠 review 每次都抓得住，在规模上不成立。

治理不是因为 agent 笨，是因为"信任 + 人审"在规模上不成立。
02 · 失败枚举

这些失败不是随机 bug，
它们反复出现、有规律、可以被列出来。

F01

模仿历史债务

AI 无比忠实地复制它周围最烂的那种写法。旧代码不是范本，是历史债务。

F02

删测试凑绿

把那条一直失败的断言删了，于是测试"全绿"了。为了过而过。

F03

过度抽象与过早设计

一边写业务，一边忍不住套设计模式、自作主张重构。分不清"跑通"与"写对"。

F04

臆测看不见的界面

没给设计图，就照文字描述凭空臆测出一个根本不存在的界面。

F05

重复造轮子

已经存在的工具/符号/函数不去复用，重新造一个。

F06

只消报错不查根因

把当前的报错消掉就交差，不查根因，留下一个更隐蔽的坑。

03 · 四层门禁

凡配了的规则必须真能阻断，
不是给一份可以无视的报告。

这是检查责任的分类框架，不是要求每层都堆规则。某一层可以不放项目特定规则，但凡是配了的规则就必须真能阻断；整条流程至少要有一道确定性阻断门禁 + 最终人审。全绿才能交付。

01
机械门禁 · Mechanical

能正则 / AST 机械判定的

结构边界、禁用写法、写权限范围。写入前的 hook 当场触发、当场拦住——不管模型愿不愿意。这是那道"绕不过去的闸"的物理来源。

越界写入■ BLOCKED
02
确定性门禁 · Deterministic

能真跑、能拦的检查

测试、构建，或项目特有的校验。不是给报告，是真跑；跑不过就停。AI 唯一不能做的，就是给自己开绿灯。

构建/测试■ BLOCKED
03
语义评审 · Semantic

独立于作者的评审者

判复用、过度设计、图文一致、根因。评审者 ≠ 作者——机制上强制，不靠自觉。学生不能自己批自己的卷子。

臆测 / 造轮子■ BLOCKED
04
人审 · Human

最终那一道闸

机器判不了的，交给人。但人审不是兜底所有——前面三层把可机械化的全卡死，人只判真正需要人判的。

交付批准■ REQUIRED
04 · 从 PRD 到交付

整条线上，AI 每一步都被
"输入约束 + 证据 + 独立判定"夹着走。

00
节点 00 · 入口

PRD 契约化

起点不是一段模糊描述，而是一份可验证的验收契约。"展示要友好"这类不可测描述会被卡住要澄清。第③条"只能一个默认"被固化成后面要反复对照的契约项。

防住：含糊 / TBD 直接进开发
01
节点 01 · 派生

/kaleido prd → 动态派生执行单元

按这份 PRD 当场派生一次性、不可变的受控执行单元，把"这一单"的写权限范围、上下文烤进去，用 digest 绑定当前 PRD。需求一改，摘要就变，下游立刻知道"源变了"。

防住：越界乱改、偏离需求、翻历史产物
02
节点 02 · 启动

受控 run · 未批准不准写源码

在隔离工作区开一次受控执行，进入"先规划、未批准不准写源码"。拿到需求闷头就写——这条路堵死。

防住：闷头就写
03
节点 03 · 拆分

业务纵向拆分

竖切成叶子，先定数据结构与映射。这个例子：列表 / 表单 / 设默认 / 删除 四叶，先定 Address 结构。不是横向按技术层摊开。

防住：横向摊开、预建"通用表单引擎"
04
节点 04 · 叶子循环

定契约 → 实现 → 留证据 → 验证

每叶小步交付、每步留证据。做"设为默认"叶时，"只能一个默认、设新取消旧"被落成具体行为约定并留证据。后面的门禁要的就是这些证据。

防住：实现与验收脱节、关键规则被漏
05
节点 05 · 重构（独立阶段）

跑通之后，才单独重构

四叶都跑通后才作为单独一步重构：此时发现"新增/编辑表单"确实重复两次 → 按真实重复抽共享表单。绝不在写第一个表单时就预抽。

防住：过早抽象、边写边重构搞乱验证
06
节点 06 · 四层门禁

机械 → 确定性 → 语义 → 人审

独立评审者逐条对验收：只能一个默认？删默认不顺延？接口失败有反馈？有没有造轮子？AI 自作主张"删默认后自动顺延"，正好违反验收④，被独立评审当场逮到。

防住：删测试凑绿、自审、吞异常、臆测
07
节点 07 · 修复回路

在批准范围内修、重跑，轮数有上限

哪层没过就在批准范围内修、重跑，轮数有上限；预算耗尽仍不过就停下、交回给人，绝不"为了过而过"。全绿后交付，留下"需求→代码→验证"的追溯链。

防住：带病交付、为了过而过
08
节点 08 · 用完即弃

脚手架拆除 · 结论毕业

kaleido- 是脚手架，交付后清理；可复用结论毕业回规范层。执行单元本身删除——无垃圾、无可漂之物。要再用？重新派生就是了，可复现。

防住：仓库堆积过期治理快照、下次翻旧账
05 · 配置的悖论

可配置性 ⊥ 可强制性。
你的功力，不体现在"能配多少"，
体现在"你敢锁死什么"。

⚿锁死 · LOCKED

元规则与门禁框架

每一步要不要留证据、验收能不能是不可测的、能不能自己给自己开绿灯、契约的定义、评审者 ≠ 作者——这些永不可按项目让步。一个什么都肯让步的系统，不是灵活，是没有立场。

⚙可调 · TUNABLE

每层具体装什么

机械层放什么结构约束、确定性层放构建还是别的校验、某一层要不要不放项目特定规则、栈约定、启用哪些规则——这些是项目自己的事。锁死的不是"每层都堆满规则"，而是这个框架本身。
