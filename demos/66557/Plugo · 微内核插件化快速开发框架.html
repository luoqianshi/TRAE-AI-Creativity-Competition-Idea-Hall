// 02 — PROBLEM vs SOLUTION

为什么需要重新定义后台框架？

传统单体框架把所有功能焊死在源码里；Plugo 让每一个功能都成为可独立装卸的插件。

⚠ 传统框架的痛点

// MONOLITHIC · HIGH COUPLING
  • ✕功能耦合严重，用户/权限/菜单/日志纠缠在同一份代码里，难以单独维护。
  • ✕增减功能必须侵入式改源码，git 里满是冲突与魔改。
  • ✕框架升级牵一发动全身，一个版本号变动可能破坏全部二开。
  • ✕二次开发 = 拷贝 → 改 → 失去同步，重复造轮子。

◆ 我们的方案

// MICROKERNEL · PLUGGABLE
  • ✓内核零业务逻辑，只保留 PluginLoader / Lifecycle / EventBus 等最小运行时。
  • ✓装卸插件即增减功能，声明式清单描述一切，无需碰内核。
  • ✓插件独立升级、独立版本，互不干扰，异常自动隔离。
  • ✓写插件 = 新增一个目录，内核与官方插件保持纯净。

// 02.5 — COMPETITIVE ANALYSIS

传统单体框架 vs Plugo

同样是后台快速开发框架，架构理念截然不同。不是做一个"功能更多"的传统框架，而是做一个"能自由拼装功能"的底座。

对比维度 传统单体框架Java PlugoPython
架构理念 单体框架，功能硬编码在源码中 微内核 + 插件化，一切能力皆插件
功能耦合度 模块间直接 import，删一个报错一片 插件间只走扩展点 / 事件总线，零直接依赖
增减功能 改源码 → 重新发版 → 全量部署 装卸插件，运行时生效，内核零改动
二次开发 clone → 删模块 → 魔改 → 失去上游同步 写独立插件目录，官方插件保持纯净
框架升级 merge 冲突频繁，二开代码易被覆盖 插件独立版本号，互不影响，平滑升级
后端技术栈 Java / Spring Boot / MyBatis Python 3.12 / FastAPI / SQLAlchemy 2.0 async
前端技术栈 Vue2 / Vue3（分版本） Vue 3 + TypeScript + Vite + Pinia
扩展生态 社区模块零散，无统一标准 manifest 声明式标准，未来插件市场
// 02.6 — MARKET POSITIONING

市场定位

微内核+插件化做后台框架这条路已被验证可行，但 Python 生态仍是空白。Plugo 要做的不是重复，而是填补。

已验证

Java 生态已有同类产品

2025 年出现的 Forge Admin 明确提出"微内核全插件化"，基于 Spring Boot 3 的 Starter/Plugin 分层，证明这条路在后台框架领域可行。

  • 架构理念：微内核 + Starter/Plugin 分层
  • 扩展方式：引入依赖即生效（自动配置）
  • 已集成 AI 能力：代码生成、数据大屏
参考：Forge Admin（Spring Boot 3 + Vue 3，2025）
空白机会

Python 生态尚无同类

FastAPI + Vue3 的后台框架很多（vue-fastapi-admin 等），但全部是单体脚手架。没有一个采用微内核+插件化架构，用户/权限/菜单仍然硬编码在源码里。

  • 现有方案：clone → 删模块 → 魔改
  • 无声明式清单，无扩展点注册
  • 无插件生命周期管理
  • 无运行时热装卸能力
结论：Plugo 是 Python 生态首个微内核插件化后台框架
差异化

Plugo 的实现哲学不同

Forge Admin 走 Spring Boot 自动配置路线；Plugo 借鉴 VSCode，用声明式清单 + 扩展点注册表 + 事件总线，更纯粹、更跨语言可移植。

  • manifest 声明式（像 VSCode）而非注解自动配置
  • 6 种扩展点显式注册，跨插件合并查询
  • 事件总线松耦合通信，异常自动隔离
  • 6 状态生命周期状态机，可观测可管控
定位：不做"功能更多"的框架，做"能自由拼装"的底座

// 04 — CORE MECHANISM

四大核心机制

从声明式清单到动态路由，每一个机制都为「热插拔」服务。

☰

声明式清单

一份 plugin.yaml 描述插件全部能力，内核据此自动注册路由、菜单、按钮与接口。

# plugin.yaml — 一份清单描述全部能力 id: sys-user name: 用户管理 entry: app.plugins.sys_user.plugin:SysUserPlugin dependencies: ["sys-core"] contributes: apis: [{ prefix: /api/system/user }] menus: [{ path: /system/user }] buttons: [{ code: system:user:add }]
⊞

扩展点机制

内核预置 6 种扩展点，插件通过 contributes 声明贡献，由 ExtensionRegistry 统一登记、跨插件合并查询。

menus routes buttons apis config_schema kernel-services
⇆

事件总线 EventBus

插件间通过发布 / 订阅松耦合通信。每个处理器独立异常隔离——单个插件出错不会影响发布方与其他订阅者，并自动广播 kernel.plugin_error。

# 插件订阅事件 await ctx.bus.on( "user.created", handler ) # 异常自动隔离，不影响其他订阅者
⟳

动态路由

采用子应用 mount 模型：插件启动时挂载独立 FastAPI 子应用到前缀，停用时从 app.routes 移除——运行时热挂载 / 热卸载，无需重启。

# 子应用挂载（start） sub_app = FastAPI() sub_app.include_router(router) app.mount(/api/system/user, sub_app) # 卸载（stop）— 路由即时 404 app.routes[:] = [r for r in app.routes if ...]

// 04.5 — QUICK START

5 分钟写一个插件

从创建插件到接口可用，只需三步。无需碰内核源码，无需重新发版，重启后端即自动发现。

1 CLI 脚手架创建

一行命令生成插件骨架

自动创建 plugin.yaml + plugin.py + api.py，重启后端自动发现并注册。

# 创建插件 python cli.py new my-feature "我的功能" # 自动生成目录结构 # plugins/my_feature/ # ├── plugin.yaml 声明式清单 # ├── plugin.py 插件入口类 # └── api.py API 路由
2 声明能力

编辑 plugin.yaml 描述能力

声明插件贡献的 API 路由、菜单节点、按钮权限，内核据此自动注册。

# plugin.yaml id: my-feature name: 我的功能 version: 1.0.0 entry: app.plugins.my_feature.plugin:MyPlugin contributes: apis: - module: app.plugins.my_feature.api prefix: /api/my-feature menus: - { path: /my-feature, title: 我的功能 }
3 重启即生效

重启后端，插件自动加载

PluginLoader 扫描目录 → 拓扑排序 → 注册扩展点 → 挂载路由。无需修改内核任何一行代码。

# 重启后端 uvicorn app.main:app --host 0.0.0.0 --port 8000 # 日志输出： # [kernel] discovered plugin: my-feature # [kernel] resolved dependencies: none # [kernel] mounted routes: /api/my-feature/* # [kernel] plugin my-feature → started ✓ # 访问接口 # curl http://localhost:8000/api/my-feature/ → 200 OK
4 效率对比

从零到可用后台系统

启用 4 个官方插件（sys-core / sys-user / sys-role / sys-menu），从零到可用后台系统耗时不到 1 分钟。

# 传统框架做法 # 1. clone 传统框架 → 2. 删不需要的模块 # 3. 改配置 → 4. 排查报错 → 5. 重新部署 # 耗时：30min ~ 2h # Plugo 做法 python cli.py enable sys-core python cli.py enable sys-user python cli.py enable sys-role python cli.py enable sys-menu # 耗时：< 60s ✓
