01 / 问题

传统系统设计教学的困境

学生学完「分布式系统」课程，能背诵 CAP 定理和熔断器模式，但面对真实流量洪峰时，依然会犯最基础的错误。

📋 传统教学

  • 概念灌输：背诵熔断器定义，但不知道何时该用
  • 延迟反馈：作业提交后数天才得到批改
  • 脱离上下文：学重试策略却不见重试风暴
  • 无法试错：改一个参数要等整个系统部署
  • 反馈笼统：「你的设计有问题」——哪里有问题？

🎓 ReckonBox

  • 建构主义：学生自己设计，失败自己涌现
  • 即时反馈：100 ticks 模拟 < 2 秒
  • 真实涌现：重试风暴、级联崩溃、队列溢出真实发生
  • 无限试错：拖动滑块即可改变参数，秒级重跑
  • 精准引导：AI 导师在决策树上指出推理链断裂点

03 / 架构

五大模块，YAML 驱动

领域包以 YAML 定义组件类型和参数空间，引擎根据 YAML phases/inject 驱动模拟。新增领域只需添加一个 YAML 文件，无需改代码。

Module 1

Domain Pack

YAML 定义组件类型、参数空间、依赖规则、场景、失败分类、知识概念。

  • 4 种组件类型 (gateway/service/db/cache)
  • 4 个场景 (normal/flash_sale/db_slow/partial_failure)
  • schema 校验含字段名+行号
Module 2

Design Builder

Streamlit 侧边栏，根据 DomainPack 自动生成参数控件。

  • int → slider (范围取自 YAML)
  • bool → checkbox
  • 循环依赖实时检测+回滚
  • JSON 导入导出
Module 3

Simulation Engine

事件驱动模拟器，100 ticks × 6 组件 < 2 秒。

  • 队列/重试/熔断/内存模型
  • 确定性：相同输入→相同输出
  • 零网络依赖，断网可用
  • YAML phases 驱动流量曲线
Module 4

Failure Analyzer

独立模块，检测 6 种失败模式，分析耗时 < 100ms。

  • retry_storm / spof_cascade
  • queue_overflow / memory_exhaustion
  • missing_circuit_breaker / rate_limiter
  • 每个模式附带数字证据
Module 5

AI Tutor

决策树分析器 + 模板/LLM 双模式反馈生成。

  • 8 概念覆盖率计算
  • 推理链断裂识别
  • 矛盾检测 (如 uniform_retry)
  • 环境变量切换 LLM 调用
Utils

Design Spec

连接 UI 和引擎的数据结构层。

  • ComponentConfig dataclass
  • JSON 序列化/反序列化
  • DFS 循环依赖检测
  • 引擎兼容转换

05 / 反馈

AI 导师：在你的决策树上提问

不是「你的设计有问题」，而是「你配置了 retry_count=3 但没有熔断器——在模拟中，这导致了 600 次重试放大。你预期重试能解决什么问题？」

📊 知识覆盖率：62%

你的设计展示了 冗余（多数组件 2 副本）和 重试语义（retry_count 配置）的初步理解，但在 故障隔离、背压、资源 sizing 三个概念上存在明显缺失。

🔗 推理链断裂：retry_without_isolation

你为 order_service 配置了 retry_count=3，说明你认为重试能提升可用性。但你没有同时配置 circuit_breaker，这意味着当 database 故障时，重试不会停止。

> 在模拟中，这直接导致了：order_service 产生 600 次重试（配置 retry_count=3），放大了 3 倍流量到已经故障的 database，引发连锁超时。

🧭 思考题

如果你的重试策略在依赖故障时反而加剧了问题，你会如何限制重试的「爆炸半径」？考虑：重试应该在什么条件下停止？谁应该负责做出停止的决策？

✅ 做对的部分

你为 cache 配置了 2 副本和 timeout=100ms，说明你理解缓存层需要快速响应。这个设计在模拟中表现良好——cache 是唯一没有崩溃的组件。
