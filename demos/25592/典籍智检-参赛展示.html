PROBLEM

图片内容，提取了却从未被检索

图片型PDF等非文本文件中的内容形同虚设，现有方案要么搜不到、要么太慢、要么丢信息。

🔍

检索失效

图片型PDF等非文本文件无法提取文字，传统检索只能搜文本，图片中的知识点、插图、图表、地图全部形同虚设，用户无法通过关键词找到图片内容。

⚡

高延迟高成本

端到端多模态方案每次查询都需调用视觉模型推理，延迟5-10秒，需要GPU支持，普通设备根本无法部署，算力资源有限的用户更无力承担。

📄

语义丢失

OCR方案只能提取图片中的文字，图片的视觉语义信息全部丢失——你无法用OCR提取出"这是一张溶洞照片"这种信息。

SOLUTION

先描述后检索

核心观察：图片的检索需求不要求实时理解图片内容，而是要求图片能被"找到"。如果离线预先为每张图片生成文本描述，图片检索就转化为文本检索问题。

壹

离线描述生成

VLM为每张图片生成100-200字中文描述，仅调用一次

贰

统一文本索引

图片描述与文本内容合并，共享BM25+语义向量索引

叁

零推理检索

查询时纯文本操作，BM25倒排查表+向量点积，无需GPU

视觉理解成本从查询阶段转移至索引构建阶段，这是"低算力"的真正来源

ARCHITECTURE

三大核心模块

系统由基础信息检索、多模态检索、语义对话三大模块构成，各模块自洽又协同。

📖

基础信息检索模块

  • BM25关键词检索（k1=1.5, b=0.75, jieba分词+66停用词）
  • 语义向量检索（腾讯混元Embedding, 1024维, 余弦相似度）
  • 混合融合检索（Min-Max归一化, 0.4:0.6加权）
  • 辅助检索（精确匹配TF密度 + 关键句Jaccard相似度）
  • AND/OR多关键词组合检索
🖼️

多模态检索模块

  • 双通道图片获取（嵌入图片提取 + 整页渲染）
  • VLM描述生成（Qwen3-VL-8B, temperature=0.3）
  • 图文融合索引（image_desc + page_render + text统一索引）
  • 图片chunk加权（1.2x提升）+ 同页结果合并
  • 多级压缩 + LANCZOS重采样 + 断点续传
💬

语义对话模块

  • 意图理解（7核心字段+4教材扩展字段, JSON容错）
  • 四路召回（主查询+关键词OR+扩展查询+语义改写）
  • 上下文构建（≤6000字符/8个chunk, 元数据完整）
  • 回答生成（腾讯混元, 对话历史管理, 风格自适应）
  • Prompt注入防御 + 四层降级策略
HIGHLIGHTS

低算力如何实现

不是算力不够所以做得简陋，而是通过架构设计把视觉理解的一次性成本放在离线阶段。

对比维度端到端多模态方案本系统（先描述后检索）
查询时VLM推理每次查询都需要不需要
查询时GPU需要不需要，纯CPU
查询时计算量VLM前向推理（数十亿参数）BM25查表 + 矩阵点积
单次查询延迟5-10秒<3秒
VLM调用次数每次查询1次全生命周期仅1次（离线）
检索基础设施图文需两套系统再合并图文共享同一套索引
混合检索

BM25 + 语义向量加权融合

BM25捕获精确词项匹配（术语、人名），语义检索捕获语义关联（"溶洞地貌"→"喀斯特地形"）。Min-Max归一化消除尺度差异，0.4:0.6加权融合，候选扩大top_k×2防遗漏。

图文融合

图片描述与文本共享索引

VLM生成的图片描述封装为image_desc和page_render两种chunk，与text chunk统一建索引。一次检索即可同时命中文本和图片，无需跨系统合并。图片chunk加权1.2x，同页结果自动合并。

典籍智检

面向非文本文件的低算力多模态检索系统设计。采用"先描述后检索"策略，将视觉理解成本从查询阶段转移至索引构建阶段，实现零GPU推理的多模态检索。
