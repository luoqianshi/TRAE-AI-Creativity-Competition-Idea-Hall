01 / 创意介绍

让 Agent 只认手册，绝不瞎编

解决嵌入式开发者翻阅数百页手册的痛点，通过对话即可生成带依据标注的可信 C 代码。

!
想解决的问题

手册太厚，AI 太假

每配置一个外设，都要在动辄数百页的芯片手册里翻找寄存器地址、位域定义、复位值，耗时且极易出错；而通用 AI 生成代码时又经常凭空捏造寄存器地址，导致硬件直接"死给你看"。

?
为什么会想到做这个

翻 20 分钟，只为配一个引脚

在 STM32 / IMU 项目开发中，我反复经历"为配一个 I2C 引脚复用而翻 20 分钟手册"的痛苦。通用大模型虽懂 C 语法，却不懂"这块芯片的寄存器到底长什么样"，常常一本正经地编造地址。于是想做一个"只认手册、绝不瞎编"的 Agent。

>_
大概是什么产品

本地命令行 Agent 系统

用户导入 PDF 手册后，通过对话提问即可生成带依据标注的嵌入式 C 代码，每条关键操作都标注来源页码与寄存器名。后续将增加可视化 Web 界面，与 CLI 共存。

02 / 目标用户及痛点

谁会用，何时用，痛点在哪

面向所有需要与芯片寄存器打交道的开发者。

面向用户

核心用户群体

拿到一款新芯片，需要快速编写寄存器级初始化代码、配置外设复用、读取传感器数据的开发者。

嵌入式工程师 硬件驱动开发者 物联网固件工程师 电子/自动化学生 创客与极客

✗ 没有它之前

  • 手册厚达数百到上千页，人工查找一个寄存器平均耗时 20-30 分钟
  • 容易误读位域定义或复位值，导致硬件 Bug 难以定位
  • 通用 AI 生成代码时常捏造寄存器地址，不可信、不敢直接用
  • 不同厂商手册格式各异，缺乏统一检索工具
  • 新人上手慢，老手重复劳动
⟶

✓ 有了它之后

  • 自然语言提问，30 秒内拿到可用的初始化代码
  • 每条关键操作标注来源页码与寄存器名，可追溯可审计
  • 严格基于检索到的手册内容，禁止捏造任何地址
  • 支持多本手册独立管理，向量库本地持久化
  • 手册未提及的配置，明确告知"未找到"

04 / 技术架构

ReAct + 混合检索 + 表格抽取

思考 → 检索 → 观察 → 生成，每一步都可追溯。

核心流程

ReAct 推理链

用户提问 → Agent 思考要查什么 → 调用混合检索（向量 + BM25）→ 命中寄存器表/文本片段 → 基于检索结果生成 C 代码并标注依据。

INPUT用户提问
→
THINKReAct 思考
→
ACTION混合检索
→
OBSERVE手册片段
→
OUTPUTC 代码+依据
▦
文档解析

表格整块抽取

page.find_tables() → 整个表格作为单个 Chunk，绝不从中间截断；剔除落入表格区域的文本块避免重复。纯文本按章节标题切分，超长章节用滑动窗口。

⇄
混合检索

向量 + BM25 融合

向量路：ChromaDB 语义召回（"配置 I2C 复用"→ I2C 章节）。BM25 路：精准命中（I2C_CR1 → 寄存器位域表）。RRF 融合 + Rerank 重排。

§
铁律约束

禁止捏造

寄存器地址、位域、复位值、引脚复用编号必须来自检索结果。手册未提及的配置必须明确告知"未找到"。C 代码标注每条关键操作的依据。

06 / 产品演进路线

从命令行到可视化

CLI 先行验证核心能力，可视化界面让更多人用得上。

V1.5 · 当前版本

交互式 CLI + 核心引擎

  • Rich 终端分色输出（青色思考 / 黄色检索 / 绿色答案）
  • 多手册独立管理（每个 PDF 独立向量目录，可单独删除）
  • ReAct + 混合检索 + 表格整块抽取
  • Rerank 重排序 + 语义缓存
  • 支持本地 Ollama / 阿里云百炼 等多后端
V2.0 · 规划版本

可视化 Web 界面（与 CLI 共存）

  • 左侧：手册库管理（拖拽上传 PDF / 删除 / 列表）
  • 中间：对话交互区（流式输出 ReAct 思考过程）
  • 右侧：检索结果与生成代码并排展示（一键复制 / 下载 .c 文件）
  • 多轮上下文记忆 + 渐进式摘要压缩
  • 语义缓存命中可视化（相似问题直接返回）
V3.0 · 远期愿景

多模态 + 协作

  • VLM 解析时序图 / 引脚图 / 扫描页
  • 团队共享手册库与代码片段
  • IDE 插件（VS Code / Keil）
