核心设计哲学
📄
文档驱动
每个阶段只读取指定的前序文档文件，不依赖会话上下文，从机制上防止 AI 幻觉
🔗
可追溯性
每阶段输出可追溯性报告，列出输入→输出映射、符合项核对清单、差异与风险
🔄
闭环修复
审查发现问题后自动生成修复任务清单，状态回滚驱动二次开发，确保功能完整性
9阶段开发流程
1
需求文档
对话收集项目信息 → 需求输入.md → 需求规格说明书 → 可追溯性报告
2
架构设计
基于需求文档生成架构设计文档，包含技术选型、分层图、安全架构
3
详细需求
需求总览 + 子模块详细需求，每个功能点分配 REQ 编号
4
数据库设计
ER 图、表结构、索引策略，每个字段关联到模块需求
5
API 设计
接口清单、请求/响应结构、错误码规范，关联数据表与需求
6
开发计划
阶段划分、任务清单、开发进度矩阵（最小功能单元追踪）
7
分模块开发
详细设计 + 开发索引 + 代码，开发完成后更新进度矩阵
8
代码审查
逐模块功能完整性校验，生成审查报告与修复任务清单
9
测试计划
测试计划 + 测试报告 + 测试代码，测试用例双向追溯到需求
核心创新：开发进度矩阵

以"最小功能单元"为粒度，追踪每个功能点的开发状态，确保开发人员知道应该开发哪个模块功能

字段 说明
最小功能单元 不可再拆分的功能点（如"用户登录"、"商品列表查询"）
优先级 P0（核心）、P1（重要）、P2（一般）
状态 待开发 → 开发中 → 已完成 → 已审查 → 已测试 → 已发布
依赖功能 本功能依赖的其他最小功能单元，确保开发顺序正确
关联关系 每个功能单元关联 REQ 编号、API 接口、数据表
解决的核心问题
⚠️
上下文幻觉
AI 在长对话中会忽略或幻想内容，导致代码与需求不一致
🔀
开发无序
没有明确的开发顺序，开发人员不知道先做哪个功能
❌
功能遗漏
开发完成后无法验证是否完全实现了所有需求
对比优势
对比维度 传统 AI 开发 全栈开发工作流
输入来源 会话上下文（易幻觉） 文档文件（防幻觉）
开发顺序 依赖 AI 判断 进度矩阵驱动
功能完整性 无法验证 逐模块校验
问题修复 手动追踪 修复任务清单 + 状态回滚
可追溯性 无 REQ → API → DB → Code 完整链路
