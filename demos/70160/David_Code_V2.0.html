▸ 创意介绍

⚠️

翻手册的痛苦

嵌入式开发者每配置一个外设，都要在动辄数百页的芯片手册里翻找寄存器地址、位域定义、复位值。人工查找一个寄存器平均耗时 20-30 分钟，容易误读位域导致硬件 Bug 难以定位。

// 人工翻手册 I2C_CR1 = ???; // 地址是多少来着？ // 翻了 20 分钟...
💡

通用 AI 不靠谱

通用大模型虽懂 C 语法，却不懂"这块芯片的寄存器到底长什么样"，常常一本正经地编造地址，导致硬件直接"死给你看"。开发者不敢直接用生成的代码。

// 通用 AI 生成（危险！） I2C_CR1 = 0x40005400; // ← 这个地址是编的
✅

只认手册，绝不瞎编

让 Agent 先读懂 PDF 手册，再基于真实内容写代码。每条关键操作都标注来源页码与寄存器名，可追溯、可审计。V2.0 新增可视化 Web 界面 + 多轮记忆 + 语义缓存。

// David Code 生成（可追溯） I2C_CR1 = 0x40005400; // 来源: P42, I2C_CR1

▸ 价值与意义

0x 效率提升（30 分钟 → 30 秒）
0% 代码可追溯（每条操作标注来源）
0 缓存命中时 API 调用（语义缓存）
⚡

效率价值

单次外设配置从 20-30 分钟压缩到 30 秒。语义缓存让重复问题零延迟返回，团队协作边际成本趋近于零。

🛡️

安全价值

生成的 C 代码每条关键操作都标注依据（来源页码 / 寄存器名），可追溯、可审计，杜绝"凭感觉写代码"导致的硬件事故。手册未提及的配置，明确告知"未找到"而非编造。

💼

商业价值

降低嵌入式开发门槛，缩短硬件产品研发周期。可作为企业内部芯片手册知识库沉淀技术资产。可视化界面 + 多会话管理，服务中小硬件团队与教育市场。

🧠

ReAct 推理 + 混合检索

Thought → Action（向量召回 + BM25）→ RRF 融合 → Rerank → 生成代码。让 Agent 像工程师一样"先想清楚要查什么，再动手查"。

📊

表格整块抽取

寄存器位域表作为单个独立 Chunk 入库，绝不在中间截断，保证位定义完整性。剔除落入表格区域的文本块，避免重复。

📝

Scratchpad 状态草稿本

Agent 每轮把关键发现（寄存器地址、位域定义）写入草稿本。调 LLM 时只传「System Prompt + Scratchpad + 最近 N 轮」，关键事实永不丢失。

🗜️

渐进式摘要压缩

对话 Token 达 70% 上下文窗口时，自动用小模型对早期对话做事实性摘要（严格保留寄存器名/地址/位域），释放窗口空间，支持超长多轮对话。

⚡

语义缓存

基于 ChromaDB 余弦相似度，相似问题 > 0.95 直接返回缓存答案，bypass LLM + RAG。LRU 淘汰策略，零 LLM 调用、零 API 费用。

🖥️

可视化 Web 界面

React + TypeScript + Ant Design + FastAPI 后端。SSE 流式输出 ReAct 思考过程，手册库可视化管理，SQLite 持久化多会话。

▸ 最终回答
// 配置 PB6 为 I2C1_SCL 复用
// 来源: MPU-6000A 手册 P38, GPIO_AFRL
GPIOB->AFRL &= ~(0xF << (6 * 4));
GPIOB->AFRL |= (4 << (6 * 4)); // AF4 = I2C1_SCL

// 来源: P42, I2C_CR1
I2C1->CR1 = 0x40005400;
I2C1->CR1 |= (1 << 0); // PE: 外设使能
