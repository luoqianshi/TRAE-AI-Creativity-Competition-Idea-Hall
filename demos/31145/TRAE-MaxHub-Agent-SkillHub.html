Pain Points

Agent 调 API 的问题，不是「不会调用」，而是「容易调用错」

传统 API 文档面向开发者，而不是面向 Agent。真实任务中，Agent 需要理解意图、选择接口、传递参数、串联端点并处理错误，这正是最容易出错的部分。

🎯

选错接口

用户说查评论，Agent 可能调用详情接口；用户说查弹幕，Agent 可能误调用评论接口。

🧩

参数混淆

uid、mid、user_id、aweme_id、note_id、video_id 等参数命名复杂，跨平台更容易传错。

🔗

链式调用复杂

搜索 → 详情 → 评论 → 用户画像，往往需要多步接口接力，字段流转不能靠猜。

🧭

文档不适合 Agent

普通文档只写端点，不告诉 Agent 先读哪个文件、如何匹配意图、如何 fallback。

🛡️

高风险缺少边界

涉及 cookie、写操作、会话、签名等能力时，需要 restricted 标记和用户确认流程。

⚡

大文件浪费上下文

大型 endpoint whitelist 会消耗大量 token，需要 Loading Map 按域精确加载。

Solution

把 API 能力封装成 Agent 能理解的 Skill 结构

MaxHub Agent SkillHub 不是简单罗列接口，而是把「用户意图 → recipe → atom → endpoint → 参数流 → 安全校验」设计成完整工作流。

01
SKILL.md

Agent 决策入口：能力说明、加载顺序、风险等级、错误处理、隐私声明。

02
recipes/_index.md

自然语言 intent 索引：用 trigger 识别用户需求，最长匹配优先。

03
recipes/<domain>.md

具体链式调用步骤：Inputs、Atomic Steps、Output、Fallback。

04
atoms/_index.md

把端点抽象为 atom，标注 risk、幂等性、写操作和 chain_role。

05
param-mappings.md

参数别名、字段流、上游 OUT 到下游 IN 的映射，避免传参错误。

06
endpoints_whitelist.yaml

端点白名单，禁止 Agent 自行拼路径、改版本号或臆造参数。

07
Loading Map

大文件按域加载，减少上下文消耗，提升调用速度。

08
Restricted Control

高风险能力默认禁用，必须用户确认后才允许调用。

Safety & Accuracy

准确调用 + 风险可控，是 Agent 工具化的底线

📍

Endpoint Whitelist

所有路径必须来自白名单，Agent 不允许自己拼路径、改版本号或发明端点。

🧠

参数别名表

统一 uid/user_id/mid、video_id/aweme_id/note_id 等易混参数，按下游端点要求传参。

🔄

字段流字典

明确上游响应 JSONPath 如何变成下游输入参数，降低链式调用失败率。

🚧

Restricted Endpoint

对写操作、cookie、会话、签名等高风险能力加 restricted 标记和确认流程。

⚙️

Risk-based Check

low 风险端点快速校验，高风险端点强制确认，兼顾效率和安全。

📊

未来 Telemetry

记录失败接口和失败原因，用真实调用数据反向优化 Skill 文档与 recipe。

Roadmap

从 SkillHub 到 Agent 数据能力中台

下一步将增加统一调用日志、失败分析、自动优化建议和可视化控制台，让 Skill 能根据真实使用数据持续进化。

调用日志与失败分析

通过 wrapper 或网关记录 endpoint、recipe、参数缺失、HTTP 状态和业务错误，识别最常失败的接口。

自动生成优化建议

根据 400/422/404/5xx 等错误，反向生成 param-mapping、recipe fallback、缺参追问等优化建议。

MCP / Agent SDK 集成

把 Skill 封装为 Agent 可直接调用的工具协议，减少手写 curl 和人工配置。

企业内部 API 扩展

将这套 Skill 规范迁移到企业内部 CRM、BI、数据仓库和业务系统 API。
