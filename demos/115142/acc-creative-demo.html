Agent Capability Contract

A2B 场景下的 Agent 能力声明开放标准——让业务系统用统一契约安全地向 AI Agent 声明哪些 API 可见、风险多大、谁来审批

ACC 管 reach（可见范围） | 业务系统管 authority（最终权限）
⚠️ 为什么需要 A2B 标准？
🔓

Agent 能调什么 API？没人知道

OpenAPI 只管接口格式，不管 "这个接口能不能给 Agent 调用"。Agent 可能误调退款、删除用户、批量操作，业务系统毫无防备。

📋

调完之后谁负责？查不到

Agent 发起的操作没有统一的审计标记：哪些字段是敏感数据要脱敏？哪个调用触发了审批？出问题后无法追溯。

🔀

每个团队自己发明规则

A 团队的 "只读白名单" 和 B 团队的 "风险分级" 互不兼容。MCP Gateway、API Gateway、SDK Generator 都要各自实现一遍，没有可移植标准。

🔄 没有 ACC vs 有 ACC

没有 ACC 的现状

Agent 无差别看到所有 API
不知道哪些操作风险高
无法判断要不要人工审批
敏感字段泄漏到审计日志
每家运行时自造权限格式
标准实现绑定特定产品

📄 实战：在 OpenAPI 中加入 ACC 声明
# 退款申请接口 —— ACC v1 完整声明示例
paths:
  /refunds/request:
    post:
      operationId: refund_request_create
      summary: 发起退款申请
      x-agent-capability:           # ← 唯一的 ACC 扩展字段
        version: 1                    # 契约版本
        enabled: true                # Agent 可见
        scope: refund.request.create # 能力范围
        risk:
          level: medium            # 中风险（涉及资金但不直接扣款）
        subject:
          required: true           # 必须有真实用户身份
        approval:                     # 审批意图声明
          when:
            - param: amount
              op: ">"
              value: 1000              # 退款金额超 1000 需审批
              label: 退款金额超过 1000
        audit:
          sensitive: true          # 请求/响应含敏感数据需脱敏
        execution:
          timeout_ms: 10000
          rate_limit:
            count: 30
            window: 1m               # 每分钟最多 30 次

ACC 不是运行时，不执行这个 API。它只是声明：
"这个接口可以给 Agent 用，中等风险，需要真人身份，大额要审批，数据要脱敏。"

🛑 ACC 不做什么——知道边界才叫真正理解
ACC 不管的事为什么？正确责任层
最终用户权限判定角色、ABAC、数据权限随业务状态变化业务授权层
审批人和审批流程会签、委托、升级取决于组织流程外部审批系统
身份格式（JWT/证书等）不同系统的身份表达不可互换运行时身份桥
跨字段不变量"退款额 ≤ 可退余额"需要权威业务数据业务操作或预检 API
回滚与补偿事务补偿不是简单反向调用，涉及授权和状态Saga / 工作流层
HTTP/RPC/MCP 传输同一份 ACC 可被不同传输协议消费Binding / 适配器

这些事不进入 ACC 不是因为他们不重要，而是因为 只有业务系统或部署方才能正确兑现。
ACC 坚持薄核心 = 高可移植性。

🏗️ 四类独立实现，平等合规

ACC Parser

读取并校验 ACC 声明，生成结构化能力注册表。可在构建时编译或运行时加载。

ACC Generator

从源码注解或现有契约自动生成 ACC 声明。适合已有 API 项目的增量接入。

ACC Runtime

执行 ACC 的暴露和调用语义：scope 过滤、subject 检查、approval 检测、audit 脱敏。

Policy Component

为其他 Runtime 或 Gateway 提供 ACC 治理语义的子集，嵌入已有基础设施。

🏛️ 中立治理——不绑定任何产品

什么是 ACC

ACC 是一个独立开放标准，不隶属于任何产品。任何控制面、API 网关、SDK、Agent 运行时、MCP Gateway 或策略引擎都可以独立实现 ACC，按语义化版本治理，Apache 2.0 开源。

什么不是 ACC

ACC 不是任何产品的配置格式、销售入口或兼容层。实现者登记 ≠ 官方认证。没有任何产品因与维护者的关系获得优先兼容地位。

规范语义由 SPEC 定义，不由任何实现的当前代码决定。
