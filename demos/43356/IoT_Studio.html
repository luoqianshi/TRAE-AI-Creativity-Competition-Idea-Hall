一、创意概述

1.1 一句话描述

通过自然语言对话，自动生成电路接线图与固件代码，并在浏览器中直接运行仿真。让没有硬件条件的用户也能完整体验 IoT 开发全流程。

1.2 想解决什么问题

物联网硬件学习门槛极高。学习者需要自行购买单片机、传感器等硬件设备，学习电路接线、C语言编程、通信协议和多层调试——一个简单的温湿度显示实验往往耗费一到两周。对于没有硬件条件的学生，这条路直接走不通。

现有仿真平台（如 Wokwi）存在诸多问题：打开网站后卡住、无法保存工程、无 AI 交互、运行延时长、成功率存在偶然性。这些工具解决了"不用买硬件"的问题，但没有解决"不知道怎么接线、代码为什么报错、自学难"的核心痛点。

1.3 为什么会想到做这个

我本人系统学习过 51 单片机、STM32 单片机、ESP32 单片机，深知物联网开发必须软硬件兼备。市面上 Wokwi 等仿真工具解决了"不用买硬件"的问题，但缺少 AI 辅助指导——初学者面对的仍然是一个冰冷的空白画布，而非一个会教的导师。

如果能将自然语言对话与浏览器端仿真结合起来，用户只需简单描述需求，AI 即可生成代码、接线，并在纠错中引导用户学习——这将彻底改变 IoT 入门教育的体验。

1.4 大概是什么产品

一个 Web 端智能IOT仿真学习平台。用户通过对话式简单描述需求，系统自动生成电路方案与固件代码，AI 辅助纠错和教学，用户可直接在浏览器中运行仿真并查看效果。平台支持 AI 对话生成、Canvas 面包板渲染、代码编辑、浏览器端仿真运行、虚拟传感器面板交互、串口监视器等功能。

四、系统架构

4.1 总体架构

系统采用前后端分离 + Web Worker 多线程架构：

前端层：React 18 + Vite + TypeScript，负责 UI 渲染（Fabric.js Canvas 面包板 + Monaco Editor 代码编辑器 + 对话面板 + 串口监视器 + 虚拟传感器面板）。

后端层：Node.js 轻量 API 服务，负责 LLM 代理转发（隐藏 API Key）、请求速率限制。

仿真层：两个独立 Web Worker 线程——编译 Worker（调用 Emscripten-WASM 编译工具链）、仿真 Worker（运行指令集模拟器 + 虚拟外设总线），与主线程隔离，不阻塞 UI。

引脚规则校验层：手写 TypeScript 引脚规则引擎（3 种 MCU × 约 60 条规则），所有 LLM 生成的引脚映射必经校验才进入渲染。

4.2 数据流

用户自然语言输入 → LLM 流式推理（生成结构化 JSON + C/C++ 固件代码）→ 引脚规则引擎校验 → Canvas 渲染面包板接线图 → Monaco 加载代码 → 编译 Worker 编译固件 → 仿真 Worker 运行指令模拟器 → 虚拟外设总线驱动 Canvas 元器件动画 + 串口监视器输出。

7.1 教学模式的教学价值

所有预设模板（T1-T3）在代码注释中预埋教学标记点（如"// 教学点：DHT11 最快每1秒读一次，改更小会发生什么？"），即使 LLM 未能动态生成教学问题，教学体验也不会落空。AI 辅助策略包括：生成 delay(2000) 后追问"为什么两秒读一次就够了？改成 200ms 会怎样？"——引导用户主动思考而非被动接收。

7.2 对路演叙事的价值

三种模式的展示让评委看到的是一套"教学方法论"而不仅仅是"代码生成工具"。产品从"效率工具"升维为"教育产品"，赛道②"造个新解法"的定位更加扎实。

7.3 路演演示策略

用 30 秒展示教学模式：先让用户自己接错线 → 系统纠正并解释原因 → 用户改正 → 仿真跑通。评委看到的是"系统在教用户做事"，而非"系统替用户做事"。

9.3 编译与仿真分离架构

编译阶段：用户代码在编译 Web Worker 中调用对应编译工具链（已编译为 WASM），生成二进制固件。编译错误通过结构化 JSON 返回前端，在 Monaco Editor 中标注错误行。常用库函数预编译为 WASM 对象缓存于 IndexedDB，增量编译仅需处理用户业务逻辑部分，编译时间从约 2 秒降至约 200ms。

仿真阶段：仿真核心（指令集模拟器 + 外设模型）运行在独立仿真 Web Worker 中，通过虚拟外设总线与 Canvas 交互。仿真时钟频率统一降频至 1MHz 以保障 UI 流畅度。WASM 内存与主线程隔离，无法访问 DOM 和浏览器 API。

十、引脚规则校验引擎

十一、LLM 方案与 Prompt 工程

11.1 LLM 选型

方案模型定位
主模型GPT-4o（OpenAI）/ Claude 3.5 Sonnet（Anthropic）对比评估选生成稳定性更高者
备选DeepSeek-V3成本更低，适合高频调用
兜底本地 Mock + 预设模板离线可用，确保路演无条件可演示

11.2 上下文管理策略

滑动窗口 + 摘要压缩：保留最近 3 轮完整对话 + 当前电路 JSON 状态（≤2KB），超出部分由 LLM 自行摘要压缩后作为前缀上下文。

代码上下文注入：每次对话自动注入当前代码编辑器的全部文件内容（≤10KB），超出部分仅注入当前活跃文件。

Token 预算：单次请求控制在 4K-8K tokens 以内，简单场景优先预设模板跳过 LLM。

11.3 Prompt 核心策略

角色设定：System Prompt 定义为资深嵌入式工程师 + 教育导师双角色，必须输出合法 JSON + 可编译的 C/C++ 代码。

Few-Shot 示例：预设 5 组典型需求-输出 JSON 的配对示例，涵盖 GPIO/I²C/PWM/ADC 常用场景。

输出约束：JSON 外层使用 json 代码块包裹，固件代码使用 c 代码块包裹，便于前端解析。

容错兜底：若 LLM 返回无法解析的内容，自动回退至预设模板中最匹配的项目；连续 3 次解析失败后建议用户从预设模板开始。

11.4 网络不可用降级方案

比赛现场若外网不可用，前端自动切换至本地 Mock 模式：用户输入需求文本 → 关键词匹配 → 命中则加载最相近的预设模板并替换参数；未命中则提示 Demo 模式下当前仅支持预设模板并展示 T1-T3 供选择。

13.2 三管齐下优化策略

策略一 —— 预编译与缓存：将常用 Arduino 库函数预编译为 WASM 对象文件并缓存于 IndexedDB。增量编译仅处理用户业务逻辑部分，编译时间从约 2 秒降至约 200ms。

策略二 —— 流式渲染：用户输入后立即开始视觉反馈——0.5s Canvas 空面包板 → 1.0s 元件弹出 → 2.0s LLM 首 Token 到达，代码逐行出现 → 4.0s 飞线绘制 → 5.0s 完整方案展示 → 6.0s 仿真启动。用户始终看到进展，而非空白等待。

策略三 —— 预设模板兜底：路演场景下预设模板 < 2 秒即可完成加载和仿真，LLM 功能作为增值亮点而非生命线。

十四、安全性设计

14.1 LLM API 安全

API Key 不在前端明文存储，所有 LLM 请求通过 Node.js 后端代理转发，后端对 Key 进行环境变量注入。请求频率限制：同一用户每分钟最多 10 次 LLM 请求。

14.2 代码执行沙箱

用户 C/C++ 代码经编译后在独立 Web Worker 中运行，WASM 内存与主线程完全隔离，无法访问 DOM 和浏览器 API。仿真核心不包含文件系统或网络访问接口。

14.3 数据安全

用户项目和代码默认存储在浏览器 localStorage/IndexedDB 中，不上传服务器。云部署功能上线后采用 HTTPS 传输，云端不存储用户源代码。
