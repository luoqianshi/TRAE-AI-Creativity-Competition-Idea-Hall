Chapter 01

问题背景

在 AI 辅助软件工程开发中，遗忘和幻觉是两个核心风险， 它们的本质是同一个问题——上下文管理失败

🧠

遗忘 Forgetting

表现：跨会话丢失关键信息（如生产环境地址、架构设计规则、版本号）

后果：重复讨论已解决的问题、使用错误的环境配置、违反已建立的约定

根因：上下文窗口有限，长对话中早期信息被压缩或丢失；跨会话时记忆不完整

🌀

幻觉 Hallucination

表现：编造不存在的 API 端点、虚构配置字段、假设架构设计

后果：生成无法运行的代码、误导用户、造成生产事故

根因：上下文不足时，模型倾向于"合理推测"而非承认不确定

Chapter 02

演进历程

从 V1 到 V3，我们经历了三个阶段，每个阶段都有不同的问题和教训

V1 阶段

无上下文管理

没有任何规则或记忆机制，AI 完全依赖对话上下文。遗忘开发/生产环境差异，导致严重生产事故。

严重问题
V2 阶段

规则过载

增加了 rules 规范，但规则太多太详细（>5000 tokens），系统提示词过大，模型性能受损，任务推进效率变差。

性能下降
V3 阶段

分层挽具模型

Trae Work 一定程度缓解了规则过大问题，通过分层管理 + 按需加载 + 强化验证，显著降低遗忘和幻觉风险。

持续优化
Chapter 03

理论框架

借鉴 Harness Engineering 理念，采用分层管理 + 按需加载 + 强化验证策略

分层挽具模型

Layer 1 .trae/rules/

给 AI 看的"硬约束"，每次对话自动注入

  • 环境 IP/端口/认证
  • 架构约束
  • 操作红线
  • 命名规范

最稳定 · 永远不丢 · < 2000 tokens

Layer 2 memory/

给 AI 看的"演进知识"，通过 system-reminder 注入

  • 当前版本号
  • 最近完成的功能
  • 踩过的坑
  • 待办事项状态

跨会话保留 · 可能被截断

Layer 3 docs/

给人看的项目文档，AI 不会主动读取

  • 设计文档
  • 操作手册
  • 测试报告
  • 发布说明

最完整 · 需要人工查阅

Layer 4 conversation

当前对话的短期记忆

  • 正在讨论的功能
  • 刚才的测试结果
  • 临时的工作文件
  • 中间推理过程

会话内有效 · 会压缩/丢失

Chapter 04

踩坑案例

从实际开发中提炼的典型案例，每一个都是血泪教训

01

遗忘生产环境信息

遗忘类 · 2026-07-08
用户反馈
"你检查的生产机是哪部服务器？？不是本地的哦"
问题对比
❌ 错误做法

直接访问 localhost:8320，返回的是开发环境的执行记录，不是生产环境的

✅ 正确做法

先读取 environment.md 确认生产环境 IP（10.115.28.218:8320），获取 JWT Token 后访问

教训

环境信息必须双写：既在 .trae/rules/environment.md（给AI），也在 docs/03-配置说明.md（给人）

02

幻觉架构设计

幻觉类 · 2026-07-08
用户反馈
"我们的字段对应应该在转换里实现啊？？DTP是实例化，需要有一个转换才能有对应的DTP，难道后边的版本里这个规则已经不存在了？？"
问题对比
❌ 错误回答

"字段映射在 DTP 执行器中实现源字段到目标字段的映射"

✅ 正确回答

"字段映射在 Transformation 中定义，DTP 通过 transformation_id 引用，执行时读取并应用"

教训

架构约束必须固化到 rules 中，涉及架构问题时必须读取源码确认，不能凭记忆回答

03

规则过多导致性能下降

上下文过载类 · V2 阶段
用户反馈
"在这个过程里出现因为规则太多太详细，系统提示词过大，模型性能受损，任务推进效率变差的问题"
问题对比
❌ 错误做法

将所有规则都写入 .trae/rules/，超过 5000 tokens，导致模型性能下降

✅ 正确做法

分层管理：rules/ 只放硬约束（<2000 tokens），memory/ 放演进知识，docs/ 放详细文档

教训

规则不是越多越好，采用分层管理，按需加载，保持 .trae/rules/ 精简

04

版本号不一致

遗忘类 · 2026-07-07
问题描述

API数据源文档中版本号不一致，部分文档仍为v3.9.1，而实际已升级到v3.9.2

解决方案

建立版本更新检查清单，同步更新代码、文档、记忆三个层面

05

字段映射配置错误

幻觉类 · 2026-07-07
问题描述

在API数据源配置示例中，错误地将 field_mappings 放在数据源配置中，而实际上应该在Transformation中配置

教训

配置示例必须经过架构验证，建立配置模板库，避免重复错误

06

环境信息重复遗忘

遗忘类 · 多次发生
用户反馈
"生产机的信息没有在我们的项目核心文档里记录吗？？我看到你已经多次丢掉这个信息了"
根因

环境信息只记录在 memory/ 中，而没有记录在 rules/ 中。memory 可能被截断或遗漏

解决方案

关键信息必须双写（rules/ + docs/），环境信息记录在 .trae/rules/environment.md（最稳定）

Chapter 05

工程实践

前馈-反馈循环：开发前确认上下文，开发中持续验证，开发后知识沉淀

📋 开发前检查清单（前馈控制）

明确当前版本 — 读取 project_memory.md 确认当前版本，确认开发环境和生产环境的版本差异

明确目标环境 — 确认本次任务针对开发环境还是生产环境，确认目标环境的 IP、端口、认证方式

明确相关约束 — 读取 .trae/rules/ 确认项目规则，确认架构约束和操作红线

明确验收标准 — 与用户确认"完成"的定义，确认测试标准和文档要求

检查相关文档 — 确认设计文档、操作手册、测试报告是否已创建，不要凭记忆回答

🔍 开发中检查清单（反馈控制）

涉及配置/环境/版本 → 必须 Read 文件确认，不可凭记忆

涉及API/CLI → 必须查阅平台API_CLI全量清单确认端点有效性

涉及架构设计 → 必须 Read 相关源码确认对象关系，不可假设

不确定时 → 明确告知用户"我不确定"，而非编造

💾 开发后检查清单（知识沉淀）

重要决策 → 更新 project_memory.md，记录架构决策和环境变更

踩坑教训 → 追加到 Lessons Learned，记录现象、根因、解决方案

版本变更 → 更新 environment.md 和 version records

配置变更 → 更新 03-配置说明.md

🎯

"我确定"

必须有文件/命令输出作为证据

⚠️

"我认为"

必须标注不确定性，建议用户验证

🔍

"我不知道"

主动说，然后去查

Chapter 06

用例演示

以"查询生产机执行记录"为例，展示正确 vs 错误流程

1

读取环境文档确认信息

PowerShell 
# 从 environment.md 确认生产环境信息
# 生产环境: 10.115.28.218:8320, 需要JWT认证
2

获取 JWT Token

PowerShell 
$token = (Invoke-RestMethod -Uri "http://10.115.28.218:8320/api/v1/auth/token" `
    -Method POST `
    -ContentType "application/json" `
    -Body '{"username":"admin","password":"admin"}').token
3

访问生产环境 API

PowerShell 
Invoke-RestMethod -Uri "http://10.115.28.218:8320/api/v3/executions?limit=50" `
    -Headers @{Authorization="Bearer $token"}
4

解析和展示执行记录

统计执行状态分布、处理链分布、展示失败记录详情

关键决策点对比

决策点 ❌ 错误做法 ✅ 正确做法
确认生产环境IP 假设在localhost 读取 environment.md 确认
确认端口 假设是8000 确认是8320
确认认证方式 假设不需要认证 确认需要JWT
获取认证Token 不获取 调用 /api/v1/auth/token
访问API 直接访问，不携带Token 携带 Authorization: Bearer
