ComputerAssistant

基于分层 LLM 的脚本驱动型电脑操作助手 — 让 AI 看懂屏幕，帮你更好地操作电脑
赛道：学习工作

💡创意介绍

想解决什么问题

当前市面上的 LLM 浏览器/桌面自动化工具（如 browser-use、UI-TARS）都是"纯 Agent 驱动"模式——用户说一句话，LLM 自主规划并执行全部操作。这种方式虽然上手快，但面对复杂业务流程时存在三个致命问题：

  • 缺乏可控性：LLM 的决策是黑盒的，出错时难以定位和修正
  • 成本高昂：每次执行都要调用云端大模型反复推理，Token 消耗巨大
  • 无法固化：即使流程已经稳定，每次仍需重新推理，无法复用已有经验

开发者真正需要的是：自己用 Python 写确定性流程，只在"看不清、想不明"的时候才调用 LLM 来辅助感知和决策。

为什么会想到做这个

在日常开发中，我们经常需要做自动化测试、数据采集、重复操作等场景。传统 Playwright/Selenium 脚本写起来繁琐（XPath 定位脆弱），纯 Agent 方案又太"黑盒"不可控。如果能把 LLM 的视觉理解能力像调用一个普通函数一样嵌入到 Python 脚本中，效率和可靠性都会大幅提升。

纯 Agent 方案
"帮我登录并提交表单"
LLM 自主规划所有步骤
黑盒执行，不可控
每次调用都重新推理
ComputerAssistant 方案
"我写脚本，你帮我看"
Python 控制主流程
LLM 只负责感知和定位
验证后可固化，省 Token

👥目标用户及痛点

面向用户

软件测试工程师 RPA 开发者 Python 自动化开发者 AI 应用开发者

使用场景

  • 自动化回归测试：测试脚本写流程，LLM 辅助定位动态元素和判断页面变化
  • 数据采集：脚本控制翻页逻辑，LLM 识别和提取非结构化内容
  • 桌面 RPA：脚本定义操作序列，LLM 辅助识别跨应用的控件和弹窗
  • 工作流自动化：多步骤表单填写、审批流程等

当前痛点

  • 传统脚本定位元素依赖 XPath/CSS 选择器，页面一改就崩
  • 纯 Agent 方案每次调用云端大模型，成本高、速度慢、行为不可控
  • 浏览器和桌面自动化是两套工具，学习成本高
  • 没有一个方案同时支持"脚本控制流程" + "LLM 辅助感知"

💎价值与意义

效率提升

开发者不用再纠结 XPath 写法和页面适配，用自然语言描述目标元素即可定位，同时保留 Python 脚本的完整控制力和可调试性。

成本优化：分层 LLM 路由

简单任务（元素定位、文本提取）走本地小模型，复杂任务（意图理解、异常诊断）才调用 API 大模型，大幅降低 API 使用成本。

1
用户参数优先 — 脚本中可显式指定 tier="local" 或 "remote"
2
本地分类器判断 — 超轻量 LLM 分析任务复杂度，自动路由
3
调用目标模型 — 简单任务本地处理，复杂任务远端推理

流程固化，持续节省 Token

区别于纯 Agent 方案每次都要重新推理，本框架在脚本运行稳定后，可以把已验证的 LLM 决策结果（如元素坐标、操作序列）固化下来，后续相同场景直接走确定性路径，不再调用 LLM。随着使用迭代，越来越多步骤从"AI 推理"退化为"规则执行"，Token 消耗持续递减。

技术价值

填补了 "Script-First + LLM-as-Function" 这一技术路线的空白。目前市面上 Stagehand（TypeScript）最接近这个理念，但 Python 生态中尚无同类产品，更不用说同时覆盖 Computer Use 场景。
