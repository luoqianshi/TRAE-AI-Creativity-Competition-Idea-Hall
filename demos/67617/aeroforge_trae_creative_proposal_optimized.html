从一句目标，到一份工程包

复杂工程不是先生成很多零件再强行拼装，而是让系统、接口、参数、装配和验证同步生长。

01 / DEFINE

工程目标

输入使用场景、课程要求、尺寸、质量、材料等关键约束。

02 / CLARIFY

AI 澄清

追问缺失条件，区分事实、假设、风险与待确认项。

03 / PROPOSE

结构化 Proposal

生成需求、模块、接口、参数和验证计划草案。

04 / CONFIRM

人工确认

关键工程决定由人确认，AI 不直接改写工程事实。

05 / BUILD

受控工具执行

生成参数化 CAD 工件、质量属性、配合检查和分析候选。

06 / PACKAGE

工程包交付

沉淀版本、变更、风险、产物与可继续迭代的资料。

不同角色，共用同一条工程数字主线

AI 不在工程规则之外工作：建议、工具产物和人工判断都有对应的上下文与边界。

学生 / 课程设计

从“我想做一个结构合理的飞行器或机体”开始，AeroForge 通过连续追问把模糊想法推进成需求、模块、参数和验证草案，让学生学习用工程流程思考问题。

用工程目标替代空白画布，降低复杂项目的启动难度
把假设和待确认项显式标记，避免把 AI 文本当作结论
导出结构化工程包，便于课程答辩、复盘和下一次迭代

当前 Demo 的三项核心能力

以教育和学生工程团队中的机体结构设计为首个验证场景，展示完整工程闭环的雏形。

◫

工程数字主线

需求、参数、零件、装配、验证、证据、版本和变更在同一条可追溯链上，不再散落在聊天、表格与文件夹里。

✦

受控 AI 协作

AI 生成的是建议与 Proposal；关键确认、工程变更和责任边界依然掌握在人手中。

⌁

参数化工程体

确认后的结构化输入可进入受控 CAD 工具，回收 CAD 工件、组件追溯与工具分析候选结果。

AeroForge Engineering Package

用户最终拿到的不是一段 AI 回复，也不只是一张模型图，而是一份能被审查、下载、继续修改的工程资料包。 设计的关键决定、工具产物、风险状态和版本记录都留下明确痕迹。

产品边界说明 本创意聚焦教育、课程设计、学生工程团队和早期创客项目中的机体结构协同。 Demo 不包含推进剂、发动机内部设计、点火、飞控、飞行执行或自动放行能力； 所有工具分析都需要人工审查，不能替代正式工程验证与安全责任。

产品会如何成长

先证明一个工程闭环可用，再证明工程师愿意持续使用，最后才面向更复杂团队与工具链扩展。

STAGE A

跑通一个工程闭环

目标、Proposal、人工确认、参数化结构、工程包与版本追溯。

STAGE B

证明工程师持续使用

更顺畅的桌面工程工作流、真实项目复盘与多次迭代体验。

STAGE C

连接团队与工具生态

逐步接入更多工程工具、现场证据和组织级协作能力。
