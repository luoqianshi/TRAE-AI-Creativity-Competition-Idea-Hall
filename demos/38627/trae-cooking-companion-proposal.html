解决的问题

日常做饭不是缺少菜谱，而是缺少一个能理解两个人、记得最近吃过什么、还能持续学习反馈的轻量助手。

选择疲劳

每天临时问“吃什么”会消耗沟通成本，最终常常回到几道熟悉但重复的菜。

偏好冲突

两个人可能在辣度、忌口、菜系和烹饪复杂度上不同，需要明确的折中理由。

菜谱分散

收藏夹、聊天记录和临时搜索难以沉淀，来源不清的菜谱也不适合直接进入个人库。

核心流程

当前应用围绕一个高频闭环实现 MVP：录入偏好，生成推荐，确认选择，记录反馈。

1

维护两份偏好

分别记录喜欢、不喜欢、忌口、常吃菜系、辣度和烹饪复杂度接受度。

2

结合近期历史

系统读取计划做、已做和手动补录记录，默认规避最近 7 天重复菜品。

3

生成今日候选

返回至少 3 个推荐，展示菜名、理由、食材、耗时、难度和来源状态。

4

反馈持续学习

用户可标记计划做、已做、收藏或不想吃，拒绝原因会影响后续排序。

当前项目实现

报名应用就是当前仓库中的 Next.js 应用，目标是可运行、可扩展但不过度设计的个人 MVP。

产品范围
  • 今日推荐首页
  • 双人偏好档案
  • 饮食历史补录
  • 菜谱导入与确认
  • 推荐反馈与撤销
技术方案
  • Next.js App Router + TypeScript + React 构建移动端 Web
  • Supabase PostgreSQL、Auth 与 RLS 存储私密双人空间数据
  • 服务端 Route Handler 编排 AI 推荐、菜谱导入和反馈写入
  • Zod 复用结构化校验，Vitest 与 Playwright 覆盖核心流程

衡量方式

做饭搭子不是一次性的灵感展示，而是通过使用数据验证是否真的减少决策成本。

40%+ 推荐候选被标记为计划做、已做或收藏，说明推荐具备实际采纳价值。
90%+ 当可选菜谱充足时，默认避开最近 7 天已做菜品，减少重复感。
2 分钟 用户从打开应用到确认晚餐方案的目标时长，让决策足够轻。
