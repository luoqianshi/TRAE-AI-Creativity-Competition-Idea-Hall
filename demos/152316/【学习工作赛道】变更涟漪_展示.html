Pain Points

需求变更评估的四大困境

一个小改动，为何总演变成大灾难？

01 // ISSUE

人工梳理耗时且易遗漏

评估一个变更的影响范围通常需要1-2天，开发人员逐行梳理代码依赖，耗时耗力且容易遗漏隐性调用关系。

02 // ISSUE

经验估算，准确性差

"这个改动很简单，2天搞定"——结果牵一发而动全身，实际花了2周。凭直觉估算，缺乏数据支撑。

03 // ISSUE

缺少可视化依赖图谱

代码模块间的调用关系如同暗网，没有可视化的依赖图谱，无法直观看到变更引发的"涟漪效应"。

04 // ISSUE

风险评估靠直觉

接不接这个变更？改多大？排期多久？决策缺乏量化依据，导致频繁延期、返工、团队士气低落。

Technology Stack

技术架构与核心亮点

静态分析 + 知识图谱 + 机器学习，构建变更评估最强引擎

01 // PARSER

多语言AST静态分析

基于Tree-sitter和语言专属Parser，将Java/Go/Python/TypeScript等源码解析为AST，提取类定义、函数签名、调用关系，构建代码的完整依赖模型。

Tree-sitter AST Static Analysis
02 // GRAPH

模块依赖知识图谱

将代码实体（类、函数、接口、表）和它们之间的关系（调用、继承、实现、引用）构建为图数据库，支持多层依赖查询和最短影响路径分析。

Neo4j Dependency Graph Graph Query
03 // DIFF

代码变更语义化Diff

超越文本级Diff，理解变更的语义含义。识别"字段新增"、"接口废弃"、"逻辑重构"等变更类型，自动映射到对应的评估模型。

Semantic Diff Change Taxonomy
04 // NLP

需求描述意图识别

通过NLP技术解析需求变更描述，提取变更目标、涉及实体、预期行为，自动关联代码库中的对应模块，降低人工输入成本。

BERT Entity Linking Intent Classify
05 // ML

工时估算回归模型

基于历史项目的变更记录（影响模块数、代码行数、文件数、团队速率），训练XGBoost回归模型，给出精确到小时的工时预估。

XGBoost Regression Velocity
06 // CI/CD

IDE与流水线无缝集成

提供VS Code/JetBrains插件和GitLab/Jenkins集成，在编码阶段和Code Review阶段实时提示变更影响，将评估能力嵌入开发工作流。

LSP Webhook Plugin
