RustMQ

基于 Rust 的高性能、低占用 MQTT Broker

学习工作赛道 物联网基础设施 高性能系统

创意介绍

一句话概括：RustMQ 是一款使用 Rust 语言从零构建的 MQTT Broker，专为解决现有 MQTT 中间件内存占用高、并发处理能力不足的问题而生，让物联网设备连接更轻量、更高效。

想解决什么问题

当前主流的 MQTT Broker（如 Eclipse Mosquitto、EMQX、HiveMQ 等）普遍存在两个核心痛点：

高内存占用：在百万级设备连接场景下，传统 Broker 内存占用动辄数十 GB，导致边缘设备和小型服务器难以部署。
低并发瓶颈：现有方案在高并发消息推送时 CPU 利用率飙升，消息延迟增加，影响实时性要求高的场景。

为什么会想到做这个

在物联网项目开发中，团队多次遇到 MQTT Broker 成为系统瓶颈的情况。Rust 语言以零成本抽象和内存安全著称，非常适合构建高性能网络服务。我们希望通过 Rust 的极致性能优势，打造一款真正轻量、高并发的 MQTT Broker，降低物联网基础设施的部署成本。

产品形态

RustMQ 是一个高性能 MQTT Broker 服务端系统，支持标准 MQTT 3.1/3.1.1/5.0 协议，提供单机部署和集群部署两种模式，面向物联网平台开发者、边缘计算场景和中小型 IoT 企业。

目标用户及痛点

核心用户群体

  • 物联网平台开发者：需要为海量 IoT 设备提供稳定的消息中间件服务
  • 边缘计算工程师：在资源受限的边缘设备上部署 MQTT 服务
  • 智能家居/工业物联网企业：需要高并发、低延迟的设备通信方案
  • 开源社区贡献者：关注高性能网络编程和 Rust 生态的开发者

使用场景

  • 智慧城市：数十万传感器数据实时采集与分发
  • 工业物联网：工厂设备状态监控与指令下发
  • 智能家居：海量家庭设备的低延迟消息通信
  • 车联网：车辆与云端的高频数据交互

当前痛点

现有 MQTT Broker 在 10 万级连接时内存占用已超 2GB，边缘服务器无法承受
高并发场景下消息延迟从毫秒级飙升至秒级，影响实时业务
商业方案（如 HiveMQ、EMQX 企业版）授权费用高昂，开源方案性能不足

技术方案与优势

技术栈

Rust Tokio 异步运行时 MQTT 5.0 QUIC 传输 无锁数据结构 内存池管理

核心技术创新

零拷贝消息转发：利用 Rust 的所有权机制实现消息零拷贝路由，减少内存分配和复制开销
自适应连接管理：基于 Tokio 的异步 I/O，单线程可管理数万连接，轻松水平扩展
智能内存池：预分配内存池复用机制，避免频繁 malloc/free 带来的性能抖动
分层存储架构：热消息内存缓存 + 冷消息持久化，平衡性能与可靠性

价值与意义

商业价值

  • 降低企业物联网基础设施的硬件成本，同等性能下服务器资源节省 80% 以上
