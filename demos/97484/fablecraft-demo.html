我的反馈

连接建立了但服务器没返回内容——多半是 SSL 握手失败或上游没响应。先自底向上，从容器查起。
排查动作 · 层5
执行 docker ps -a | grep nginx 检查容器状态
我的反馈
容器在跑，端口映射 0.0.0.0:443→443 正常
容器与端口都正常，排除层 5。上移到 Nginx 配置层。
排查动作 · 层4

我的反馈
syntax is ok，test is successful
Nginx 配置无误，排除层 4。下一步查 SSL 证书是否存在。
发现 · 层3
检查证书目录 ls /etc/letsencrypt/live/…
我的反馈
目录是空的，证书根本不存在
找到第一层原因：证书缺失 → SSL 握手失败 → Nginx 无内容返回 → 浏览器 ERR_EMPTY_RESPONSE。
修复
用 webroot 方式签发证书 certbot certonly --webroot
我的反馈

应用层已修复。但外网仍打不开——绕过 DNS 直连源站 IP，看是不是链路问题。

从前有一个王国的首都，住着一位名叫小明的人。他想给住在另一个城市的网友小红寄一封信。

第一幕 · 日常

小明只知道小红的名字，不知道地址。他翻开电话簿，查到"长安街 104 号"，把信交给快递员。到了门口，前台拦下他：要出示身份证，还得用大楼的专用信封重新封装。一切照做，信 3 秒就送到了小红手里。

第二幕 · 出事

有一天，信寄不出去了。同样的信、同样的地址、同样的邮筒——回信始终没来，屏幕上只有一片空白。小明不知道：他的电话簿被人偷偷改过，地址成了不存在的"落日大道 28 号"；楼下新开的连锁邮局用普通明信片送信，被只收专用信封的前台反复退回，陷入死循环。

第三幕 · 破案

小明一层层排查。他亲自把信塞进大楼门缝——小红收到了，说明大楼本身没问题。再查连锁邮局，发现明信片与专用信封的死循环，让它改用专用信封。可信还是寄不到。他当面重查电话簿——地址早被人篡改。而另一个城市、拿着没被改过电话簿的小王，寄信畅通无阻。真相大白：不是一封信、一栋楼、一家邮局的问题，是他的电话簿坏了，而且不止一处。

实践钩子

下次浏览器打出 ERR_EMPTY_RESPONSE，先别查代码——快递员被拦在哪个环节了？
① docker ps 大楼还在吗 → ② curl localhost 前台能收信吗 → ③ curl -H "Host:" https://IP 直接敲门 → ④ dig +trace 看电话簿哪页被撕了。从底往上排。
