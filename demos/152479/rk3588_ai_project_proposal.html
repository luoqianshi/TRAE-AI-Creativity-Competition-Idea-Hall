项目背景

💡 痛点：开源 Demo 好看不好用

在智能安防、边缘网关、工业视觉领域，RK3588 凭借 6TOPS NPU 算力已成为端侧 AI 设备的主流芯片。然而调研发现，市面上绝大多数 RK3588 AI 开源项目存在三大通病：

问题具体表现后果
单路为主大多只实现单路采集+推理最简链路无法直接用于多路并发场景
CPU 依赖预处理用 OpenCV 软运算，RGA 硬件加速闲置资源浪费、帧率低、功耗高
Demo 级别无线程安全、无内存管理、无异常恢复跑几小时就内存溢出、进程崩溃
一句话总结：能跑，但跑不久、跑不稳、跑不多，离量产落地差得远。

🎯 机会：缺一套"拿过来就能用"的工程方案

嵌入式 AI 开发者、小型安防团队、高校科研团队都在苦苦寻找一套完整、稳定、可复用的 RK3588 多路 AI 视觉工程模板。与其每个人都从零开始踩坑，不如做一套开源的、工程化的参考实现。

⚡ 全链路硬件加速

  • 采集：OV5695 MIPI + V4L2，零 CPU 占用
  • 预处理：RGA 硬件缩放/裁剪/格式转换
  • 推理：RKNN + NPU，单帧 ~7-9ms
  • OSD：RGA 图层混合，硬件叠加
  • 显示：MIPI DSI 直接输出
目标：4 路并发时 CPU 占用 ≤ 20%

🔄 多线程流水线

  • 每路视频独立流水线
  • 采集 → 预处理 → 推理 → 后处理 → OSD → 显示
  • 生产者-消费者模式 + 环形帧缓存队列
  • 线程优先级动态调度
  • 智能帧丢弃策略，避免堆积

💾 内存池化管理

  • 预分配固定大小帧内存池
  • 运行期零 malloc/free
  • 帧引用计数，多模块共享
  • 句柄统一管理，异常不泄漏
  • 从根源杜绝内存碎片

🚨 告警闭环

  • 区域入侵：自定义多边形警戒区
  • 跟踪去重：ByteTrack 抑制重复告警
  • 本地可视化：红框 + 告警文字
  • 本地存证：自动截图 + 日志记录
  • 远程上报：MQTT 推送告警事件

风险与应对

风险概率影响应对策略
DDR 带宽竞争，帧堆积/花屏高中先单路打通再逐步加路；分层打印时延日志
RGA 格式对齐/色彩转换问题中中优先验证 NV12/RGB 常用格式，减少转换次数
OV5695 驱动兼容性低高Day 1 优先验证，备选 USB 摄像头替代
ByteTrack 多路 CPU 负载过高中低降低跟踪帧更新频率，简化特征匹配
