第一章 · 项目概述与设计理念

传统的慈善系统往往只关注"钱去哪了"，而本系统将其升级为"钱变成了什么"。通过原子化追踪、全生命周期覆盖和信任可视化，让每一位捐赠者看到的不是冷冰冰的报表，而是受助者的真实改变。

🎯 三大核心设计原则
原则内涵对标行业实践
原子化追踪 资金流转最小颗粒度为 0.01 元，每一分钱在入账瞬间绑定全局唯一追溯码（UTC），形成不可篡改的数字身份链 Endaoment 每笔捐赠触发 EntityDonationReceived 链上事件
全生命周期 覆盖 捐赠 → 归集 → 立项 → 采购/执行 → 验收 → 反馈 六大环节，无盲区、无断点 Giveth Impact Graph 全链路可查询
信任可视化 用数据讲故事 — 将资金流转映射为实物（米、书、药品）和人的改变（孩子的午餐、减少的碳排放），形成情感闭环 GiveDirectly 情境化 AI 叙事

设计哲学：从"资金流向"到"价值闭环"

系统不仅仅是财务工具，而是信任基础设施。每一个 0.01 元的轨迹都在向捐赠者、监管方和公众回答三个问题：钱从哪来、变成了什么、改变了谁。

💡 设计决策：本方案参考了 Endaoment 的链上透明模型、Giveth 的去中心化验证机制、Gitcoin 的二次方融资算法以及 GiveDirectly 的 84.8% 资金效率实践，但针对中国慈善监管环境进行了本土化适配（联盟链替代公链、三单匹配替代纯链上验证）。

第二章 · 核心业务架构设计

系统采用三层架构：自底向上的资金归集与身份绑定层、中层的项目执行与成本分摊层、顶层的全链路可视化引擎。

01

资金归集与身份绑定层 Layer 1

子模块核心能力关键设计
捐赠即时打标 任意金额入账瞬间生成全局唯一追溯码 UTC = {date_hash(8) + donor_id(6) + sequence(6) + checksum(4)}，UUID v7 格式，内嵌时间戳实现按时间分片查询
资金池策略 定向资金（专款专用，物理隔离）+ 非定向资金（统筹使用，逻辑隔离）混合管理 每个项目维护独立虚拟账户，非定向池按配置比例自动分配，支持实时调整分配权重
利息与增值处理 自动计算在账期间利息/理财收益，按比例分配至原捐赠项目 公式：每笔分配的收益 = (该笔金额 / 池总额) × 期间总收益，低于 0.01 元则累计至下期

02

项目执行与成本分摊层 Layer 2

子模块核心能力关键设计
多级项目树 基金会 → 专项基金 → 具体项目 → 执行子项，支持无限层级 采用邻接表 + 物化路径双存储模型，兼顾灵活层级与快速子树查询

尾款处理 项目结余自动触发结转规则 三种结转策略：转入备用金池 / 转入下一个同类项目 / 原路退还捐赠人（需满足最小金额阈值）

第三章 · 细化业务流程图

以下为系统六大核心业务流程的逐步细化设计，每步标注角色、触发条件、动作、数据流、校验规则、异常处理。

3.1 捐赠与身份绑定流程

从捐赠人发起捐赠到资金完成身份绑定并入池的全链路。

步骤角色触发动作数据流校验异常处理
1.1 捐赠人 点击"我要捐赠" 选择金额、支付方式、可选指定项目 捐赠表单 → 支付网关 指定项目存在且未满额？金额 ≥ 最低限额？ 项目已满额 → 推荐同类项目或转为非定向
1.2 系统 支付网关回调确认 生成全局唯一追溯码 UTC，写入资金账本 支付回执 + UTC → 资金池 DB Payment Nonce 防重？交易 ID 唯一性？ 支付失败 → 记录错误日志，触发退款流程
1.3 系统 UTC 生成完毕 分类：定向 → 锁定到具体项目虚拟账户；非定向 → 进入通用池等待分配 分类元数据 → 分配引擎 项目预算上限？池分配比例有效？ 定向项目已满 → 提示捐赠人换选或转非定向
1.4 系统 会计期末（日/月） 计算池资金利息/理财收益，按公式按比例分配至每笔 UTC 池收益数据 → 按比例计算器 APY 乘数正确？最小分配阈值？ 收益低于阈值 → 累计至下期；收益率数据缺失 → 沿用上期保守值
1.5 系统 收益分配完成 向每笔 UTC 账本追加收益事件；更新捐赠人"慈善账单"余额 UTC_Earning_Event → 捐赠人账本 链完整校验：sum(分配收益) == 池总收益（容差 0.01%） 不匹配 > 0.01% → 冻结池，告警财务审计
1.6 基金会财务 月度对账 批量审计：UTC 账本 vs 银行对账单，签字确认 UTC Ledger + 银行 CSV → 审计报告 每笔 UTC 对应一笔已确认支付，无孤零 UTC 发现孤零 UTC → 启动人工调查流程
⏱️ 支付超时处理：UTC 已生成但 30 分钟内未收到支付确认 → UTC 作废回收，捐赠人收到新支付链接。银行退款/冲正 → 系统创建负向 UTC 条目关联原始 UTC，捐赠人账单显示退款行。

3.2 项目执行与成本分摊流程

从项目立项到成本分摊、尾款处理的全生命周期管理。

步骤角色触发动作数据流校验异常处理
2.1 基金会 新项目获批 在项目树中创建节点，设定预算上限、时间线、分摊规则 项目元数据 → 项目树 DB 父节点存在？预算 ≤ 父节点未分配上限？ 预算超父节点 → 拒绝并显示超限原因
2.2 执行方 里程碑达成 / 需采购 提交费用申领，含明细行、发票、UTC 消耗申请 费用申领表 → 成本引擎 行项目在已批准预算中？UTC 余额充足？ UTC 不足 → 请求从上级节点或池中调配
2.3 系统 费用申领提交 直接成本：从项目 UTC 中扣减。间接成本：按分摊规则自动计算（人头比/时间比/面积比） 成本分配器 → 多级账本 分摊规则有效？总间接费比 ≤ 上限（默认 15%）？ 间接费超上限 → 拒绝申领，标记审计
2.4 审计 成本分配记录 审核申领文档、GPS 水印照片、AI 发票验证结果 申领 + 证据包 → 审计队列 发票 OCR 与申领金额一致？GPS 在项目地址围栏内？ 不一致 → 退回执行方并附差异报告；三次退回自动升级
2.5 系统 项目/财期结束 计算尾款：sum(已分配 UTC) – sum(实际消耗)。正数按结转规则重新分配 尾款计算器 → 重分配引擎 重分配规则文件读取成功？ 无规则 → 默认退回非定向池
2.6 基金会 尾款重分配完成 批准项目结项报告；归档项目树 结项报告 → 归档 DB 所有子项目已关闭？所有 UTC 已消耗或重分配？ 有未结行项 → 阻止关闭，通知执行方
⚡ 预算熔断机制

当子项支出达到预算 90%，系统向执行方 + 基金会发送黄色预警。达到 95% 自动冻结该子项所有支付，仅基金会总监级可手动解锁或追加预算。达到 100% 后任何新申领直接拒绝。

3.3 "一分钱之旅"全链路追溯流程（12 步）

这是系统的核心体验——当捐赠人点击一笔具体交易时，系统如何从数据库逐层解析，最终呈现完整的故事版。

捐赠入账 → 资金归集 → 项目分配 → 采购下单 → 物流运输 → 签收确认 → 反馈闭环
#角色触发动作数据查询校验异常
3.5捐赠人点击某笔捐赠（如"¥100 · 2026-03-15"） 前端发出 GET /api/trace/{traceCode} traceCode → API Gateway → AuthZ 校验 Token 有效？捐赠人拥有该 traceCode？ traceCode 无效 → 404 + "该记录不在追溯链中"
3.6追溯服务收到有效 traceCode 查询资金层账本（按月分区 PostgreSQL 表） SELECT * FROM fund_ledger WHERE trace_code = :code 资金状态 ≥ ALLOCATED？若仍为 POOLED → 停止 未分配 → 返回"您的资金仍在资金池中等待项目分配，预计等待 X 天"
3.7追溯服务资金记录解析 查询成本分摊引擎：该笔资金被拆分到哪些项目节点 SELECT * FROM cost_splits WHERE fund_id = :id + JOIN project_tree sum(split_amounts) == original_amount（容差 0.01） 拆分不匹配 → 标记对账标志 + "成本分摊对账中，N% 可追溯"
3.8追溯服务项目节点解析 查询采购/订单账本：该笔资金实际购买了何物 SELECT * FROM purchase_orders WHERE project_node_id = :nid + JOIN order_line_items 三单匹配：PO 金额 vs 发票金额 vs 实收数量 无采购订单 → "资金已分配但尚未执行采购" + 展示预算计划作为占位
3.9追溯服务订单解析 查询物流/运输记录：物资如何从仓库到达受益人 SELECT * FROM logistics_manifest WHERE po_id = :pid + JOIN waybill_tracking 送达 GPS 在受益人注册地址 500m 围栏内？送达照片 EXIF 时间有效？ 无物流 → "已采购待发运" + 预计发运日期。GPS 异常 → "送达地点异常" + 升级合规团队
3.10追溯服务物流解析 查询签收/验收记录：谁接收并核验了物资 SELECT * FROM acceptance_records WHERE waybill_id = :wid 签名与预注册受益人 ID 匹配？照片 GPS 与送达 GPS 一致？时间戳在送达 72h 内？ 未签收 → "已送达等待受益人确认"。签名不匹配 → "身份核验中"
3.11可视化引擎全链组装完毕 构建旅程故事版：DAG 卡片链 + 交互式时间轴 所有记录聚合为 TraceJourneyDTO，渲染 SVG/Canvas 交互式时间轴 每个节点颜色编码：🟢已验证 🟡部分数据 🔴异常 ⚪未达 任何环节缺失 → 渲染至最后已知节点 + 虚线箭头 + "⏳ 等待中" 标识
3.12捐赠人可视化渲染完毕 看到完整旅程，可点击每个节点展开详情（照片、订单号、地图） TraceJourneyDTO → 前端 React 组件 — —

缺失链路的 6 种降级展示策略

缺失环节可视化表现系统动作
资金未分配实线链：捐赠人 → 资金池（⏳ 等待分配）分配后自动推送通知（预计 1-30 天）
成本拆分不匹配捐赠人 → 池 → 项目（⚠️ 对账中）后台创建合规工单，72h 内解决否则自动升级
无采购订单捐赠人 → 池 → 项目 → 预算（📋 计划中）展示已批准预算明细作为占位

GPS/签名异常→ 物流 → 送达（⚠️ 核验中）橙色高亮送达节点 + "核验中"标识；合规团队 48h 内处理
完全未签收实线至送达，虚线：送达（✅）→ （⋯ 签收待确认）7 天自动提醒执行方；30 天自动升级至基金会

3.4 条件触发支付流程（智能合约规则引擎）

以"受助学校上传食堂验收照片后，方可划拨剩余 30% 尾款"为例。

步角色触发动作数据流校验异常
4A.1规则引擎项目里程碑 Phase1_Complete 触发 将 30% 余额锁定在托管子账户；创建 EscrowCondition 记录（类型 PHOTO_ACCEPTANCE） INSERT INTO escrow_conditions (project_id, amount, condition_type, status='HELD', deadline) 已释放总额 ≤ 预算 70%？条件类型已注册？ 已释放 → 幂等返回 ALREADY_RELEASED
4A.2学校管理员 App 中看到待办"提交食堂验收照片" 使用 App 内置相机拍摄 3+ 张照片（正面/左侧/右侧），自动嵌入 GPS + 时间水印 照片（含 EXIF GPS）→ POST /api/evidence/acceptance 最少 3 张、每张 ≤ 10MB、GPS 已开启、EXIF 完整。GPS 在学校注册地址 200m 内 GPS 关闭 → App 阻止提交。光线不足/模糊 → AI 质检警告"照片过暗，请重新拍摄"
4A.3AI 核验引擎 验收照片上传完毕 运行计算机视觉管线：(a) YOLOv8 检测食堂场景，(b) GPS 一致性交叉校验，(c) 屏幕翻拍检测 视觉模型 → confidence_score (0-100)；OCR 提取画面文字 confidence ≥ 80% → 自动通过。50-79% → 人工审核队列。<50% → 自动拒绝 自动拒绝 → 通知学校具体原因（"未检测到食堂场景——请包含餐桌/打饭窗口"）
4A.4基金会审核员 confidence 50-79% 入人工队列 人工查看照片、GPS 坐标、AI 标注，做出通过/退回判断 审核决定 + 备注 → escrow_conditions 审核员有中级以上权限？ 退回 → 学校收到具体改进指引
4A.5规则引擎 条件满足（自动通过 或 人工批准） 释放托管金额到执行方账户；记录释放事件到 UTC 链 escrow_conditions.status → RELEASED；资金划拨 → 执行方虚拟账户 释放金额 == 托管金额？ 超时未满足 → 到期前 7 天提醒，到期后自动升级至基金会总监

3.5 多维反馈与证据链流程

步角色触发动作数据流校验异常
5.1执行方项目里程碑完成 打开结构化反馈表单（拒绝纯文本），上传：发放名单 Excel、GPS 水印照片、受助人签字板/指纹数据 结构化数据包 → POST /api/feedback/submit 所有必填字段已填？照片含 GPS？Excel 格式符合模板？ 必填字段缺失 → 拒绝提交，红色标记缺失项
5.2AI 审核引擎 反馈包提交 (a) 发票 OCR 提取金额/日期/抬头；(b) 图像识别验证发票真伪（防篡改检测）；(c) 交叉核对签收名单与发放金额 OCR 结果 + CV 结果 → 审核报告 OCR 金额 == 申领金额？发票未被 PS？签收人数 × 单人金额 == 总发放？ 不一致 → 标记差异行，生成差异报告
5.3基金会审核员 AI 审核报告异常 人工复核差异项，决定通过/退回/要求补充 审核决定 → 反馈记录 — 三次退回 → 项目冻结，启动全面审计
5.4系统 反馈审核通过 将证据包哈希写入 UTC 链（存证不存数据），更新可视化引擎中的签收节点为"已验证" evidence_hash → UTC 链；节点状态 → VERIFIED 哈希写入成功？ 哈希写入失败 → 重试 3 次，失败则记录异常日志

第四章 · 交互设计详案

4.1 信息架构与三端功能地图

系统面向三类用户，提供差异化界面：

端用户角色核心功能设备倾向
公众端 捐赠人 / 社会公众 捐赠、慈善账单、一分钱之旅、影响力计算器、项目浏览 Mobile First（微信 H5 / 小程序）
执行端 项目执行方 / 学校 / 供应商 费用申领、反馈提交、结构化拍照、任务看板 Mobile App（离线能力优先）

7.2 审计接口

预留外部审计机构的"只读探针"：

  • 基于角色的访问控制（RBAC），审计角色拥有所有 UTC 账本的只读权限
  • 支持导出符合 《民间非营利组织会计制度》 的标准化审计底稿（Excel/CSV）
  • 所有数据变更记录在 audit_log 表（不可删除，仅追加），含操作人、时间戳、变更前后快照
  • 区块链存证层可作为独立证据提供给外部审计，验证数据未被篡改

· 激励机制：执行方上传速度和完整度计入信用评分，高信用执行方可享更快的资金拨付周期

· 设置行政分摊上限（默认 15%，可配置），超标自动熔断
· 参考 GiveDirectly 实践：公开三路成本分解，建立行业透明度标杆
· 增设"管理费用捐赠专项"，让有意的捐赠人专门捐赠管理费
3 历史数据清洗：旧项目的烂账如何处理？ 新老划断策略：
· 设定明确的切换日期，新系统只跑新逻辑
· 旧数据做只读归档展示，页面标注"历史数据·未经精细化追溯"
· 提供数据迁移工具，允许对核心旧项目手动补录关键节点（但标注"补录"标识）
4 区块链上链成本：每笔 0.01 元都上链 Gas 费不可承受 · 采用"存证不存数据"策略：仅将 UTC 哈希 + evidence_hash 上链，原始数据存于链下数据库
· 使用联盟链（FISCO BCOS / Hyperledger Fabric）而非公链，无 Gas 费
· 批量上链：每小时聚合一批 UTC 的默克尔根上链一次
5 AI 审核的误判风险：计算机视觉可能误判照片场景和发票真伪 · 设置置信度三级分流：≥80% 自动通过，50-79% 人工复核，<50% 自动拒绝
· 建立人工反馈闭环：人工复核的结果回灌训练集，持续提升模型精度
· AI 审核结果始终标记为"AI 辅助"，最终责任仍在人工审核员
6 执行方数字化能力不足：偏远地区执行方可能缺乏智能设备和网络 · 执行端 App 支持离线模式：无网络环境下拍照、填表，恢复网络后自动同步
· 提供极简模式：针对低端设备优化（APK ≤ 15MB，支持 Android 6+）
· 允许替代方案：无法使用 App 的执行方可邮寄纸质材料，由基金会工作人员代为录入（标注"代录入"）
