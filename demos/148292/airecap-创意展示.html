WHY · 02

真正流失的，不是聊天记录，而是判断过程。

一次 AI 编程会话里，目标、试错、文件修改和测试结果彼此交错。任务完成并不等于学习完成。

看见结果，看不见依据

代码已经能运行，但用户不清楚为什么选择这一方案，也不知道哪些替代方案被放弃。

讨论过，不代表真正做过

长对话里有大量计划和建议。若不核对文件变更与测试结果，复盘很容易把设想写成成果。

同样的问题，下次仍然重来

没有结构化归档，Prompt 的歧义、有效判断和技术边界不会沉淀为可复用的个人经验。

PIPELINE · 03

旁路观察，不打断原来的工作流。

产品本体是一套 Python CLI、Codex/Claude Skill 与本地归档机制。用户照常编程，复盘发生在任务结束之后。

01 CAPTURE

发现会话

从 Codex 或 Claude Code 的本地会话目录读取公开消息、工具操作和错误。

02 SANITIZE

先做脱敏

遮盖密钥、认证头、密码、凭据 URL 与用户主目录，再进入生成环节。

03 EVIDENCE

核对证据

区分用户请求、真实文件变更、失败操作与成功测试，拒绝无依据结论。

04 RECAP

生成与归档

宿主模型按固定结构生成复盘，通过本地校验后写入 Markdown 与长期记忆。

这次做成了什么

标题不再照搬第一条消息，而是扫描整段对话后概括核心目标与最终结果；README 同时补齐了小白模式切换方法。

关键决策是怎么定的

公开标题、归档标题和历史记录必须使用同一字段，否则用户会在不同入口看到互相矛盾的名称。

AI 的计划方案

  • 先把 title 加入生成契约，再统一终端、Markdown、JSON 与数据库入口。
  • 保留会话编号作为文件名，避免中文或特殊字符影响跨平台打开。

你的 Prompt 写得怎么样

“标题改为对话内容的总结”目标明确，但若补充“终端、归档、历史记录都要一致”会减少实现边界的猜测。

用到的技术：如何复用与底层原理

单一数据源意味着所有公开格式都从同一个 title 字段读取。这样修改命名规则时，只需调整生成入口，不必在每个渲染器里分别猜测。
