PART 01

想解决什么问题

绝大多数中小团队到今天仍然不做性能压测——不是不想做，是根本做不动。

✕

脚本门槛极高。登录返回的 token 要传给下一个请求，得用"正则表达式提取器"写正则 "token":"(.*?)" 或 JSONPath，配引用名、匹配数字、默认值——新手写这个正则能卡一下午。

✕

插件 / Listener 是概念灾难。查看结果树、聚合报告、聚合图、Backend Listener、Response Time Graph……十几种监听器，新手根本不知道用哪个，乱开 Listener 反而会反过来拖慢压测。

✕

施压机配置是玄学。最致命的是"施压机自己先成为瓶颈"——社区实测过分布式比单机还慢，测出来的其实是施压机的极限而不是被测系统的极限，结论完全失真。

✕

压测很危险。压力给大了会压挂测试环境甚至误压生产，全程得有专人死盯监控手动停止，简单静态阈值又会误杀（负载测试本来就要测到错误来找拐点）。

✕

瓶颈分析靠老师傅。压完一堆曲线（TPS、RT、错误率、CPU、GC、慢查询），对着图看出问题——这是高级性能工程师的核心能力，普通人完全不具备。

✕

报告丑且难懂。JMeter 原生报告晦涩，老板和业务方看不懂，沟通成本极高。

结果：大量系统"裸奔上线"，大促或流量高峰一来就崩，每一次故障都是几十上百万损失。

PART 02

为什么会想到做这个

调研后发现，行业里其实已经有大量压测工具——JMeter（老牌但难用）、k6（现代但脚本还得手写）、MeterSphere / RunnerGo（开源平台，本质还是把 JMeter 包了个 Web UI，脚本还是要你自己写）。

所有这些工具解决的都是"工具"问题，没有解决"门槛"和"安全"问题——它们都默认使用者已经是个懂行的性能工程师了。

而真正缺性能工程师的，恰恰是占绝大多数的中小团队（专业性能测试工程师年薪 30-80 万，还稀缺）。AI 大模型 + 代码生成的成熟，让我们有机会跳过"教人学会 JMeter"这条路，直接 让 AI 当那个性能工程师——它来理解需求、写脚本、配施压机、盯监控、调熔断、看曲线、出报告。

这是一个"AI 写代码 + 调度真实压测引擎 + 采监控 + 智能决策"的全栈工程产品，正是 TRAE 的主场，绝不是建个对话 agent 就能替代的（豆包 agent 给不了你真实并发、给不了施压机调度、给不了实时熔断、给不了可视化报告）。

PART 03

三大核心 AI 能力

不是套个对话框，而是三个需要写大量代码才能实现的专业能力。

创新点 1

AI 自动写脚本：开始 → 过程 → 结果全链路

打掉 JMeter 那套让人懵的插件体系（正则提取器 / BeanShell / Listener 选择困难）。AI 把整个流程自动跑通：

始

开始：需求输入与解析

自然语言 / Swagger / Postman / curl / HAR 录制 → AI 识别业务链路（登录→下单→支付整条链）、识别接口依赖、输出结构化的"压测场景规格"

中

过程：脚本生成

自动处理关联（提 token，不用写正则）、参数化（批量用户数据）、动态逻辑（签名/加密直接写代码，不碰 BeanShell）、断言（状态码+业务字段+RT 三层）、思考时间；自动选对 Listener 策略（默认 Backend Listener 推时序库，不开吃资源的 GUI Listener）

终

结果：脚本自检与自修复

单线程试跑验证逻辑，失败自动定位原因（关联没提到值？断言写错？数据源不对？）并 AI 自动修复，而不是甩给用户一堆报错。试跑通过才进入正式压测。

创新点 2

结合机器情况，自动推荐施压机配置

解决性能测试里最隐蔽、最致命的坑——施压机自己先成为瓶颈，得出错误结论。目前几乎没有工具能自动解决。

①目标评估

根据目标并发/TPS、接口复杂度、链路长度，估算需要发出的总压力（RPS）。

②施压机能力探测

先让单台施压机跑基准测试，实测该机型真实发压上限（每秒能发多少请求、自身资源占用曲线、多少线程时开始吃紧）。

③智能计算配置

所需施压机数 = 目标总 RPS ÷ 单机安全发压能力（留余量）；自动给出每台线程分配、JVM 配置、带宽校验、分布式拓扑建议。

④施压机自监控 + 结论可信度

压测全程监控每台施压机 CPU/内存/网络。施压机先扛不住时，报告明确标注"本次测的是施压机极限，被测系统真实能力未知"，不给你误导性数字。

创新点 3

自动识别问题并智能停止 + AI 瓶颈定位

压测安全的生命线。不是简单的静态阈值（错误率>5% 就停），而是多指标趋势识别 + 分级响应：

●软告警

RT 缓慢漂移等异常苗头 → 记录但继续（稳定性测试需要观察的趋势，不能停）。

●降级

压力接近风险线 → 自动降低压力继续观察。

●硬熔断

错误率突增 + RT 飙升 + 资源打满 → 立即全停并保留现场快照，避免压垮系统。

●AI 根因定位

不是"建议优化代码"这种废话，而是 "连接池 max=20 耗尽 + 慢查询集中在 order 表索引缺失，建议加索引并验证"。

完整工作流程

0

1

AI 生成脚本 ★创新点1

自动推荐施压机 ★创新点2

基准探测单机能力 → 算施压机数量/分布/JVM → 带宽校验 → 全程施压机自监控

分层压测 + 智能熔断 ★创新点3

基准测试 → 负载测试（找拐点）→ 稳定性压测（查泄漏）→ 容量测试（验目标 TPS）；全程智能熔断保现场

4

全链路监控采集

应用层（TPS/RT/错误率）+ 资源层（CPU/内存/GC）+ 中间件层（慢查询/连接池/MQ/Redis）

5

AI 瓶颈定位 + 根因分析

时序关联 + 模式识别 + 可执行优化建议

6

可视化报告

含施压机健康度、结论可信度标注，老板能看懂

大压测 / 小压测自动适配：基准测试（建基线）、负载测试（找拐点）、稳定性压测（查泄漏）、容量测试（验大促）、全链路压测（流量染色+影子库，对标字节 Rhino / 美团 Quake）。AI 根据用户场景自动推荐组合，不让用户自己选。
