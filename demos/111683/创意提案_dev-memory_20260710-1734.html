1创意介绍

为什么我们需要一个"项目级"的 AI 记忆系统

核心洞察：AI 行业发展至今，已经有针对"用户"的记忆系统（如 ChatGPT 的 Memory），也有针对"Agent 工具"的记忆系统（如 Claude Code 的 CLAUDE.md、Hermes Agent 的四层记忆）。但始终缺失一环——针对"项目和设备"的记忆系统。而恰恰只有项目代码和本地设备，才是开发者真正拥有、不会因外部因素而失去的资产。

想解决的问题

用 AI 编程助手开发项目时，每一轮对话都会积累大量隐性知识：为什么选了这个方案、踩过什么坑、API 参数怎么调对、架构上做了哪些取舍。但这些知识存在对话上下文里，对话一结束就蒸发了。下次开新对话，AI 两眼一抹黑，你刚解决过的坑它再踩一遍，你刚论证过的方案它再质疑一圈。算力在重复探索中白白消耗，开发节奏被反复打断。

更深层的问题在于，现有的记忆方案全部绑定在某个特定载体上——要么绑账号（ChatGPT Memory 跟着 OpenAI 账号走），要么绑工具（Claude Code 的 CLAUDE.md 离开 Claude Code 就没人读）。可现实是，AI 行业产品迭代极快，今天用的工具明天可能就变了，账号也可能因为各种原因需要切换。我自己就经常在多个 AI 编程工具和账号之间来回切换。工具和账号都是流动的，只有本地设备和项目代码是真正稳定的锚点。

动机与灵感

这个想法来自一个很具体的痛点。我在用 AI 助手开发一个数据分析项目时，前一轮对话刚花了不少时间排查一个第三方 API 的参数问题，终于找到了正确的调用方式。结果下一轮新对话，AI 又从头试错，把走通的路重走了一遍。那一刻我意识到，AI 缺的不是能力，是记忆。

我开始研究现有的记忆方案，发现一个有意思的现象：记忆系统在 AI 领域并不新鲜，但所有人都在往"更高层"做——用户层的个性化记忆、Agent 层的技能积累。没人往下看一层：项目本身需要什么记忆？那些跟着代码走、不跟账号走、不跟工具走的记忆，应该放在哪里？答案其实很简单——放在项目目录里，用最朴素的 Markdown 文件，跟着 Git 一起版本管理。

2AI 记忆的历史脉络

从用户记忆到 Agent 记忆，缺的恰恰是项目记忆

2023 — 2024

用户级记忆：记住"你是谁"

ChatGPT 率先推出 Memory 功能，记住用户的偏好、习惯、背景信息。这类记忆绑在用户账号上，跨对话生效，但换个平台就没了。它解决的是"AI 了解你"的问题，不解决"AI 了解你的项目"的问题。

2025 — 2026 初

Agent 级记忆：记住"怎么干活"

Claude Code 推出 CLAUDE.md 和 Auto Memory，把构建命令、代码习惯、架构约定存在项目目录里。Hermes Agent 更进一步，搞了四层自进化记忆体系——运行时技能积累、系统级优化、模型级训练，号称"越用越聪明"。但这些记忆要么锁死在特定工具里，要么需要重型框架支撑。

2026 · dev-memory

项目级记忆：记住"这个项目经历了什么"

把记忆的归属权从账号和工具上拿下来，放到项目和设备这一层。记忆文件住在项目目录里，跟着代码走，不绑任何平台。任何 AI 工具来了都能读，工具换了记忆还在。同时借鉴 Hermes 的自我进化思路，让 Skill 自身也能迭代——但用最轻量的方式实现，不需要框架，不需要运行时，一个 Markdown 文件搞定。

三层记忆的互补关系：用户级记忆解决"AI 认识你"，Agent 级记忆解决"AI 会干活"，项目级记忆解决"AI 懂这个项目的来龙去脉"。三者不冲突，但项目级记忆是目前缺失的那一环——而且是最稳定、最该被沉淀的那一环。

3为什么是现在

AI 工具快速迭代的时代，稳定性反而成了稀缺品

🔄

工具在变

AI 编程领域半年一个格局。今天的主力工具，半年后可能就被替代了。绑在特定工具上的记忆，工具一换就归零。开发者需要的是工具无关的记忆载体。

👤

账号在变

且不说多平台切换的常态，单是国内开发者面临的访问限制就够头疼了。某些海外工具对中国用户区别对待已经不是秘密——近期 Claude Code 被曝出在代码中植入针对中国用户的隐蔽检测逻辑，这件事让很多人意识到，把记忆托管给特定平台是有风险的。

💻

设备和项目不变

不管外部环境怎么变，你的电脑还在，你的项目代码还在。把记忆放在项目目录里，就是放在了最稳定的锚点上。这是开发者真正"拥有"的东西。

📦

轻量即可移植

不需要数据库，不需要服务端，不需要 API。几个 Markdown 文件，打了个包就能带走。新项目复制一份 SKILL.md 就能启用。可移植性不是设计出来的，是"没什么不能移植"。

现实背景：2026 年 7 月，Claude Code 被安全研究者逆向分析后发现，其客户端代码中包含针对中国用户、中国代理网络和中国 AI 公司环境的隐蔽检测与标记逻辑。这意味着依赖单一海外工具的记忆体系存在不可控风险。dev-memory 的价值在于：记忆归你所有，存在你的项目里，不经过任何第三方。

一个 Skill，融合两种范式的长处

dev-memory 不是从零发明的东西。它站在两个已有的成熟方案肩上，取其精华，去其重量。

dev-memory

取 Claude Code 的"项目目录存储 + 自动维护"，取 Hermes 的"自我进化 + 迭代记录"，用纯 Markdown Skill 实现，不绑任何工具。

项目级 自动维护 自我进化 工具无关
关键区别：Claude Code 的记忆是"工具的功能"，dev-memory 的记忆是"项目的资产"。前者服务于工具，后者服务于项目本身。工具可以换，但项目的记忆不应该跟着工具一起消失。

5六维记忆提取

每一轮对话结束后，自动从上下文中提取六个维度的开发记忆

①

任务与变更摘要

这轮对话具体做了什么。1-3 句话概括，不啰嗦但能让人（或 AI）快速回忆起上下文。

②

踩坑记录

遇到什么错误、根因是什么、怎么修的。标注已解决或未解决。这是最省算力的一维——不再重复踩同一个坑。

③

探索路径

试了哪些方案、为什么放弃、最终选了什么。记录"不走的路"和"为什么不走"，避免下次又绕进去。

④

最终结论与最佳实践

当前验证有效的结论。比如某个 API 的正确参数、某个配置的最佳值。直接可用，不用再查。

⑤

架构决策记录

为什么选这个方案、放弃了什么、影响范围。防止"这个为什么这么写"的灵魂拷问在三个月后无人能答。

⑥

环境与依赖信息

工具版本、API 变更、配置调整。环境一变就能对上号，不用猜"上次是什么版本"。

6追加式演进与自我进化

旧记忆不删除，新认知追加更正，Skill 自身也在迭代

追加式演进：记忆的"版本控制"

开发认知是会迭代的——上周觉得对的参数，这周发现更好的。dev-memory 的做法是：旧记忆原封不动保留，新认知以"更正记录"的形式追加在后面。这和 Git 的版本管理思路一脉相承：你不删历史 commit，而是在上面叠新的。这样既保留了认知演进的过程（本身就有价值），又确保最新结论总是清晰的。

# 历史更正记录 [2026-07-10 16:30 更正] 旧记忆"依赖第三方Token获取数据" → 更正: "可直接用公共API获取，无需Token" # 旧记忆不删，更正追加在后

自我进化：Skill 也能迭代自己

这一点借鉴了 Hermes Agent 的进化飞轮思路，但做得极轻。Hermes 的进化分三层：运行时技能积累、系统级 DSPy/GEPA 优化、模型级 RL 训练——强大但重，需要完整框架支撑。dev-memory 只取最外层那一点：每次执行完后回头检查，这次有没有遇到六维覆盖不了的信息？归档逻辑有没有边界情况没处理？如果有，直接在 SKILL.md 的迭代记录区域追加一条改进说明，版本号递增。

不需要训练模型，不需要优化框架，不需要额外算力。就是 AI 在每次执行后多想一步："刚才有没有什么情况我没处理好？"有的话记下来，下次改进。这和人类工程师做完一件事后的 retro（复盘）是同一个道理——简单，但有效。

## 迭代记录 ### v1.0 — [2026-07-10 17:19] 初始版本 - 六维记忆提取 + 按周归档 + 追加式更正 ### v1.1 — [2026-07-12 09:30] 改进说明 - 触发原因: 发现环境信息维度经常遗漏依赖版本 - 改进内容: 在提取规则中增加"检查 package.json/requirements.txt 变更" - 影响范围: Step 2 环境信息提取逻辑

9目标用户与价值

谁需要它，为什么需要

面向谁

所有使用 AI 编程助手（TRAE、Cursor、Copilot 等）进行项目开发的开发者。尤其是经常在多个工具和账号间切换、重视数据主权、希望项目知识可传承的人。

使用场景

项目开发全生命周期。多轮对话之间传递上下文、多人协作时传递项目历史、工具切换时保持记忆连续、项目交接时完整交付知识。

效率价值

消除"AI 重复探索已解决问题"的算力浪费。实测中，仅"避免重复踩坑"一项就能在复杂项目中节省 20%+ 的对话轮次。新对话开局 AI 先读记忆文件，直接跳过已验证的结论。

战略价值

在 AI 工具快速迭代、平台政策不确定的环境下，为开发者提供一个稳定的、可移植的、不受外部因素影响的记忆资产层。记忆归你所有，不归任何平台。
