01 · INDUSTRY PAIN

造数据，是后端工程师最脏最累的活。

每一次联调、每一条冒烟、每一份回归报告的背后，都藏着一段不为人知的造数地狱。
🎯

效率低

手写 Python mock 脚本，每张表一个循环，半天没了。还要去应付外键、时间戳、自增 ID 的琐碎细节。

🧩

跨表不一致

FK 孤儿、金额不守恒、时序错位。订单表里的 user_id 在 users 里不存在；支付金额跟订单金额永远差两块钱。

🎲

不真实

纯随机数没有客单价分布、没有会员优惠逻辑。造出来的订单 "1970-01-01" 发货、客单价 ±10 元均匀分布，跑起来像个笑话。

02 · PRODUCT DEFINITION

两个入口，一条流水线

不管你手里有 Schema、有 JSON 样例、还是只有一句大白话 —— DataForge 都能接住。
入口 A · 有 Schema

上传 SQL / 粘 JSON Schema / 贴一条真实 JSON 样例

支持 DDL、Protobuf、OpenAPI Schema、任意一条真实响应样本。我们自动抽取字段类型、约束、枚举、外键关系，5 秒出 ER 图。

一句话描述业务

统一输出：ER 图可视化 + 语义化数据 + 一致性校验 + 5 种格式一键打包（CSV / SQL / JSON / Parquet / Kafka）

04 · CORE ARCHITECTURE

ER 推断 + AI 编排 + Faker 底座 + 规则引擎

四阶段流水线：LLM 负责"想明白"，Python 负责"造对了"。
STAGE 1 意图解析

LLM 从自然语言抽取规模、时间窗、业务规则

INPUT: "电商 30天 500用户" OUT: {"domain":"ecom","users":500,"days":30}
STAGE 2 Schema 推断

LLM 推断表结构、主键、外键、ER 关系 + seed_hint

OUT: {"users":{...},"orders":{"fk":"user_id"}}
STAGE 3 语义增强

LLM 为每个字段生成分布策略、枚举、业务约束

OUT: {"amount":{"dist":"lognorm","mu":4.6,"s":0.7}}
STAGE 4 规则引擎

Python + Faker：拓扑排序 → 逐表造数 → 一致性校验

OUT: CSV/SQL/JSON/Parquet/Kafka

数据导出 · 5 种格式一键打包

底层使用同一套 JSON 中间格式，导出器按需转换，无需重新造数。

📄CSV
🗄️SQL (MySQL / PG / SQLite)
🧾JSON
🐦Parquet
📡Kafka (JSON / Avro)
