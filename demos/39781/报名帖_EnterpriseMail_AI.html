EnterpriseMail AI 调度中枢

让企业邮件自己跑腿

1 创意名称 & 创意介绍
创意名称
EnterpriseMail AI 调度中枢 ——让企业邮件自己跑腿
想解决什么问题

传统跨境工厂型企业每天处理大量客户邮件，回复质量依赖员工经验，容易遗漏、回复慢、口径不统一。

现有AI写作工具只能辅助生成内容，无法真正代替人去做判断和对接系统，而打通邮件与内部系统的成本又极高，碎片化集成让很多项目烂尾。

为什么会想到做这个

看到很多企业花大价钱上RPA、WMS系统，但邮件这个最核心的对外入口反而还是纯人工处理。

问题根源不在技术能力，而在集成思路——每家企业系统版本、定制深度、数据格式都不同，什么都接的集成商模式注定难以规模化。

所以我想：不做低效的定制集成商，而是做一套类似USB协议的标准接口规范，让企业自己来适配内部系统，平台专注做AI调度这件事。

大概是什么产品

一个部署在企业端的AI邮件调度系统，后端用Python FastAPI + LangChain，前端React，支持PGVector、Qdrant等多种向量数据库。

它不直接操作企业RPA和WMS，而是通过连接邮件系统（IMAP/SMTP）、钉钉协同工具以及企业按标准接口规范实现的内部数据适配层，以"业务协调者"角色自动完成邮件意图识别、多源信息检索、内部人员调度、回复生成与发送的全链路闭环。

技术栈
Python FastAPI LangChain React PGVector Qdrant IMAP/SMTP 钉钉 DWS
2 目标用户及痛点
面向哪些用户

有大量客户邮件需要处理的跨境工厂型企业，尤其是制造业、供应链、外贸电商等与海外客户频繁沟通的业务部门，内部通常已部署ERP、WMS等系统但各系统间数据割裂。

在什么场景下使用

客户发来询价邮件 → 系统通过IMAP自动获取并识别意图 → 检索客户历史记忆库及企业知识库 → 按标准接口向企业内部数据适配层发起查询（库存/价格/交期）→ 信息不完整时通过钉钉向生产或业务负责人发起确认并监听回复 → 汇总全部信息生成回复草稿 → 推送给对应业务员做最终确认 → 一键发送邮件。

全流程人只做确认和决策，AI负责跑腿和组装信息。
当前痛点
邮件堆积易遗漏 回复口径不统一 多系统切换繁琐 内部协调效率低

核心组件说明
  • 邮件网关（IMAP/SMTP）：基于异步IMAP长连接实时监听新邮件，支持多邮箱聚合。采用增量同步策略，已读邮件建立索引后不再重复处理，支持附件解析（PDF/Excel/图片OCR）。
  • 意图识别引擎：基于LangChain构建多阶段意图分类管道。第一阶段用轻量模型判断业务类别（询价/投诉/催单），第二阶段用大模型提取关键实体（SKU、数量、交期要求），输出结构化JSON供下游使用。
  • 向量记忆库：客户历史沟通记录按时间戳向量化存储，支持时间衰减权重。新邮件到达时自动检索该客户最近N条记录作为上下文，确保回复具备连续性和个性化。
  • 标准接口适配层：平台定义标准RESTful接口（/inventory、/price、/delivery），统一OAuth2认证、统一数据格式、统一错误码。企业内部开发一个轻量适配服务即可对接，开发成本从数月降至数天。
  • 协同调度器（钉钉 DWS）：信息缺失时自动@对应负责人，监听钉钉群/单聊回复，将人工确认结果回填到工作流上下文。支持超时升级和代班机制。
  • 人在回路审批引擎：所有AI生成回复必须经过人工确认才能发出。系统记录每次确认的时间、人员和版本，形成完整的审计链，实现责任100%可追溯。

标准接口规范设计（核心壁垒）

这套接口规范是整个产品的核心设计决策，它决定了产品能否从定制泥潭中脱身。

维度 平台侧（我们定义） 企业侧（客户实现）
接口协议 RESTful API，OpenAPI 3.0 文档 按规范暴露端点，内部转发到 WMS/ERP
认证方式 OAuth2 Client Credentials + JWT 实现令牌颁发与校验中间件
数据格式 统一JSON Schema，字段命名规范 内部数据映射到标准Schema
错误处理 标准错误码（4xx/5xx + 业务码） 内部异常转换为标准错误响应
版本演进 v1.0 → v1.1 向后兼容 按版本号适配，平滑升级
核心优势 一套平台，服务N家企业 一次适配，长期受益
关键洞察：这不是技术限制，而是商业策略。平台只认标准接口，不认具体系统。SAP、金蝶、自研ERP——对企业来说只是适配层内部的实现细节，对平台完全透明。
关键技术选型理由
  • FastAPI 而非 Flask/Django：原生支持异步IO（async/await），IMAP长连接和并发邮件处理需要高吞吐；自动生成OpenAPI文档，与"标准接口规范"的产品定位天然契合。
  • LangChain 而非裸调 LLM API：提供标准化的Chain抽象、Memory管理和工具调用（Tool Calling）机制，让意图识别→信息检索→回复生成这条链路可以模块化组装和替换。
  • PGVector + Qdrant 双支持：PGVector适合已有PostgreSQL基础设施的企业（零新增组件）；Qdrant适合对向量检索性能要求极高的场景。双选项降低客户接入门槛。
  • 钉钉 DWS 而非自建IM：企业已在使用钉钉，利用现有协同习惯零成本迁移；DWS提供标准化群机器人、卡片消息和审批接口，避免自建IM的庞大投入。
