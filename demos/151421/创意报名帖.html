一、创意名称与介绍
创意名称

MaaS 运营管理平台

想解决什么问题

企业在构建和运营 AI 能力平台时，面临"管理分散、计量不准、计费不清"的痛点。智能体、模型、插件、知识库等资源缺乏统一管理，token 消耗和费用难以追踪，缺乏统一的运营看板和告警机制。我们需要一个一站式的 MaaS 运营管理平台，实现从资源管理到计量计费的全链路管控。

为什么会想到做这个

在部署企业级 AI 能力平台（Coze Studio + OneAPI + RuoYi）时，我们发现现有工具无法满足内部精细化管理需求。于是基于 POC 验证成果，打造了这套 MaaS 运营管理平台，以计量计费为核心能力，逐步扩展到智能体中心、模型管理、资源管理等全链路运营能力。

大概是什么产品

一个基于 RuoYi-Vue + OneAPI + Prometheus 的 MaaS 运营管理平台，以计量计费为核心，覆盖智能体中心、模型管理、资源管理、数据管理等全链路运营能力。

二、目标用户及痛点
面向哪些用户
  • 企业 IT 管理员：负责平台运维和资源管理
  • AI 平台运营人员：负责客户管理和额度监控
  • 部门预算负责人：负责本部门费用控制和分摊
  • 财务人员：负责费用结算和账单管理
在什么场景下使用
  • 日常监控：IT 管理员每日查看各部门模型用量和成本报表
  • 额度预警：运营人员在额度接近 80% 阈值时收到告警通知
  • 费用结算：财务人员每月根据用量数据进行费用分摊和结算
  • 系统运维：运维人员通过 Prometheus + Grafana 实时监控服务状态
当前痛点
  • ✗无法按客户/部门维度统计模型调用费用和 token 消耗
  • ✗缺乏实时监控和预警机制，额度用完才发现
  • ✗计量数据分散在多个系统（OneAPI、OpenMeter、RuoYi），核对困难
  • ✗手动统计效率低下，容易出错
三、价值与意义
效率提升
  • 自动化计量替代人工对账，每月节省 8 小时以上 统计时间
  • Debezium CDC 实时采集，延迟从 30 秒降至 <1 秒
  • 三方自动比对（OneAPI / OpenMeter / RuoYi）确保数据一致性
商业价值
  • 精细化成本管理帮助企业控制 AI 支出，避免无效调用浪费
  • 支持企业内部自用和对外商用两条路线的灵活切换
  • 可扩展 Kill Bill 实现订阅/阶梯计价/账单/发票等商用计费能力
四、核心功能设计
4.1 客户管理
  • 客户台账管理，支持客户信息录入和维护
  • OneAPI 用户与客户的映射关系管理
  • 客户额度配置和计费单价设置
4.2 用量看板
  • 月度汇总统计（调用次数、Token 消耗、费用金额）
  • 按客户/部门/模型维度的用量明细
  • 实时用量曲线和趋势分析
4.3 额度告警
  • 额度使用率 80% 阈值告警
  • 多渠道告警通知（系统消息）
  • 告警记录管理和处理状态追踪
4.4 自动化任务
  • 每 5 分钟增量同步 OneAPI 用量数据
  • 三方数据自动比对和不一致告警
  • 月度报表自动生成

六、关键决策
6.1 数据一致性
  • 基准来源：以 OneAPI 为准（原始调用数据最权威）
  • 比对机制：三方自动比对（OneAPI / OpenMeter / RuoYi）
  • 差异处理：系统自动从时间窗口和过滤条件两个维度排查不一致原因
6.2 定价策略
  • 阶梯定价：用量越多单价越低
  • 管理方式：后台可视化动态配置
  • 示例规则：
    • 0-100 万 Token：0.002 元/Token
    • 100-500 万 Token：0.0018 元/Token
    • 500 万以上：0.0015 元/Token
6.3 租户隔离
  • 混合方案：
    • 物理隔离：客户账单信息、客户 API 密钥
    • 逻辑隔离：普通业务数据
6.4 告警响应
  • 仅发送告警通知，由运营人员人工处理
  • 不自动执行限流或停止服务操作
6.5 系统扩展
  • 配置化支持新模型和新渠道
  • 只需配置模型名称和 Token 倍率
  • 无需修改代码
6.6 费用分摊（内部自用）
  • 混合方式：部门基础固定配额 + 超出部分按用量分摊
  • 各部门分配固定月度额度
  • 超出部分按实际 Token 消耗比例分摊
