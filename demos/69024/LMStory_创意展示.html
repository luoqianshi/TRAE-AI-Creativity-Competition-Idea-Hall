先把故事玩出来，
再把玩出来的故事变成书。

LMStory 是一个手机电脑都能跑的多端 App。它不是又一个 ChatGPT 套壳，而是一套「让 AI 真正能讲长故事」的工程方案——每轮你控剧情，AI 边玩边记，玩完导出小说。

赛道 生活娱乐 形态 Flutter 多端 App 开源 v0.1 + v0.2 截稿 7/15 前
为什么做这个

市面上的「AI + 写故事」，你是旁观者。

AI 写小说你给大纲、AI 跑团你配世界、AI 陪伴只陪聊不前进、通用聊天 20 轮就失忆。LMStory 想把你拉回主角位——剧本是你推动的，AI 只负责续写、记忆、不前后矛盾。

现状 · 旁观者模式

AI 写小说类

给个大纲，AI 一段段写。你在旁边看，没参与感，写到第 8 章 AI 已经忘了第 2 章的人物叫什么。

LMStory · 玩家模式

每轮你推一步

你跟 AI 说一句，剧情往前走一步。AI 一边续写一边把发生过的事记进「小本本」。玩到结束，小说就是玩的过程本身。

矛盾不在结尾爆发 → 在玩的过程里就被记账本挡掉
PAIN 01

AI 失忆

对话一长，早期情节全忘，剧情自相矛盾。

PAIN 02

状态失控

角色伤好没好、欠不欠债，AI 自己说不清。

PAIN 03

交互单一

只能线性推进，没法探索另一种选择。

PAIN 04

配置僵化

换个模型换风格就要改代码，普通用户动不了。

PAIN 05

玩和写割裂

从「玩」产出一个「可读作品」没有现成工具链。

三档深度

同一个 App，三个深度档。

玩家从基础起步，玩爽了切中级，再喜欢上完整角色扮演。一档比一档慢，但一档比一档不会忘、不会乱。

v0.2 工作机制

AI 不靠幻觉，靠检索。

中级档的核心是「两步生成 + 经历层语义检索」。AI 不自己决定检索什么——它出一稿草稿，顺带标关键词，程序拿关键词去翻历史。这把幻觉风险拦在了程序这一层。

1

草稿生成

LLM · 第 1 次请求
AI 先出一稿，顺带输出关键词。这一步不让 AI 决定检索什么——AI 直接决定容易幻觉，标个关键词就行。
2

关键词 → 检索 → 改写

Program + LLM · 第 2 次请求
程序拿关键词去「小本本」翻发生过的事（FTS5 全文 + 纯 Dart 向量余弦，混合权重 0.5/0.5）。AI 拿翻到的记忆改写一版，顺带输出事件摘要入经历层。
⌘

经历层 append-only：发生过的事件只追加不改写

保留完整时序，是导出小说时不矛盾的根源。失败处理走 原子事务，无降级质量——宁可报错重试，不糊弄用户。组装时稳定前缀优先，最大化 LLM 缓存命中，省 token。

技术栈

不为酷炫，为「能跑、可控、可开源」。

每个选型都对应一个真实约束：包体积、平台兼容、长程叙事连贯性。Clean Architecture 四层，单向依赖，Domain 层纯 Dart 不沾 Flutter。

框架
Flutter ≥ 3.19
一套代码多端跑，Skia 渲染，移动端最佳选择。
状态
Riverpod 2.x + 代码生成
Provider 粒度可控，家族模式动态创建，编译时安全。
存储
drift + SQLite + FTS5
类型安全访问，全文检索，trigram 中文分词。
网络
Dio + http 双引擎
Dio 跑常规，http 跑 SSE——规避 Android 流式 TLS bug。
向量
纯 Dart 余弦相似度
Isolate 后台执行，无原生依赖，≤ 50ms / 2500 条。
安全
flutter_secure_storage
API Key 加密存储，平台 Keychain/Keystore。
工程决策 · 不硬撑

v0.2 原计划用 sqlite-vec 做向量检索，P0 风险门验证：NO-GO——pub 包已废弃（0 likes / 5 月无更新），CMake 构建致命失败。果断切回纯 Dart 暴力检索方案。该回头就回头，文档留痕、决策可见。

诚实的边界，不画饼。

  • v0.1 仅中文 UI、仅 Android 发布，iOS 推迟到正式发版前——精力先压在「长程叙事不出错」这件最难的事上。
  • 不集成图片 / 语音，纯文本交互。把作品的差异化做透，不做大而全。
  • 向量检索为中小规模设计（≤ 5000 条），不追求企业级向量库能力。
  • v0.3 完整角色扮演是规划项，本次大赛交付聚焦 v0.1 可用 + v0.2 冲刺。
