1产品概述

1.1 产品定义

CodeHub 是一款个人化代码仓库管理平台，旨在为开发者提供统一的代码仓库聚合管理能力。平台通过对接多个主流代码托管平台，将分散在不同平台上的仓库信息统一汇聚，实现一站式的仓库监控、变更追踪与发布管理。

1.2 核心价值

📊

聚合

统一聚合 GitHub、Gitee、Gitea、GitCode 四大平台的仓库与用户信息，消除平台壁垒，提供统一视图

🔄

变更追踪

对关注仓库的版本发布、标签创建、文件变更进行持续监测，精准定位每次版本间的差异

📣

发布监测

自动监测关注仓库的新版本发布，对比版本间文件变更，辅助依赖升级决策

📋

技术方案管理

以看板形式管理技术方案，关联仓库组件与部署资源，形成从方案设计到部署落地的闭环

1.4 目标用户

  • 个人开发者：需要同时关注多个平台上的开源项目与技术方案
  • 技术管理者：需要追踪团队依赖的第三方库版本变化，评估升级影响
  • 开源爱好者：关注多个开源项目的动态，及时获取更新信息

1.5 产品边界

包含不包含

  • CI/CD 流水线执行

  • 代码搜索与代码阅读

5.4 核心实体定义

codehub_platform — 平台配置

  • platform_code VARCHAR(20) PK 平台编码，如 GITHUB、GITEE
  • platform_name VARCHAR(50) NOT NULL 平台显示名称
  • platform_color VARCHAR(10) NOT NULL 平台品牌色值
  • api_base_url VARCHAR(255) NOT NULL 平台 API 基础地址
  • access_token_encrypted VARCHAR(512) 加密存储的 Access Token

codehub_repository — 仓库

  • repo_seq BIGINT PK 自增主键
  • repo_code VARCHAR(64) UNIQUE 仓库业务唯一标识
  • platform_code VARCHAR(20) FK 所属平台编码
  • repo_full_name VARCHAR(200) NOT NULL 仓库全名，如 vuejs/vue
  • language VARCHAR(50) 主要编程语言
  • stars_count / forks_count / watchers_count INT Star/Fork/Watcher 数量
  • has_update_flag TINYINT 是否有更新（0=无, 1=有）
  • deleted_flag TINYINT(1) 软删除标志

codehub_tech_plan — 技术方案

  • plan_seq BIGINT PK 自增主键
  • plan_code VARCHAR(64) UNIQUE 方案业务唯一标识
  • plan_name VARCHAR(200) NOT NULL 方案名称
  • status_name VARCHAR(20) 方案状态：PLANNED / IN_PROGRESS / COMPLETED
  • component_count / repo_count INT 关联组件/仓库数量

MongoDB: api_request_log — API 请求日志（集合）

缓存规则 默认缓存有效期：1 小时；缓存 Key：{method}:{url}:{queryParamsHash}；仅缓存 GET 请求的成功响应；Proxy 接口优先从缓存读取，命中则直接返回。

CodeHub 采用单体架构（Monolithic Architecture），不使用微服务架构。系统按业务领域划分为多个 Maven 模块，模块间通过接口依赖通信，共享同一数据库。

7接口规范

7.1 命名规范

约束项规则正确示例错误示例
路径参数禁止使用路径参数，所有参数通过 query param 或 request body 传递/api/repo/queryDetail?repoCode=xxx/api/repo/{id}
路径格式POST /api/{动作}{资源}POST /api/repo/queryPageGET /api/repos

动作（Action）列表

动作说明典型返回
queryPage分页查询{ records: [], total: 100, pageNum: 1, pageSize: 30 }
queryList查询全部（不分页）{ list: [] }
queryDetail查询详情{ data: {} }
create新建资源{ data: { code: "xxx" } }
sync同步数据{ success: true, message: "同步完成" }
check检查/监测{ success: true, message: "检查已触发" }

统一响应格式

JSON Response 
{
  "code": "200",
  "message": "success",
  "data": {}
}
注意 code 字段为字符串类型（String），不是数字类型。前端判断时需同时兼容 "200" 和 200 两种情况。分页响应使用 records（不是 list）和 total（不是 totalCount）。

7.3 第三方 API 代理

代理原则 CodeHub 的前端不直接调用第三方平台 API。所有对 GitHub、Gitee、Gitea、GitCode 的 API 请求均通过 codehub-gateway-proxy 模块统一代理。代理层负责 Token 注入、限流、日志记录、响应转换和错误处理。

GET/api/proxy/org/repos获取组织仓库列表

搜索模式（mode 参数）

mode 值说明行为
exact精准匹配（默认）直接调用 detail 接口，返回精确匹配的单条结果
fuzzy模糊搜索调用平台搜索 API，返回模糊匹配的多条结果

设计模式

  • 策略模式：PlatformClient 接口，每个平台一个实现类
  • 工厂模式：PlatformClientFactory 根据 platformCode 获取对应策略实现
  • 拦截器模式：ApiLogInterceptor 记录所有 API 请求到 MongoDB，并支持接口缓存

8事件驱动机制

8.1 事件总线

使用 RabbitMQ 5.x 作为事件总线，实现模块间的异步解耦。当第三方 API 的支撑能力各异（有的提供 Webhook、有的不支持），需要组合使用各种 API 实时/异步构建才能满足接口需求时，事件驱动机制确保各环节可靠串联。

8.2 事件类型定义

事件名称说明发布方消费方
codehub.repo.follow仓库关注事件codehub-repocodehub-repo, codehub-monitor
codehub.repo.sync仓库同步事件codehub-repocodehub-repo, codehub-monitor
codehub.release.published新 release 发布事件codehub-monitorcodehub-monitor
codehub.tag.created新 tag 创建事件codehub-monitorcodehub-monitor
codehub.baseline.change基线变更检测事件codehub-monitorcodehub-monitor
codehub.file.watch文件变更检测事件codehub-monitorcodehub-monitor
codehub.plan.update方案变更事件codehub-plancodehub-plan, codehub-monitor

8.3 事件流程示例 — 仓库关注流程

1
用户操作：关注仓库

用户在前端发起 POST /api/import/repo 请求

2
codehub_repo 接收请求

验证仓库在第三方平台是否存在 → 创建仓库关注记录（写入 codehub_repository）

3
发布 codehub.repo.follow 事件

通过 RabbitMQ 发布事件，多个消费者异步处理

4
消费者 1（codehub-repo）：触发首次数据同步

同步分支、标签、提交、release 等数据，同步完成后发布 repo_sync_event

5
消费者 2（codehub-monitor）：创建默认配置

创建默认基线、创建默认文件监听规则、创建默认关注基线（基于 default_branch 的最新提交）

8.4 消费者容错策略

策略说明
重试机制消费失败时自动重试，最多 3 次，重试间隔递增（1s → 5s → 30s）
死信队列超过最大重试次数的消息转入死信队列（codehub.dlq），等待人工处理
幂等性每个事件携带唯一 eventCode，消费者处理前检查是否已处理过

9.2 安全性需求

需求项说明
Token 存储第三方平台 Access Token 使用 AES-256 加密后存储，运行时解密
API 日志脱敏请求头中的 Authorization 字段在日志中隐藏
SQL 注入防护使用 MyBatis-Plus 参数化查询，禁止拼接 SQL
XSS 防护前端渲染用户内容时进行转义处理
CSRF 防护后端接口验证 Origin/Referer 头

9.3 性能需求

需求项指标
页面加载首屏加载时间 < 2s（正常网络）
API 响应普通 CRUD 接口响应时间 < 500ms
第三方 API代理转发响应时间 < 3s（含网络延迟）
缓存策略热点数据使用 Redis 缓存，TTL 5 分钟
日志清理API 调用日志按月清理，保留 90 天

9.4 可用性需求

需求项说明
事件重试RabbitMQ 消息消费失败自动重试 3 次
死信处理超过重试次数的消息进入死信队列，支持手动重新投递
优雅停机Spring Boot 应用关闭时等待消息消费完成
数据备份MySQL 每日全量备份，binlog 实时同步
