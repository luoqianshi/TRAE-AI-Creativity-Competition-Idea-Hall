轻量 API Gateway 管理系统

按系统负载/健康度/权重，把流量路由到不同上游接口或页面；并通过“适配层”把各商家不同的 API 报文封装为统一返回，让业务只面对一个稳定接口。

接口负载路由 报文统一（Adapter） 页面跳转路由 灰度 / A/B / 降级 可观测 + 可回滚
目标：统一入口，收敛差异 痛点：多商家字段不一致 风险：上游抖动导致业务连锁故障

为什么做它（背景痛点）

当我们接入多个第三方（商家/供应商）API 时，最大的问题往往不是“能不能调通”，而是 “如何长期维护”：字段命名、嵌套结构、缺省值、单位、错误码……都不一样。

  • 每个业务方各写一套 mapping → 重复建设、质量不一致
  • 供应商字段一变 → 到处改代码，上线风险大
  • 上游故障/抖动 → 很难做到 统一降级与切流

1) 统一入口

对外只提供一个稳定域名与路径，内部再做路由、适配与治理。

2) 负载/健康路由

按权重、健康检查、系统负载或错误率，把请求路由到不同上游。

3) 报文统一（Adapter）

把各商家的返回映射成统一 schema，让业务端调用方式稳定可控。

场景 A：天气聚合（接口报文统一）

业务方只调用：GET /api/weather?city=shanghai，永远拿到一致结构。 

{
  "city": "shanghai",
  "tempC": 28.1,
  "humidity": 0.62,
  "windKph": 12.4,
  "provider": "vendorA",
  "timestamp": "2026-06-26T10:30:00+08:00"
}

上游差异（示例）

Vendor A 与 Vendor B 的返回结构完全不同：

// Vendor A
{ "city": "shanghai", "temp_c": 28.1, "rh": 62, "wind_kph": 12.4 }

// Vendor B
{ "location": { "name": "shanghai" }, "temperature": 28.1, "humidity": 0.62, "windSpeed": 12.4 }

路由 + 适配规则（表达意图的伪配置）

路由策略决定“打到哪个商家”，适配规则把响应映射成统一输出，并支持类型转换/缺省值/容错。 

route:
  path: /api/weather
  upstreams:
    - name: vendorA
      url: https://a.example.com/weather
      weight: 70
    - name: vendorB
      url: https://b.example.com/current
      weight: 30

adapter:
  outputSchema: WeatherV1
  mappings:
    vendorA:
      city: $.city
      tempC: $.temp_c
      humidity: ($.rh / 100)
      windKph: $.wind_kph
    vendorB:
      city: $.location.name
      tempC: $.temperature
      humidity: $.humidity
      windKph: $.windSpeed

场景 B：页面负载路由（跳转/灰度/A/B/降级）

当目标是“页面”而不是 API 时，也可以用同一套路由能力： GET /landing 按策略跳到不同版本。

  • 灰度：白名单/分桶逐步放量
  • A/B：按用户分桶 50/50，观测转化
  • 降级：高负载或依赖异常时切到轻量页面

示例（表达意图）

path: /landing
type: redirect
strategy:
  - when: system.load > 0.85
    to: /landing/low
  - when: user.bucket == "B"
    to: /landing/v2
  - default: /landing/v1

架构设想（轻量但可进化）

为了保持轻量，我倾向于拆分为：控制面（配置/发布/回滚/审计）与 数据面（高性能转发 + 适配执行）。 配置存储可从单机 SQLite 演进到集群化方案（PostgreSQL/etcd/Consul）。

控制面（Control Plane）

  • 路由/适配规则编排
  • 版本发布、回滚、审计
  • 权限与多环境（可选）

数据面（Data Plane）

  • 反向代理转发（高性能）
  • 健康检查与切流
  • 适配执行（mapping/表达式/容错）

路线图（Roadmap）

V0.1（能用）

  • 权重路由 + 健康检查
  • JSON mapping：提取/重命名/简单表达式
  • 基础管理台：CRUD + 发布/回滚

V0.2（好用）

  • 限流/熔断/重试（插件化）
  • 灰度：Header/Cookie/分桶
  • 指标：QPS、P95、错误率、上游健康

V1.0（可规模化）

  • 多租户/权限/审计（企业向）
  • 更强适配：模板/脚本沙盒/缓存
  • 多环境与自动化发布
