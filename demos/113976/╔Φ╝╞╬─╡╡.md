## 1. 产品概述

### 1.1 产品定位
"亲络"是一款**去中心化家族社交平台**。与传统家谱软件不同，它不依赖于单一家族管理员录入数据，而是通过"人人可建、人人可认"的分布式节点模式，将全球用户自动串联成一颗动态演进的"人类家族树"。

### 1.2 核心价值主张
- **发现未知亲人**：通过"认亲"机制，自动补全家谱分支
- **低门槛录入**：不知道姓名也能建节点（占位符），未来可补全
- **隐私分级**：亲疏有别，三代内和三代外信息可见性不同
- **家族社交**：红白喜事通知、活动组织、老照片共享

### 1.3 产品口号（Slogan）
> *"每个人都是一颗星，认亲让家族连成星河。"*

## 2. 核心概念与术语

| 术语 | 定义 |
| :--- | :--- |
| **注册节点（Registered Node）** | 拥有独立账号的正式用户，可登录、编辑、社交 |
| **影子节点（Shadow Node）** | 被添加但未注册的亲属，有临时ID，不可登录 |
| **占位节点（Placeholder Node）** | 连名字都不知道的亲属（如"爷爷的父亲"），仅保留关系，名字为空 |
| **认亲（Claim/Accept）** | 双方互相确认亲属关系的动作 |
| **认领（Claim）** | 影子节点被其本人注册后，升级为正式节点的过程 |
| **合并（Merge）** | 两个节点（通常两个影子）确认为同一人，合并为一个节点 |
| **关系链（Relationship Chain）** | 两个节点之间的路径，如"我→父亲→爷爷→伯父→堂兄" |
| **辈分（Generation）** | 以某人为基准（0代），向上为负，向下为正 |
| **同心圆隐私（Concentric Privacy）** | 以用户为中心，按亲疏距离分层控制信息可见性 |

## 3. 用户角色与权限体系

### 3.1 用户角色定义

| 角色 | 权限 |
| :--- | :--- |
| **普通用户** | 管理自己和三代以内直系亲属，可认亲、合并、社交 |
| **家族分支管理员** | 由系统根据关系网自动识别（如某分支年长者），可编辑该分支公共数据（如字辈、祖籍） |
| **系统管理员** | 处理投诉、违规内容、系统运维 |

### 3.2 隐私分级（核心设计）

| 层级 | 范围 | 可见信息 | 谁可见 |
| :--- | :--- | :--- | :--- |
| **Lv.0 公开** | 无限制 | 姓名（仅昵称/谱名）、在世/已故、辈分 | 任何人 |
| **Lv.1 宗亲** | 五代以内（含旁系） | 真实姓名、出生年份、头像、关系类型 | 确认的亲属 |
| **Lv.2 核心** | 直系三代（父母、子女、配偶） | 联系方式（手机/邮箱）、详细生日、住址城市 | 直系亲属 |
| **Lv.3 私密** | 仅自己 | 身份证号、精确住址、银行信息、个人日志 | 仅本人 |

### 3.3 隐私默认规则

```
默认可见性规则：
- 本人创建的所有节点，默认对【直系三代 + 旁系两代】内亲属开放 Lv.1-Lv.2
- 超出此范围的亲属，默认仅见 Lv.0 公开信息
- 用户可单独对某个亲属或某个分支调整权限（更开放或更封闭）

访问申请流程：
1. 远亲请求查看 Lv.1 以上信息
2. 系统发送通知给信息所有者
3. 所有者可批准/拒绝，或要求回答验证问题（"请说出我母亲的姓氏"）
4. 批准后建立"临时查看"关系，可设有效期（7天/30天/永久）
```

### 3.4 特殊处理：已故人员

```
已故人员的信息可见性自动升一级：
- 已故超过50年：默认 Lv.0 公开（名字、生卒年）
- 已故但不足50年：仅对认亲的亲属开放 Lv.1
- 用户可手动设置"已故人员信息全网公开"（用于历史人物整理）
```

##### 4.2.2.1 添加亲属（双向绑定）

```
操作流程：
1. 选择关系（下拉菜单）：
   - 父母：父亲 / 母亲
   - 子女：儿子 / 女儿
   - 配偶：丈夫 / 妻子
   - 兄弟姐妹：哥哥 / 弟弟 / 姐姐 / 妹妹

   - 其它：岳父 / 岳母 / 公公 / 婆婆 / 养父母 / 继父母

2. 搜索已有用户：
   - 输入姓名/昵称/手机号/曾用名
   - 系统返回匹配结果（含注册用户和影子节点）
   - 如找到 → 选择已有节点，发送"关系确认请求"
   - 如未找到 → 创建新节点（影子或占位）

3. 创建新节点（影子）：
   - 必填：姓名（或留空作为占位节点）
   - 可选：性别、出生年份、籍贯、头像
   - 备注：自由文本
   - 保存后生成影子节点，ID为临时UUID

4. 关系确认：
   - 对方是注册用户：发送"亲属关系确认通知"
   - 对方是影子节点：无需确认（由创建者管理）
   - 对方是占位节点：显示为"待完善"状态
```

##### 4.2.2.2 认亲机制（您的核心创意）

| 场景 | 操作 | 系统行为 |
| :--- | :--- | :--- |
| **您添加了表弟的账号** | 搜索"李四"（表弟）→ 选择账号 → 选择"表兄弟" | 发送认亲请求给李四，李四确认后，双方关系链自动交叉比对 |
| **认亲后的关系补全** | 李四有"姑姑王芳"，您没有 | 系统检测到您和李四的共同祖先（外祖父母），向您推荐"疑似姑姑" |
| **一键添加推荐亲属** | 您点击"确认" | 王芳作为影子节点加入您的族谱，标注"来自表弟李四" |
| **从对方处批量导入亲属** | 认亲后，系统展示"对方有而您无"的亲属列表 | 您可勾选批量添加（需对方公开权限允许） |

```
认亲请求确认后的数据合并逻辑：
1. 比对双方的直系祖先链，找到共同祖先（最近公共祖先）
2. 基于共同祖先，计算各自的旁系分支
3. 将对方的旁系分支中"您缺失且对方公开"的部分，作为推荐列表
4. 您确认一个，系统就在您的谱系中创建影子节点
5. 所有节点保留"数据来源"元数据（来自XX的认亲）
```

##### 4.2.2.3 合并节点

```
触发条件：
- 您发现两个影子节点实际上是同一人（如"舅舅"和"大舅"）
- 系统智能推荐合并（相似度>85%）

合并流程：
1. 选择主节点（保留的节点）和从节点（被合并的节点）
2. 系统展示两个节点的所有信息，供用户选择保留哪些
3. 确认合并后：
   - 所有关系边从主节点继承
   - 从节点标记为 merged_to = 主节点ID
   - 从节点的ID保留在历史中（用于回溯）
   - 所有引用从节点的关系自动重定向到主节点
```

# “亲络”关系建模与功能设计 V2.0
## —— 超越血缘：覆盖传统、现代与拟亲缘的完整关系网络


### 1. 核心理念升级

“亲络”不仅连接血脉，更尊重选择。我们认为，**构成“家人”的，既有血缘的必然，也有情感的联结**。因此，系统将原生支持：

- **血缘关系**：传统父系、母系血亲。
- **姻缘关系**：通过婚姻建立的亲属。
- **拟亲缘/非血缘关系**：通过情感、仪式或约定建立的类家庭关系。


### 2. 关系类型全集（枚举）

### 3. 技术建模方案

#### 3.1 数据存储策略
所有关系，无论血缘或拟亲缘，在Neo4j图数据库中均存储为 **`RELATIONSHIP`** 边（Edge）。通过`type`属性区分具体类型。

**关系边的JSON结构（扩展后）：**
```json
{
  "id": "rel_uuid_123",
  "type": "SWORN_FATHER", 
  "from_person_id": "uuid_child",
  "to_person_id": "uuid_godfather",
  
  // 元数据
  "verified": true,
  "verified_at": "2024-01-01T00:00:00Z",
  "verified_by": "uuid_verifier",
  "source": "user_added", // 或 'sworn_ceremony', 'claim_merge'
  
  // 拟亲缘特有字段 (扩展)
  "sworn_details": {
    "ceremony_date": "2020-08-15",
    "ceremony_place": "北京市朝阳区XX酒店",
    "witnesses": ["证人1", "证人2"],
    "notes": "正式拜师认亲仪式",
    "group_name": "京城四少" // 适用于结拜组
  },
  
  // 通用时间线
  "start_date": "2020-08-15",
  "end_date": null, // 如关系解除，则记录日期
  "is_active": true,
  
  // 隐私控制
  "privacy_level": 1, // 默认为宗亲可见。认亲关系较敏感，默认不公开。
  "created_at": "...",
  "updated_at": "..."
}
```

#### 3.2 用户界面交互设计

在“添加亲属”的流程中，增加一个**高阶选项**：

**界面文案**： *“这段关系是？（可选）”*
**选项**：
- ○ **血缘/姻亲** (默认)
- ● **非血缘关系** (选择后展开子选项)
    - ☑ 义亲 (父/母/子/女)
    - ☑ 结拜 (兄/弟/姐/妹)

**选择“非血缘关系”后，新增录入字段：**
- 确认日期（或仪式日期） `sworn_details.ceremony_date`
- 地点 `sworn_details.ceremony_place`
- 证人或见证人 `sworn_details.witnesses`
- 结拜组名（可选） `sworn_details.group_name`
- 备注（用于记录这段关系的由来或故事）

#### 3.3 在家族树上的视觉呈现

为了让家谱图能直观反映这些关系，可以设计一套视觉区分方案：

*   **血缘关系**：实线 `——`，金色/暖色。这是家族树的“骨架”，视觉上最突出。
*   **姻亲关系**：虚线 `- - -`，暖橙色。表明是通过婚姻连接的“外延”。
*   **义亲关系 (新增)**：**双线** `══`，翠绿色或天蓝色。寓意“双重联结”，既有情感的牵绊，也有承诺的约束。
*   **结拜关系 (新增)**：**点虚线** `···`，紫色。表明是“精神盟友”，如兄弟般的情谊。


### 4. 跨功能交互逻辑

#### 4.1 隐私默认规则（补充）

*   **拟亲缘（义亲/结拜）默认隐私等级为 `Lv.1（宗亲）`**：即只对已确认的五代以内亲属可见。理由是这类关系在中国文化中有时涉及隐私或特殊背景（如旧社会拜干亲避灾、商业结盟等），不应默认全网公开。
*   用户可以手动为每条拟亲缘关系调整可见性（公开/仅自己/特定分支可见）。
*   当拟亲缘关系被删除或解除时，系统记录“关系解除”事件，可保留历史版本（显示为“已解除”的灰色虚线）。

#### 4.2 动态与事件通知

*   **结拜/认亲事件模板**：当用户添加义亲或结拜关系时，系统可自动生成一条动态模板。
    *   示例：*“🎉 张伟与李强于2024年元旦在西安结为异姓兄弟，共立金兰之誓。”*
    *   示例：*“🙏 王芳今日正式认刘奶奶为干娘，从此两家结亲。”*
*   **关系提醒**：在义亲/干娘的生日、结拜纪念日等节点，系统可发送提醒。

#### 4.3 搜索与发现

*   支持通过**结拜组名**搜索，发现历史上的义结金兰群体（如“民国时期‘七君子’结拜组”）。
*   在亲属推荐中，若两人有共同的义亲或结拜兄弟，可作为“弱关系”推荐，提示：“您和XXX可能通过义亲XXX产生关联，是否建立连接？”


### 5. 总结：本次升级的核心价值

1.  **更真实地反映中国（及东亚）社会现实**：在中国人的实际生活中，“干亲”和“结拜”是极其普遍且重要的社会关系。许多人的家谱或人生叙事中，这些人扮演着不亚于血缘亲属的角色。
2.  **增加用户粘性与故事性**：记录一段“拜把子”或“认干亲”的历史，本身就充满了故事性。这能让“亲络”从单纯的“工具”变成承载家族记忆与情感的“叙事平台”。
3.  **技术稳健扩展**：选择在现有关系模型上增加枚举值（Type）和可选扩展字段（Sworn Details），而非推翻重来，这对开发团队最友好，技术风险最低。

## 5. 数据模型设计

### 5.1 用户节点（Person Node）

**存储位置**：PostgreSQL（主表）+ Neo4j（节点属性）

```sql
CREATE TABLE persons (
    -- 主键
    id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    
    -- 节点类型标识
    node_type VARCHAR(20) NOT NULL DEFAULT 'registered', -- registered / shadow / placeholder
    is_registered BOOLEAN DEFAULT true,
    is_placeholder BOOLEAN DEFAULT false, -- 名字为空的占位
    
    -- 姓名相关（核心）
    primary_name VARCHAR(100) NOT NULL, -- 显示用主名
    surname VARCHAR(50),                -- 姓氏（便于检索）
    given_name VARCHAR(50),             -- 名字（便于检索）
    
    -- 多语言名（JSON数组）
    names JSONB DEFAULT '[]'::jsonb,
    -- 结构: [{"lang":"zh-CN","type":"official","name":"张伟"},
    --        {"lang":"en-US","type":"english","name":"David Zhang"},
    --        {"lang":"zh-CN","type":"childhood","name":"小石头","period":"1980-1990"}]
    
    -- 别名（JSON数组）
    aliases JSONB DEFAULT '[]'::jsonb,
    -- 结构: [{"name":"建国","period":"1980-1990","note":"曾用名"}]
    
    -- 基本人口学信息
    gender VARCHAR(10), -- MALE / FEMALE / OTHER
    birth_date DATE,
    birth_date_accuracy VARCHAR(20), -- exact / year / decade / estimated
    birth_place VARCHAR(200),
    death_date DATE,
    death_date_accuracy VARCHAR(20),
    death_place VARCHAR(200),
    is_alive BOOLEAN DEFAULT true,
    
    -- 隐私与状态
    privacy_level INT DEFAULT 2, -- 0=公开, 1=宗亲, 2=核心, 3=私密
    status VARCHAR(20) DEFAULT 'active', -- active / pending / merged / deleted
    
    -- 关联信息
    shadow_token VARCHAR(64) UNIQUE, -- 影子节点的临时邀请码
    created_by UUID REFERENCES persons(id), -- 影子节点由谁创建
    merged_to UUID REFERENCES persons(id),  -- 如果被合并，指向主节点
    
    -- 扩展信息
    bio TEXT,                           -- 备注
    avatar_url VARCHAR(500),
    contact_info JSONB DEFAULT '{}'::jsonb, -- 手机/邮箱/微信（受隐私控制）
    custom_fields JSONB DEFAULT '{}'::jsonb, -- 用户自定义字段
    
    -- 系统字段
    created_at TIMESTAMP DEFAULT NOW(),
    updated_at TIMESTAMP DEFAULT NOW(),
    last_active_at TIMESTAMP,
    
    -- 索引
    INDEX idx_persons_name (primary_name),
    INDEX idx_persons_shadow_token (shadow_token),
    INDEX idx_persons_merged_to (merged_to),
    INDEX idx_persons_created_by (created_by)
);
```

### 6.3 Neo4j查询示例（给开发者的参考）

```cypher
// 1. 查询两个节点的共同祖先
MATCH path1 = (a:Person {userId: 'uuid1'})-[:FATHER_OF|MOTHER_OF*]->(ancestor)
MATCH path2 = (b:Person {userId: 'uuid2'})-[:FATHER_OF|MOTHER_OF*]->(ancestor)
RETURN ancestor, path1, path2
LIMIT 1

// 2. 查询某个人的所有三代以内亲属
MATCH path = (me:Person {userId: 'uuid1'})-[:FATHER_OF|MOTHER_OF|SPOUSE_OF*1..3]-(relative)
RETURN relative, relationships(path)

// 3. 推荐可能认识的亲属（基于共同朋友/亲属）
MATCH (me:Person {userId: 'uuid1'})-[:FATHER_OF|MOTHER_OF*1..2]->(ancestor)
MATCH (ancestor)-[:FATHER_OF|MOTHER_OF*1..2]->(candidate:Person)
WHERE NOT (me)-[:FATHER_OF|MOTHER_OF|SPOUSE_OF]-(candidate)
AND candidate.userId <> 'uuid1'
RETURN candidate, count(candidate) AS relevance
ORDER BY relevance DESC
LIMIT 10
```

### 9.2 安全需求

| 需求 | 措施 |
| :--- | :--- |
| 数据传输 | 全站HTTPS（TLS 1.3） |
| 密码存储 | bcrypt加密（加盐） |
| JWT有效期 | Access Token 2小时，Refresh Token 7天 |
| 敏感信息 | 手机号/邮箱在数据库中加密存储（AES-256） |
| 防滥用 | 认亲请求每天上限20次，防止爬虫骚扰 |

## 11. 风险与应对

| 风险 | 影响 | 应对措施 |
| :--- | :--- | :--- |
| **数据隐私泄露** | 严重（产品生死） | 严格权限控制、数据加密存储、定期安全审计、第三方安全认证 |
| **恶意认亲/虚假关系** | 中等 | 验证问题机制、人工举报、合并请求需双方确认、关系权重评分 |
| **数据膨胀（影子节点过多）** | 中等 | 定期清理孤岛节点（无关系连接）、合并建议算法、用户可手动归档 |
| **亲属关系复杂（再婚/收养）** | 中等 | 关系类型枚举全面覆盖、支持多重关系（如同父异母）、姻亲关系明确标注 |
| **用户增长缓慢** | 中等 | 先发功能（GEDCOM导入）吸引家谱爱好者、裂变机制（邀请有奖） |
| **法规合规（GDPR/CCPA）** | 低 | 隐私政策明确、数据导出功能、账号删除功能、未成年人保护 |
| **数据库性能瓶颈** | 低 | Neo4j集群部署、查询优化、缓存策略、分库分表（未来） |

### 12.1 GEDCOM映射表（导入/导出）

| GEDCOM字段 | 内部字段 | 处理方式 |
| :--- | :--- | :--- |
| `0 @I1@ INDI` | `persons.id` | 映射为UUID（或生成新ID） |
| `1 NAME David /Zhang/` | `primary_name` + `names` | 解析姓氏/名字，存入primary_name；完整名存入names数组 |
| `1 SEX M` | `gender` | M→MALE, F→FEMALE |
| `1 BIRT 2 DATE 15 JUN 1985` | `birth_date` | 解析日期，精确度标记为exact |
| `1 DEAT Y` | `is_alive` | Y→false, N→true |
| `1 NOTE ...` | `bio` | 直接映射 |
| `1 _NAME_ZH 张伟` | `names` (lang=zh-CN) | 自定义标签，存入扩展字段 |
| `1 FAMC @F1@` | 关系边 | 创建父子/母女关系边 |
