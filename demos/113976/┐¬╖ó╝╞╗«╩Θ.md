# 亲络家谱 开发计划书

创建日期：2026-07-11
文档定位：分阶段开发计划与验收标准
适用阶段：S0–S7（核心功能闭环）

---

## 一、总体原则

### 1.1 开发节奏
- 分阶段交付，每完成一个阶段（S0、S1...）由用户验收
- 验收通过后，合并到 `main` 分支，进入下一阶段
- 验收不通过，在当前阶段修改直到通过

### 1.2 技术路线分两步走

| 阶段 | 数据存储方案 | 说明 |
| :--- | :--- | :--- |
| **S0–S3** | 纯前端 + IndexedDB | 不需要后端、不需要数据库，先把 UI 和功能做对 |
| **S4 之后** | 评估是否加本地后端 | 视情况引入 Node.js + SQLite |
| **设计验证通过** | 申请域名、上云 | 部署到 Gitee Pages / Vercel / 阿里云 |

### 1.3 关键设计原则
- 所有数据操作通过 `service` 层封装（如 `personService.ts`、`relationshipService.ts`）
- service 内部初期用 IndexedDB，后期可换成 HTTP API 调用
- UI 组件不直接操作数据库，只调 service
- 这样后期迁移到后端时，只改 service 实现，UI 完全不动

## 二、Git 版本管理

### 2.1 托管平台
**Gitee**（码云），私有仓库

### 2.2 分支策略

```
main         ← 稳定版，每完成一个阶段合并一次
  └── dev    ← 日常开发在这里
       ├── feature/tree-layout    ← 做家谱树布局
       ├── feature/auth-login     ← 做登录功能
       └── feature/claim-system   ← 做认亲系统
```

| 分支 | 用途 | 合并规则 |
| :--- | :--- | :--- |
| `main` | 验收通过的稳定版本 | 只接收 dev 合并 |
| `dev` | 当前正在做的开发版 | 接收 feature 合并 |
| `feature/xxx` | 单个功能开发 | 完成后合并到 dev |

### 2.3 版本号规则

```
v0.1.0  ← S0 准备完成
v0.2.0  ← S1 登录认证完成
v0.3.0  ← S2 本人节点完成
...
v1.0.0  ← 全部核心功能完成，可上线
```

格式：`v大版本.功能版.修复版`

### 2.4 提交信息规范

```
feat: 添加家族树布局算法（父母上层、子女下层 U 形连接）
fix: 修复虚拟节点 Handle ID 不匹配导致线条不显示
docs: 更新 P0 需求文档
refactor: 重构关系服务为图数据库适配
style: 调整家谱树节点样式
```

| 前缀 | 含义 |
| :--- | :--- |
| `feat:` | 新功能 |
| `fix:` | 修 bug |
| `docs:` | 改文档 |
| `refactor:` | 重构（不改功能） |
| `style:` | 改样式 |

### 2.5 操作流程

```bash
# 1. 看当前状态
git status

# 2. 切到 dev 分支
git checkout dev

# 3. 干完一个功能，提交
git add .
git commit -m "feat: xxx功能"

# 4. 推送到 Gitee
git push origin dev

# 5. 验收通过后合并到 main
git checkout main
git merge dev
git push origin main
```

#### S7.1 认亲后合并逻辑（详细规则）

**背景**：用户 A 和用户 B 可能各自添加了同一个人（如 A 记录了父亲张三，B 也记录了父亲张三）。认亲成功后需要合并这两个节点。

**合并优先级规则**：

| 关系层级 | 合并以谁为准 | 说明 |
| :--- | :--- | :--- |
| 晚辈（子女/孙辈） | 以本人直系为准 | 本人直接添加的子女优先于配偶添加的 |
| 平辈（兄弟姐妹/配偶） | 以账号人为准 | 有注册账号的人优先于影子节点 |
| 长辈（父母/祖父母） | 以点选谁的为准 | 谁主动添加的长辈就以谁的为准 |
| 长辈有账号 | 以长辈为准 | 如果长辈自己也注册了账号，以长辈自己的资料为准 |

**合并流程**：
1. 检测到重复（认亲成功后，两人有共同亲属节点）
2. 提示用户"检测到可能重复的亲属，是否合并？"
3. 按优先级规则确定主节点和从节点
4. 字段冲突解决（逐项选择）
5. 关系迁移（从节点的关系重定向到主节点）
6. 从节点标记为 `merged`，保留历史记录

**特殊情况处理**：
- 前妻/前夫的子女：不自动合并，需手动确认
- 收养/继子女：保留关系类别标记，不合并为亲生
- 同名不同人：提供"不是同一人"选项，跳过合并

**认亲请求触发合并的场景**：
1. A 认亲 B 为兄弟 → A 的父亲 和 B 的父亲 可能是同一人
2. A 认亲 B 为父子 → A 和 B 的记录直接关联，不需要合并
3. A 认亲 B 为配偶 → A 的子女 和 B 的子女 可能重复，需合并

## 十、风险提示

| 风险 | 应对 |
| :--- | :--- |
| 家谱树布局算法复杂 | S4 单独列为重点阶段，参考成熟方案 |
| IndexedDB 数据丢失 | 定期导出 JSON 备份 |
| 一个人开发进度慢 | 严格按阶段走，不跳步 |
| 后期迁移后端工作量大 | service 层抽象到位，UI 不动 |
| 功能膨胀 | 每阶段严格限定范围，不临时加功能 |
