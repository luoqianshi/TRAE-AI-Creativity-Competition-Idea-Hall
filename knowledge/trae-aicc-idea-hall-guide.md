## 二、产品定位与价值

### 2.1 解决的问题

TRAE AI 创造力大赛吸引了海量参赛者，每天有数百条新的创意帖发布在社区论坛。但存在三大痛点：

1. **发现难**：参赛作品散落在论坛各个帖子中，没有统一入口浏览和体验
2. **筛选难**：论坛帖子格式不一，HTML Demo 需要逐个下载打开，无法快速预览
3. **追踪难**：官方审核通过名单分散在飞书多个批次的多维表格中，无法与论坛帖子自动关联

### 2.2 产品定位

一个**自动化的创意作品聚合展示平台**，核心价值主张：

- **实时性**：从发帖到上线，全程无人干预，每日自动更新
- **可体验**：每个 HTML Demo 可一键在线打开，附带截图预览
- **可筛选**：按五大赛道分类，支持搜索、排序、审核状态筛选
- **零成本**：纯静态托管，无服务器、无数据库、无运行时依赖

### 2.3 目标用户

| 用户群体 | 核心需求 | 产品价值 |
|---|---|---|
| 大赛参赛者 | 参考他人作品，获取灵感 | 一站式浏览 26000+ 创意，按赛道/关键词筛选 |
| 大赛组委会 | 监控参赛进度，发现优秀作品 | 实时数据看板，审核通过率/赛道分布统计 |
| TRAE 产品团队 | 了解用户创意方向，发现产品机会 | 结构化的创意数据库，支持关键词搜索 |
| TRAE 开发者运营 | 推广社区生态，策划运营活动 | 可分享的展示链接，截图预览提升传播效果 |

### 3.2 技术选型

| 层级 | 技术选型 | 选型理由 |
|---|---|---|
| 数据采集 | Python + requests + BeautifulSoup | 成熟稳定的爬虫技术栈，社区支持好 |
| 数据源 | 飞书lark-cli + Discourse REST API | 双数据源确保完整性和准确性 |
| 模板渲染 | Jinja2 | Python 生态标准模板引擎，灵活可靠 |
| 截图生成 | Playwright + headless Chromium | 现代 WebDriver 替代方案，API 简洁 |
| 前端 | 原生 HTML/CSS/JS（无框架） | 零依赖，加载快，GitHub Pages 完美兼容 |
| 部署 | GitHub Pages + GitHub Actions | 免费托管，自动部署，自带 HTTPS 和 CDN |
| 自动化 | TRAE 定时任务（cron） | 原生集成 TRAE 生态，每日自动执行 |

### 3.3 技术选型的核心思路

**「零成本 + 全自动」是整个架构的核心设计约束。**

不使用任何付费服务：没有云服务器、没有数据库、没有 CDN 付费套餐、没有监控告警服务。整条链路的成本为零，但支撑了 26000+ 条数据的每日自动更新和全球访问。

这要求在技术选型上做出取舍：
- 放弃 React/Vue 等前端框架，用原生 JS 换取零构建依赖和最快加载速度
- 放弃后端 API，用静态 JSON 文件换取零运维成本
- 放弃数据库，用 JSON 文件 + 增量更新逻辑换取零基础设施依赖
- 放弃传统截图方案（Selenium），用 Playwright 换取更轻量的依赖和更好的并发能力

## 四、核心模块详解

### 4.1 爬虫系统

#### 4.1.1 双数据源策略

项目从 v1（纯 Discourse API）演进到 v2（双数据源），核心变化是以飞书审核名单为主数据源：

```
v1 架构（已弃用）:
  Discourse API → 遍历 Category 39 所有帖子 → 提取 Demo

v2 架构（当前）:
  飞书审核名单（主）          Discourse API（补充）
       │                           │
       ▼                           ▼
  已审核项目优先收录        未审核的新帖捕获
  approved = True           approved = False
       │                           │
       └─────────┬─────────────────┘
                 ▼
           合并去重 → demos.json
```

**双数据源的必要性**：
- 飞书审核名单确保已审核项目 100% 收录（不会因 API 分页遗漏）
- Discourse API 补充捕获尚未审核的新帖（用户发帖后立即可见）
- 两者的 topic_id 用于交叉比对，确保审核状态准确

#### 4.1.2 四层 Demo 提取策略

参赛者上传 Demo 的方式多种多样，爬虫需要处理所有情况：

| 优先级 | 策略 | 场景 | 实现方式 |
|---|---|---|---|
| 1 | HTML 附件 | 最常见，直接上传 .html 文件 | 解析 `<a class="attachment">` 标签 |
| 1b | ZIP 附件 | 上传压缩包，内含多个文件 | 下载 ZIP → 解压 → 查找 HTML（优先 index.html） |
| 2 | Onebox 链接 | 外部部署的 Demo（如 Netlify） | 解析 `<aside class="onebox">` 外链预览卡片 |
| 3 | 关键词兜底 | 正文中有"demo/体验/预览"等关键词的链接 | 遍历 `<a>` 标签 + 父元素文本匹配 |

**排除规则**：过滤 github.com、bilibili.com、forum.trae.cn 等非 Demo 域名。

#### 4.1.3 爬虫类设计

爬虫采用面向对象设计，四个核心类各司其职：

```
DemoHallCrawler（主编排器）
    │
    ├── DiscourseClient（API 客户端）
    │   ├── 限速：1.5s/请求
    │   ├── 重试：最多5次，指数退避（基数2，上限8s）
    │   ├── 429处理：读取 Retry-After 头动态等待
    │   └── 超时：API 15s，下载 60s
    │
    ├── DemoExtractor（Demo 提取器）
    │   ├── 四层优先级策略
    │   ├── URL 校验和域名过滤
    │   └── 文件类型识别（HTML/ZIP）
    │
    └── DataManager（数据管理器）
        ├── 增量更新：topic_id 去重
        ├── 合并写入：只覆盖非 None 字段
        ├── 自动统计：total/approved/unapproved
        └── 检查点：每25条自动保存
```

#### 4.1.4 容错与恢复机制

爬虫在设计上充分考虑了中断恢复：

- **检查点机制**：每处理 25 条记录自动保存 demos.json，中断后重新运行从断点继续
- **合并写入模式**：`add_or_update()` 只覆盖非 None 字段，不会因重试丢失已有数据
- **降级方案**：飞书 API 不可用时回退到纯 Discourse 模式
- **容错截图**：Playwright/Chromium 不可用时跳过截图，不影响主流程

### 4.2 Insight 洞见生成引擎

#### 4.2.1 设计目标

为每张卡片自动生成一句话洞见（平均 26 字），让用户在不点开 Demo 的情况下快速理解项目核心价值。

#### 4.2.2 规则引擎四层策略

```
输入：title + excerpt（帖子标题 + 摘要）
                    │
                    ▼
┌─────────────────────────────────────┐
│ 策略1: 提取「想解决什么问题」后的描述  │ ── 命中率最高
└──────────────┬──────────────────────┘
               │ 未命中
               ▼
┌─────────────────────────────────────┐
│ 策略2: 提取「创意介绍」后的项目说明    │
└──────────────┬──────────────────────┘
               │ 未命中
               ▼
┌─────────────────────────────────────┐
│ 策略3: 取 excerpt 中第一个有意义的句子│
└──────────────┬──────────────────────┘
               │ 未命中
               ▼
┌─────────────────────────────────────┐
│ 策略4: 从 title 提取副标题或整个标题  │ ── 兜底
└─────────────────────────────────────┘
               │
               ▼
         文本清洗 + 截断至60字
```

#### 4.2.3 文本清洗

自动去除以下噪音：
- HTML 标签（`<br>`, `<p>`, `<span>` 等）
- Discourse 格式标记（`【标题】`, `【标签】`, `【正文】`）
- 赛道前缀（如「学习工作赛道」「生活娱乐」）
- 填充词（如「做一个」「一款」「基于」开头的冗余表述）
- 多余空白和特殊字符

**质量指标**：赛道前缀残留率 0%，仅 2 条回退为「暂无简介」。

### 4.3 截图生成系统

#### 4.3.1 技术方案

使用 Playwright 驱动 headless Chromium，为每个有 Demo 的项目自动生成截图：

```
demos/{topic_id}/xxx.html → Playwright加载 → 截图 → JPEG(quality=75) → WebP转换
```

#### 4.3.2 性能优化

| 维度 | 参数 | 说明 |
|---|---|---|
| 并发数 | 8 路页面同时截图 | asyncio.Semaphore 控制并发 |
| 视口尺寸 | 1280 x 800 | 保证截图清晰度 |
| 超时 | 15 秒 | 防止恶意页面卡死 |
| 渲染等待 | 1.5 秒 | 等待 JS 动画完成 |
| 格式 | WebP (quality=75) | 比 PNG 小 70%，比 JPEG 小 30% |
| 增量 | 跳过已存在的截图 | 基于文件存在性判断 |

#### 4.3.3 浏览器发现策略

`_find_chrome()` 按以下顺序自动查找浏览器：
1. Playwright 管理的 Chromium（`~/.cache/ms-playwright/chromium-*/chrome-linux64/chrome`）
2. 系统 `google-chrome-stable`（`/usr/bin/google-chrome-stable`）
3. 系统 `chromium` / `chromium-browser`

### 4.4 前端展示系统

#### 4.4.1 性能优化策略

支撑 26000+ 卡片展示的核心性能设计：

| 策略 | 实现 | 效果 |
|---|---|---|
| 骨架数据分离 | index.html 仅 6.3KB，数据外置 demos.min.js | 首屏不阻塞 |
| 手动加载更多 | 每批 50 张，底部按钮触发 | 用户可控，不自动消耗资源 |
| DOM 回收 | 超过 200 张移除顶部，保留 150 张缓冲 | DOM 节点数恒定 |
| 数据层过滤 | 搜索/排序在 JS 数组完成，不操作 DOM | O(n) 复杂度 |
| CSS 渲染优化 | `content-visibility: auto` 跳过离屏渲染 | GPU 负担降低 |
| Gzip 压缩 | GitHub Pages 自动启用 | 传输体积降至 23% |

#### 4.4.2 交互功能

| 功能 | 实现方式 | 用户体验 |
|---|---|---|
| 赛道筛选 | 点击 tag-pill 切换 active | 即时响应，五大赛道 + 野蛮生长 |
| 关键词搜索 | 300ms 防抖，匹配 title + insight | 大小写不敏感，实时过滤 |
| 排序 | 最新发布 / 最多浏览 / 最多点赞 | 三种排序维度 |
| 审核筛选 | Toggle 开关 | 仅展示官方审核通过 / 展示全部 |
| 在线体验 | 新窗口打开 HTML Demo | 无需下载，直接体验 |
| 截图预览 | 卡片展示 WebP 截图 | 快速了解 Demo 长什么样 |

#### 4.4.3 视觉设计

TRAE 品牌风格的深色科技风：

- **配色**：纯黑底色（`#0a0a0a`）+ 荧光绿强调色（`#22c55e`）
- **粒子动画**：Canvas 2D 实现 60 个粒子 + 距离连线 + 鼠标交互
- **毛玻璃导航**：`backdrop-filter: blur(14px)`，滚动后加深
- **卡片动画**：IntersectionObserver 逐张延迟 30ms 入场
- **语义化 SVG**：所有图标内联 SVG，统一荧光绿配色

### 4.5 自动化更新流程

#### 4.5.1 每日更新七步流程

```
Step 0: 环境准备 → 安装依赖、配置Git
    │
Step 1: 飞书Wiki获取 → lark-cli读取审核名单（17个批次）
    │
Step 2: 审核名单同步 → 合并到 approved_projects.json
    │
Step 3: 交叉比对 → 更新 demos.json 中的 approved 状态
    │
Step 4: 增量Demo爬取 → 四层策略提取新审核项目的Demo
    │
Step 4.5: 截图生成 → Playwright为新增Demo自动截图
    │
Step 5: 渲染 → 生成 demos.min.js + index.html
    │
Step 6: README更新 → 统计表格和日期
    │
Step 7: Git提交推送 → 触发GitHub Actions自动部署
```

#### 4.5.2 TRAE 定时任务

```
cron: 0 4 * * *  （每日北京时间 04:00）
```

通过 TRAE 定时任务执行 `prompt/update.md` 中的自动化提示词，完整覆盖七步流程。

#### 4.5.3 CI/CD 部署

```
Git push 到 main
    │
    ▼
GitHub Actions (deploy.yml)
    ├── checkout 代码
    ├── 配置 Pages 环境
    ├── 上传静态资源
    └── 部署到 GitHub Pages
    │
    ▼
用户访问 (HTTPS + CDN加速)
```

## 六、工程实践与能力体现

### 6.1 产品思维

#### 6.1.1 用户场景驱动设计

从「参赛者如何发现他人作品」这一核心场景出发，设计了完整的用户旅程：

```
用户打开网站
    │
    ▼ 首屏50张卡片 + 统计数字
    │
选择赛道筛选（如「学习工作」）
    │
    ▼ 即时过滤，展示9930条学习工作赛道作品
    │
关键词搜索（如「AI学习」）
    │
    ▼ 300ms防抖搜索，匹配title+insight
    │
看到感兴趣的项目
    │
    ▼ 查看截图预览 → 点击「在线体验」→ 新窗口打开Demo
    │
查看原帖
    │
    ▼ 点击作者名 → 跳转社区原帖
```

#### 6.1.2 数据驱动决策

项目中的每个设计决策都有数据支撑：
- 「手动加载更多」取代自动无限滚动：因自动滚动出现"鬼畜"抖动问题
- 数据外置到 demos.min.js：因 index.html 内联数据导致首屏阻塞
- DOM 回收机制：因 26000+ DOM 节点导致页面卡顿
- 检查点间隔从 100 条降至 25 条：因超时中断导致数据丢失

4. **体现了产品能力**：从用户场景出发，数据驱动决策，持续迭代优化
5. **展现了技术深度**：爬虫架构、前端性能优化、自动化流程、容错恢复

这些能力直接映射到 AI 产品经理和 TRAE 开发者运营岗位的核心要求：理解技术、理解用户、理解数据、理解生态。
